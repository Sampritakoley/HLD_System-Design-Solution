01 / Understanding the problem

What is this system, really?

A cloud drive lets users upload files from any device, access them anywhere, share them with others, and keep every device automatically in sync. The promise is simple: your file is never lost, and every device shows the same version.

The core tension: file bytes are huge and rarely change, while metadata (names, folders, permissions, versions) is small but changes constantly and needs strong consistency. The two need different systems.

Core features in scope

Upload & download

Upload large files reliably, resume after failures, download or stream quickly.

Folders & sync

Organize files in folders and sync changes across phones, web and desktop.

Sharing & permissions

Share by user or link with viewer, commenter or editor roles.

Versions & trash

Keep file history, restore old versions and recover deleted files.

What makes this hard at scale

  • Huge data. Exabytes of blobs that must survive disk, rack and datacenter failures.
  • Large files on bad networks. A 5 GB upload must resume, not restart.
  • Sync correctness. Many devices, concurrent edits, offline changes and conflicts.
  • Cost. Duplicate files and old versions can double storage unless handled smartly.
  • Permissions. Every read must check access, including inherited folder sharing.
02 / Requirements

Functional vs. non-functional requirements

Non-functional requirements drive the architecture, so they come first.

Functional

  • Upload, download and delete files
  • Create folders; move and rename
  • Auto-sync across all devices
  • Share with people or by link, with roles
  • Version history and restore
  • Search by name and content
  • Offline access with later sync
  • Storage quota per user

Non-functional

  • 1B users, 100M DAU, ~200M uploads/day
  • 11 nines (99.999999999%) durability for files
  • 99.99% availability for reads
  • Strong consistency for metadata and permissions
  • Change visible on other devices in < 5 s
  • Resumable uploads for files up to TBs
  • Secure: encryption in transit and at rest
  • Cost-efficient at exabyte scale

Clarifying questions

Do we support real-time collaborative editing (Docs), or only file storage and sync?
What are the maximum file size and per-user quota?
How do we resolve conflicts when two devices edit the same file offline?
Is cross-user deduplication allowed, given privacy and encryption concerns?
What are the retention rules for versions and trash?

Read : write ratio     = ~5 : 1; dedup saves ~20-30%
Files stored in total  = ~100B

Throughput

Uploads:   200M / 86,400 = ~2.3K files/sec avg → ~10K/sec peak
Ingest:    200M × 2 MB = ~400 TB/day raw → ~280-320 TB after dedup
Downloads: ~5x → ~12K files/sec avg, served from CDN and edge caches
Metadata:  list/stat operations ~50K/sec peak

Blob traffic is large but simple. Metadata traffic is small per
call but latency- and consistency-sensitive.

Storage

Blobs per year: ~300 TB/day × 365 ≈ ~110 PB/year (before replication)
With erasure coding (~1.5x): ~165 PB/year; with 3x replication it would be ~330 PB
Total across years: exabyte scale
Metadata:  100B files × 1 KB = ~100 TB (plus versions and ACLs), in a sharded DB

Erasure coding instead of 3x copies saves roughly half the
disks at similar durability.

Connections

Sync notifications: ~20M concurrent long-lived connections
At ~100K per node → ~200 notification nodes
Send only "something changed" pings; clients then pull the delta.
04 / High-level design

Architecture

Every box exists because of a number from Step 3.

 CLIENTS (web · mobile · desktop sync client)
     │  chunked upload / download · change notifications
 [ CDN / Edge ] ── [ API Gateway / LB ]  auth · quota · rate limit
     │
 ├─► [ Metadata Service ] ─► [ Metadata DB: sharded SQL ]   (file tree, versions, ACL)
 │         │
 │         ├─► [ Permission Service ]
 │         └─► [ Change Log / Sync Service ] ─► [ Notification Service (WebSocket) ]
 │
 ├─► [ Upload Service ] ─► [ Chunk Store API ] ─► [ Blob Storage (erasure coded) ]
 │         │                       ▲
 │         └─► [ Dedup Index: hash → chunk location ]
 │
 └─► [ Kafka ] ─► Search indexer · Virus scan · Thumbnails · Quota · GC · Analytics

Blobs go straight to the storage layer; metadata is the source of truth for what a file is

Component rationale

Upload service + chunk store
Splits files into chunks, uploads them in parallel and resumably, and stores each chunk by its content hash.
Blob storage
Immutable, content-addressed chunks stored with erasure coding across racks and regions for extreme durability at low cost.
Metadata service + DB
Holds the file tree, file-to-chunk lists, versions and ownership in a strongly consistent, sharded SQL store.
Permission service
Evaluates ACLs including inherited folder shares and link sharing, with a cache for hot checks.
Sync + change log
Every metadata change appends to an ordered per-user log; devices pull changes since their last cursor.
Notification service
Pushes a lightweight “changes available” signal over WebSocket or long poll so devices sync within seconds.
Kafka + workers
Async jobs: virus scan, thumbnails, content search indexing, quota updates and garbage collection.

End-to-end flow — "user saves a file and another device sees it"

  1. The desktop client detects a changed file, splits it into 4 MB chunks and computes a hash for each.
  2. It asks the Upload Service which chunks already exist; only missing ones are uploaded, in parallel and resumably.
  3. Chunks are written to blob storage (erasure coded) and registered in the dedup index.
  4. The client commits the version to the Metadata Service: file id, ordered chunk hashes, size, parent, with a base version for conflict checks.
  5. The commit is a single transaction; it appends an entry to the user’s change log and increments quota.
  6. The Notification Service pings the user’s other online devices: “changes since cursor N”.
  7. Each device fetches the delta from the change log, downloads only new chunks and rebuilds the file locally.
  8. Kafka workers scan for viruses, generate thumbnails and index content for search.

Storage layer

Different data, different access patterns, different stores: bytes in blob storage, structure in a relational store.

Dedup index (hash → chunk)Distributed KV (Bigtable / DynamoDB)Very large, key lookups by hash

Core tables and keys

-- Metadata DB (strongly consistent)
files(file_id PK, owner_id, parent_id, name, is_folder, current_version,
      trashed, created_at, modified_at)
file_versions(file_id, version, size, chunk_hashes[], modified_by, created_at,
              PRIMARY KEY (file_id, version))
permissions(file_id, principal_id, role, inherited_from)   -- viewer | commenter | editor | owner
changes(user_id, seq BIGINT, file_id, op, version, PRIMARY KEY (user_id, seq))

-- Chunk store (content addressed)
Key:   chunk:{sha256}     Value: bytes  (immutable)
Index: chunk_refs  sha256 → { location, ref_count }

Sharding strategy

  • Metadata — shard by owner_id (or root folder) so a user’s tree and change log stay together; shared files use a lookup index.
  • Chunks — placed by hash across storage clusters; immutability makes replication and caching simple.
  • Change log — keyed by user with a monotonically increasing sequence, the cursor for sync.
  • Hot shards — very large shared folders are split and permissions cached to avoid single-shard load.
06 / Deep dives

Deep dive on 3 critical components

For each: the problem, the naive solution, why it fails, and the real solution. Volunteer these before the interviewer asks.

01 Chunked upload & dedup — big files, bad networks, no waste

The problem: Users upload multi-gigabyte files over flaky connections, and edit large files repeatedly, yet we must not re-send or re-store data we already have.

Naive solution — upload the whole file in one request
PUT /files/report.mp4   (5 GB body)  →  store as one object

Why it fails: A dropped connection at 99% restarts everything. One tiny edit re-uploads the entire file. Identical files from many users are stored again and again, wasting petabytes.

Real solution — content-addressed chunks, resumable and parallel
1. Client splits the file into chunks (~4 MB, or content-defined
   chunking so inserts do not shift every boundary) and hashes each
   with SHA-256.

2. Client sends the hash list. Server answers which chunks are missing
   (checks the dedup index). Only missing chunks are uploaded.

3. Chunks upload in parallel with retries per chunk. State is tracked
   by an upload session id, so after a failure the client asks which
   chunks arrived and continues. Nothing restarts.

4. Chunks are immutable and keyed by hash. The file version is just an
   ordered list of chunk hashes in the metadata DB.

5. Edits: only changed chunks have new hashes, so only they upload
   (delta sync). Old versions share unchanged chunks for free.

6. Dedup: same hash = same chunk, stored once with a ref_count.
   Within one user it is safe. Across users, use it carefully
   (encryption keys, privacy attacks that probe "does this exist").

7. Integrity: verify each chunk's hash on receipt and again at rest;
   the commit step fails if any chunk is missing.

Small files (most of them) are a single chunk, so the extra
protocol cost is negligible.
Make the unit of storage a small immutable, content-addressed chunk. Resume, parallelism, delta sync, versioning and dedup all fall out of that one decision.
02 Metadata & sync — every device converges to the same truth

The problem: Millions of devices edit, rename and move files, sometimes offline. Each must see a consistent folder tree and discover changes within seconds, without polling the server constantly.

Naive solution — clients poll and compare whole folders
every 5s: GET /files?folder=root  → diff against local state

Why it fails: 20M devices polling every few seconds is enormous load, mostly returning “nothing changed.” Full listing diffs are slow for large drives, and last-write-wins silently destroys offline edits.

Real solution — ordered change log, cursors, push-then-pull, versioned commits
1. Every metadata change (create, rename, move, delete, new version)
   appends a row to the user's change log with an increasing seq.

2. Each device remembers a cursor (last seq seen). It asks:
     GET /changes?since=cursor  → delta only, then moves its cursor.

3. Push-then-pull: on commit, the Notification Service sends a tiny
   "changes available" signal (WebSocket / long poll). Clients then
   pull the delta. Pings carry no data and may be dropped safely, since
   the next pull catches up. Devices also pull on reconnect.

4. Optimistic concurrency: a commit says "based on version N".
     UPDATE files SET current_version = N+1
     WHERE file_id=? AND current_version = N
   0 rows → someone else changed it first → conflict.

5. Conflict handling: do not drop data. Keep both: save the loser as
   "file (conflicted copy)" or merge for structured docs. Folder
   operations are transactions so moves and renames stay atomic.

6. Move or rename is a metadata-only change (parent pointer), never a
   copy of bytes.

7. Permissions are checked on every metadata and download call, with
   inherited shares resolved through the parent chain and cached.

Metadata needs strong consistency; blob bytes do not,
because chunks are immutable and referenced by hash.
Sync is a log-and-cursor problem, not a polling problem. Keep an ordered change history, push tiny hints, and never resolve conflicts by silently overwriting someone’s work.
03 Blob storage — 11 nines of durability without 3x cost

The problem: Store exabytes of user data so that it is essentially never lost, stays cheap, and remains fast to read when needed.

Naive solution — copy every file to 3 servers forever
replicate(file, 3 servers); keep all versions on the same fast disks

Why it fails: Three full copies triple the disk bill at exabyte scale. Same-rack copies die together in a power or switch failure. Most files are never opened again, yet they sit on the most expensive media.

Real solution — erasure coding, failure-domain spreading, tiering, safe GC
1. Erasure coding: split a chunk into k data + m parity fragments
   (e.g. 10+4). Any k fragments rebuild it. Overhead ~1.4x instead of
   3x, with durability as good or better.

2. Spread fragments across failure domains: different disks, racks,
   and for important data, different datacenters or regions.

3. Hot chunks (just uploaded, popular) are also replicated or cached
   at edge/CDN for fast reads. Fresh uploads can use simple
   replication first, then convert to erasure coding in the background.

4. Tiering: recently used on SSD/HDD, cold data to cheaper, denser
   storage after N days. Retrieval stays automatic and transparent.

5. Repair: continuous scrubbing verifies checksums; on disk or node
   loss, background jobs rebuild missing fragments at once.

6. Garbage collection: chunks are shared (dedup, versions), so track
   ref_count or run mark-and-sweep from metadata. Delete only
   when no version references the chunk, after a safety delay.

7. Encryption: per-chunk or per-file keys, encrypted at rest, with
   keys in a separate key management service.

8. Trash: delete = metadata flag first; real purge after retention
   (e.g. 30 days), then GC reclaims chunks.

Durability math: independent failures plus fast repair is
what produces 11 nines, not just the number of copies.
Durability comes from spreading data across failure domains and repairing fast. Erasure coding gives the same safety at roughly half the cost of replication.
07 / Tradeoffs & alternatives

What we did NOT choose and why

Rejected alternatives

AlternativeWhy rejected
Whole-file uploadNo resume, no delta, wasteful on edits and failures.
Polling for syncHuge idle load; push-then-pull with a change log is far cheaper.
3x replication for all dataTriple the disk cost; erasure coding is the better tradeoff.
Last-write-wins on conflictsSilently loses user edits; keep both copies instead.
Store files and metadata in one DBBlobs bloat the DB; different scaling and consistency needs.
Global cross-user dedup everywherePrivacy leaks and key-management complexity; limit scope.

What breaks at 10× scale and how we fix it

Problem — Hot file or folder

A viral shared file or a huge shared folder gets millions of reads and permission checks.

Fix

Serve bytes through CDN and edge caches, cache permission decisions, replicate hot metadata shards, and rate limit link access.

Problem — Metadata shard overload

One shard owns very large accounts, or a bulk operation touches millions of files.

Fix

Split shards by folder subtree, batch and throttle bulk operations as background jobs, and use pagination with cursors for listings.

Problem — Silent data corruption or disk loss

Bit rot or failed disks reduce redundancy without anyone noticing.

Fix

End-to-end checksums, periodic scrubbing, automatic fragment repair, and monitoring that alerts when redundancy drops below target.

Problem — Regional outage

An entire region loses power or network access.

Fix

Cross-region replication of metadata and cross-region erasure coding for blobs, active-active stateless services, and clients that retry against another region.

08 / Summary

Cheat sheet

What to remember before walking into the room.

Key numbers

100M DAU · 200M uploads/day · ~400 TB/day · ~2.3K uploads/sec (10K peak) · ~20M sync connections

Key datastores

Blob store (erasure coded) · Spanner / sharded SQL (metadata) · KV (dedup index) · Redis · Kafka

Upload strategy

4 MB content-hashed chunks, resumable parallel upload, upload only missing chunks, delta sync.

Sync strategy

Per-user change log with cursors, push-then-pull notifications, optimistic version commits, keep-both conflicts.

File model

A file version = ordered list of chunk hashes. Rename and move touch metadata only.

Key tradeoffs

Strong consistency for metadata vs. cheap eventual blobs. Dedup savings vs. privacy. Replication vs. erasure coding.

Hardest part

Keeping millions of devices consistent with a huge, durable store at low cost.

Patterns

Content-addressable storage · change log and cursor · optimistic concurrency · erasure coding · ref-counted GC

Sharding keys

Metadata → owner_id · Chunks → hash · Change log → user_id · Kafka → file_id
