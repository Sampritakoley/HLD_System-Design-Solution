01 / Understanding the problem

What is this system, really?

An online judge lets users read coding problems, write solutions in many languages, run them against hidden test cases, and get a verdict in seconds. Contests add a time limit and a live ranking.

The core tension: we run untrusted code from strangers, at scale, in bursts. Everything about the design is shaped by safety first, then by throughput during contest spikes.

Core features in scope

Problems

Browse, search and filter problems by tag and difficulty; read statements and examples.

Run & submit

Run against sample tests, or submit against hidden tests and receive a verdict.

Contests

Timed events with a live leaderboard, penalties and ratings.

Profiles

Submission history, solved count, streaks, discussion and editorials.

What makes this hard at scale

  • Untrusted code. Users can submit infinite loops, fork bombs, file or network abuse.
  • Bursty load. Contest start and end create sharp spikes in submissions and page views.
  • Fair, reproducible judging. The same code must get the same verdict with consistent time and memory limits.
  • Heavy compute. Each submission can use several seconds of CPU across many test cases.
  • Live ranking. Leaderboards must update within seconds for tens of thousands of viewers.
02 / Requirements

Functional vs. non-functional requirements

Non-functional requirements drive the architecture, so they come first.

Functional

  • List and view problems with tags and difficulty
  • Code editor with multiple languages
  • Run on samples, submit on hidden tests
  • Verdicts: Accepted, Wrong Answer, TLE, MLE, RE, CE
  • Submission history and stats
  • Contests with live leaderboard and penalties
  • Discussion, editorials, bookmarks
  • Admin tools to add problems and test cases

Non-functional

  • 1M DAU, 5M submissions/day, ~3K/s contest peak
  • Verdict in < 5 s for typical submissions (p95)
  • Strong isolation of untrusted code
  • 99.9% availability; contests must not break
  • No lost submissions (durable)
  • Deterministic, fair resource limits
  • Leaderboard lag < 5 seconds
  • Scales workers horizontally on demand

Clarifying questions

Is this practice only, or do we also host live contests with rankings?
Which languages are supported, and are the time limits scaled per language?
Do we need special judges (custom checkers) or only exact-output matching?
What happens on a flaky TLE: re-run, or accept the verdict?
Do we need plagiarism detection and anti-cheating in scope?

Back-of-envelope math

Order-of-magnitude accuracy, with every assumption stated.

~60/sAvg submissions (3K/s peak)

Assumptions

DAU                    = 1M; ~5 submissions per active user
Submissions per day    = 5M (avg ~60/sec)
Contest peak           = 100K users, ~3K submissions/sec at spikes
Judge time per run     = ~3 seconds (compile + run on tests)
Source code size       = ~5 KB
Problems               = ~3,000, each with ~50 MB of test data

Compute

Concurrent sandboxes at peak = 3K/sec × 3 s = ~9K at once
Per 16-core worker running ~8 sandboxes → ~1,100+ workers at peak
Average load (60/sec × 3 s)  = ~180 sandboxes → ~25 workers

Peak is ~50x average. Autoscale workers from a queue-depth signal
and pre-scale before scheduled contests.

Storage

Submissions: 5M/day × 5 KB = 25 GB/day ≈ ~9 TB/year (plus verdict metadata)
Test cases:  3,000 × 50 MB = ~150 GB in object storage, cached on workers
Problems and users: small, relational
Leaderboard: 100K users in a Redis sorted set = a few MB

Bandwidth

Problem pages are mostly static → CDN. Submissions are tiny (5 KB).
The constraint is CPU for judging and isolation, not bandwidth or storage.
04 / High-level design

Architecture

Every box exists because of a number from Step 3.

 BROWSER / APP
     │
 [ CDN ]  problem pages, static assets
     │
 [ API Gateway / LB ]  auth · rate limit
     │
 ├─► [ Problem Service ] ─► [ Problems DB ] ─► [ Redis cache ]
 ├─► [ Submission Service ] ─► [ Submissions DB ]
 │         │ enqueue
 │         ▼
 │   [ Queue: Kafka / SQS ]  (normal lane · contest lane)
 │         │
 │         ▼
 │   [ Judge Workers ] (autoscaled pool)
 │         │   sandbox per run (container + gVisor / Firecracker)
 │         ├─► [ Test case cache ] ◄─ [ Object store S3 ]
 │         └─► result ─► [ Results topic ]
 │
 ├─► [ Contest Service ] ─► [ Redis sorted set: leaderboard ]
 └─► [ Notification / WebSocket ]  verdict push to the user

Judging is asynchronous: the submit API returns an id immediately, the verdict arrives later

Component rationale

Submission service
Validates the request, stores the code durably, enqueues a job and returns a submission id fast. Never runs code itself.
Queue (Kafka / SQS)
Buffers bursts, decouples submit rate from judge capacity, and lets workers pull at their own pace. Separate lanes for contests.
Judge workers
Pull jobs, compile, run in a sandbox with hard limits, compare outputs, and publish the verdict. Stateless, so they autoscale.
Sandbox runtime
Isolates untrusted code with containers hardened by gVisor or Firecracker microVMs, seccomp and cgroups.
Test case store + cache
Master copies in S3; workers keep hot problems on local disk so each run does not download 50 MB.
Contest service + Redis
Updates scores on each accepted submission and serves the live leaderboard from a sorted set.
WebSocket / polling
Pushes verdicts to the browser; polling by submission id is the simple fallback.

End-to-end flow — "user submits a solution"

  1. User clicks Submit; the API checks auth and rate limits, stores the code and creates a submission as QUEUED.
  2. The job (submission id, language, problem id) is enqueued; the API immediately returns the id.
  3. A free worker pulls the job, fetches the source and loads test cases from its local cache (or S3 on a miss).
  4. The worker compiles in a sandbox; a compile error ends the run with COMPILE_ERROR.
  5. It runs each test with time, memory, process and output limits, then compares the output (or runs a custom checker).
  6. It stops at the first failure, or finishes all tests, and publishes the verdict (ACCEPTED, WRONG_ANSWER, TLE…).
  7. The Submission Service stores the result, pushes it to the user over WebSocket, and updates the contest leaderboard if applicable.

Core tables and keys

-- PostgreSQL
CREATE TABLE submissions (
  submission_id  UUID PRIMARY KEY,
  user_id        BIGINT NOT NULL,
  problem_id     INT NOT NULL,
  contest_id     INT,
  language       TEXT,
  code_ref       TEXT,           -- S3 key or inline for small code
  status         TEXT NOT NULL,  -- QUEUED | RUNNING | ACCEPTED | WRONG_ANSWER | TLE | MLE | RE | CE
  runtime_ms     INT, memory_kb INT,
  failed_test    INT,
  created_at     TIMESTAMP DEFAULT now()
);
CREATE INDEX ON submissions (user_id, created_at DESC);
CREATE INDEX ON submissions (problem_id, status);

-- Redis
Key: contest:{id}:lb          Value: ZSET  member=user_id  score=encoded(solved, penalty)
Key: ratelimit:{user}         Value: counter, TTL 60s
Key: problem:{id}             Value: cached problem JSON, TTL 10m

Sharding strategy

  • Submissions — shard by user_id so “my submissions” is one shard; archive old rows to cold storage.
  • Problems — small, replicate and cache; no sharding needed.
  • Queue — partition by problem or contest lane; separate topics for contest and practice.
  • Leaderboards — one sorted set per contest; shard by contest id.
06 / Deep dives

Deep dive on 3 critical components

For each: the problem, the naive solution, why it fails, and the real solution. Volunteer these before the interviewer asks.

01 Sandboxed execution — run hostile code safely and fairly

The problem: We execute arbitrary code from the internet. It may loop forever, eat memory, fork-bomb, read secrets, or attack our network.

Naive solution — run the code directly on the server
subprocess.run(["python", "solution.py"])   # same host, same user

Why it fails: Code can read files, kill processes, open sockets, or exhaust CPU and RAM. One malicious submission can take down the worker or leak data from other users.

Real solution — layered isolation with hard resource limits
1. Run each submission in a fresh sandbox:
   container hardened with gVisor (user-space kernel) or a Firecracker
   microVM for stronger isolation. Destroyed after the run.

2. Limits via cgroups: CPU time, wall time, memory, number of
   processes (stops fork bombs), open files, output size.

3. Syscall filtering with seccomp: allow only what a program needs.
   No network namespace, read-only filesystem, tiny writable tmpfs.

4. Run as an unprivileged user with no capabilities; no access to
   host mounts or secrets.

5. Time and memory: measure CPU time (not just wall time) and kill on
   exceed → TLE / MLE. Use a language multiplier for slower runtimes.

6. Fairness: pin to dedicated cores, avoid noisy neighbours, and
   re-run borderline TLEs on a quiet worker before final verdict.

7. Output: compare against expected output (ignore trailing whitespace),
   or use a custom checker program for problems with many valid answers.

Warm sandbox pools (pre-created) cut startup from ~1 s to ~100 ms.
Assume every submission is hostile. Isolation (kernel boundary), hard cgroup limits and no network are non-negotiable; speed tricks come after safety.
02 Submission queue & scaling — survive the contest spike

The problem: Judging takes seconds of CPU. At contest start, thousands of submissions per second arrive, far above the steady-state judging capacity.

Naive solution — judge synchronously inside the request
POST /submit → compile → run all tests → respond with verdict

Why it fails: HTTP requests hang for seconds, connections pile up and time out, and a traffic spike exhausts web servers. A worker crash loses the submission entirely.

Real solution — asynchronous queue with autoscaled workers
1. Persist the submission first (status QUEUED), then enqueue the job.
   The API returns the id in milliseconds. Nothing is lost if a
   worker dies later.

2. Workers pull from the queue; capacity is decoupled from arrival
   rate. The queue absorbs the burst; latency rises a little, the
   system never falls over.

3. Visibility timeout / ack: a job taken by a worker that crashes
   becomes visible again and is retried. Verdict writes are idempotent
   on submission_id to avoid double-processing.

4. Priority lanes: contest submissions get a reserved, higher-priority
   queue and dedicated workers so practice traffic cannot starve them.

5. Autoscale on queue depth and oldest-message age; pre-scale before
   scheduled contests (we know the start time). Keep a warm pool.

6. Per-user rate limit (e.g. 1 submission per few seconds) and dedupe
   identical code to prevent abuse and wasted compute.

7. Deliver results by WebSocket push; clients fall back to polling
   GET /submissions/{id}.

Cache test cases on worker disks (LRU) so most runs avoid
downloading from S3.
The tradeoff is explicit: during a spike we accept longer queue wait (seconds more) to protect correctness and availability. Show “Judging…” status instead of failing.
03 Contest leaderboard — live ranking for 100K users

The problem: Tens of thousands of participants watch rankings that change with every accepted submission, ordered by problems solved and then penalty time.

Naive solution — compute rank with SQL on every page load
SELECT user_id, COUNT(*) solved, SUM(penalty) FROM results
GROUP BY user_id ORDER BY solved DESC, SUM(penalty) ASC

Why it fails: A group-by and sort over a hot table, executed by 100K users refreshing every few seconds, kills the database. Finding one user’s rank is also an expensive scan.

Real solution — Redis sorted set with an encoded score, cached pages
1. Encode score so higher is better in one number:
     score = solved × 10^9 − penalty_seconds
   (more solved wins; lower penalty breaks ties)

2. On each accepted verdict: ZADD contest:{id}:lb score user_id
   O(log N). Rank lookup: ZREVRANK; top page: ZREVRANGE 0 49.

3. Penalty rules (wrong attempts, time since start) are computed by the
   Contest Service when it updates the score, not at read time.

4. Serve the top pages from an in-memory snapshot refreshed every
   1-2 seconds and cached at the CDN. Users see ≤ 2 s old data,
   and the DB sees almost no read traffic.

5. A user’s own rank is a single ZREVRANK call, shown separately.

6. Freeze the scoreboard in the last N minutes if the rules say so.

7. Source of truth is the submissions DB. If Redis is lost, rebuild
   the sorted set by replaying accepted submissions for that contest.

100K members in a sorted set is only a few MB, comfortably in memory.
Precompute the ranking at write time and serve reads from memory and cache. Ranking is a read-heavy, derived view; the DB remains the source of truth.
07 / Tradeoffs & alternatives

What we did NOT choose and why

Rejected alternatives

AlternativeWhy rejected
Run code in the web serverUnsafe and unscalable; one bad submission harms everyone.
Plain Docker with default settingsShares the host kernel; add gVisor, seccomp and no network, or use microVMs.
Synchronous judgingSpikes exhaust connections; no retry safety.
Always-on worker fleet for peakPeak is ~50× average; pay only for what is needed, pre-scale for contests.
SQL aggregation for rankingToo slow under refresh load; sorted sets give O(log N) updates.
Download test cases per runWasteful; cache on workers.

What breaks at 10× scale and how we fix it

Problem — Contest-start spike

Hundreds of thousands open the same problems and submit at the same second.

Fix

Serve problem statements from CDN (published at start time), pre-warm caches and worker pools, rate-limit submissions per user, and keep the contest queue separate.

Problem — Worker crash mid-judge

A sandbox or node dies while running a submission.

Fix

Visibility timeout returns the job to the queue, idempotent result writes, a cap on retries, and a final SYSTEM_ERROR state with automatic re-judge rather than blaming the user.

Problem — Sandbox escape or abuse

A malicious program tries to escape, mine crypto or reach internal services.

Fix

Defense in depth: microVM or gVisor, seccomp, no network, short lifetimes, runtime monitoring, and workers in an isolated network segment with no credentials.

Problem — Cheating and unfair verdicts

Plagiarism in contests, and TLE results that differ run to run.

Fix

Code similarity detection (token fingerprints) after contests, re-run borderline TLEs on quiet hardware, dedicated cores for timing, and rejudge tools for admins.

08 / Summary

Cheat sheet

What to remember before walking into the room.

Key numbers

1M DAU · 5M submissions/day · ~3K/s contest peak · ~3 s per judge · ~9K concurrent sandboxes at peak

Key datastores

PostgreSQL (problems, submissions) · S3 (test cases) · Redis (leaderboard, cache) · Kafka / SQS (queue)

Execution strategy

Fresh sandbox per run: gVisor or Firecracker, cgroups, seccomp, no network, CPU-time limits.

Queue strategy

Persist then enqueue, async verdicts, priority contest lane, visibility timeout retries, autoscale on queue depth.

Submission state machine

QUEUED → RUNNING → ACCEPTED / WRONG_ANSWER / TLE / MLE / RE / CE (or SYSTEM_ERROR → rejudge).

Key tradeoffs

Safety vs. startup speed. Queue wait vs. fleet cost. Leaderboard freshness vs. read load.

Hardest part

Running untrusted code safely and fairly while absorbing a 50× burst of judging work.

Patterns

Async job queue · worker pool autoscaling · sandboxing · idempotent writes · write-time ranking · CDN for statics

Sharding keys

Submissions → user_id · Queue → lane / problem · Leaderboard → contest_id · Cache → problem_id

Interview time map

0–3: clarify · 3–7: requirements + estimation · 7–16: HLD + flow · 16–23: data model · 23–29: deep dives · 29–30: tradeoffs
