01 / Understanding the problem

What is this system, really?

BookMyShow is an online ticketing platform. Users discover movies and events in their city, pick a theatre and showtime, choose exact seats on a seat map, pay, and receive an e-ticket. Think of it as a giant distributed inventory system where every item (a seat) can be sold exactly once.

The core challenge: unlike Twitter, where losing a few updates is tolerable, here correctness is the product. Two people paying for the same seat is a support nightmare and a trust killer. Yet traffic is wildly spiky — a big release opens bookings and millions arrive in the same minute, all fighting for the same few hundred good seats.

Core features in scope

Browse — discover shows

City-based listing of movies, theatres and showtimes, with search and filters (language, format, genre). Extremely read-heavy and cacheable.

Seat selection — the live map

Shows real-time seat availability for one show. Must reflect seats being held by others without flickering or lying.

Booking — the hard part

Temporarily hold selected seats, take payment, then confirm. Zero double-bookings, ever.

Payments & tickets

Integrate with payment gateways, handle failures and timeouts, issue QR e-tickets, support cancellations and refunds.

What makes this hard at scale

  • Contention on a tiny resource. A show has ~200 seats; a blockbuster's first-day evening show can have 50,000 people targeting them. Classic hot-row problem.
  • Double-booking is unacceptable. Seat state needs strong consistency, unlike a social feed.
  • Holds must expire. A user who abandons checkout must not block seats forever, yet must have enough time to pay.
  • Flash-sale spikes. Booking opens for a mega release at a known time; traffic jumps 50× in seconds.
  • Payments are unreliable. Gateway timeouts, duplicate callbacks, money debited but booking failed — all must be handled.
02 / Requirements

Functional vs. non-functional requirements

Non-functional requirements are what actually drive architecture decisions — they're listed first for a reason.

Functional

  • Browse movies/events by city
  • Search by title, genre, language
  • View theatres and showtimes
  • View live seat map per show
  • Select and hold seats
  • Pay and receive e-ticket
  • Cancel and refund
  • Notifications (SMS/email/push)

Non-functional

  • 10M DAU, 3M tickets booked/day
  • Read:Write ratio = ~100:1
  • Browse < 200ms (p99)
  • Seat map load < 300ms
  • 99.99% availability
  • Strong consistency for seats
  • Eventual consistency OK for listings
  • Survive 50× spikes on release day

Clarifying questions

Is seat selection free-choice (seat map) or auto-assigned? Free-choice makes contention far worse.
How long should a seat be held during checkout — 5 or 10 minutes?
Do we integrate with theatre-owned systems, or do theatres use our platform directly?
Do we need a waiting room / queue for high-demand releases?
Which payment methods — cards, UPI, wallets? Any refund SLA?
Is the system single-country, or multi-region with different currencies and taxes?
Are events (concerts, sports) in scope alongside movies, including general-admission tickets?
Do we support dynamic pricing or coupons that affect the final amount?

DAU                     = 10M users
Bookings per day        = 3M bookings (~2.5 seats each)
Browse / seat-map reads = 500M reads/day
Seat-hold attempts      = 10M/day (only ~30% convert to a booking)
Theatres / screens      = 5,000 theatres, ~20,000 screens
Shows per day           = ~100K shows × ~200 seats = 20M seat rows/day

QPS

Read QPS:
  500M / 86,400               = ~5,800/sec
  Peak (5× average)           = ~30,000/sec

Seat-hold (write) QPS:
  10M / 86,400                = ~115/sec
  Flash-sale peak (50×)       = ~6,000/sec

Average load is tiny. The design is about surviving the spike
and staying correct under contention, not raw throughput.

Storage

Bookings per day:
  3M × 1 KB                   = ~3 GB/day

Seat inventory per day:
  20M seat rows × 50 bytes    = ~1 GB/day

5-year total:
  Bookings: 3GB × 365 × 5    = ~5.5 TB
  Inventory: 1GB × 365 × 5   = ~1.8 TB
  Total (with posters, tickets) = ~10-15 TB

Bandwidth

Seat map payload: 200 seats × ~20B         = ~4 KB
Listing payload (with posters via CDN)     = ~50 KB
30K reads/s × 50 KB                        = 1.5 GB/sec
CDN + cache absorb ~95%                    → ~75 MB/sec reaches origin

Component rationale

CDN
Posters, trailers and static assets never touch origin. Movie metadata pages are also edge-cached for a short TTL, absorbing most of the 30K reads/sec.
API Gateway / Load Balancer
Auth, rate limiting, routing and SSL termination. Also the place to enforce per-user limits on seat-hold attempts to blunt bots and scalpers.
Waiting Room
For mega releases, admits users into the booking flow at a controlled rate instead of letting 1M people hit seat selection at once. Protects the inventory layer by design.
Catalog & Search Service
Serves movies, theatres, showtimes. Data changes rarely, so it's heavily cached. Elasticsearch powers search, filters and autocomplete by city, language and genre.
Show & Inventory Service
Owns seat state for every show. Serves the seat map from Redis and is the single authority for holding and releasing seats. Correctness lives here.
Booking Service
Orchestrates the booking state machine: create booking → hold seats → await payment → confirm or expire. Writes to Postgres in transactions.
Payment Service
Abstracts payment gateways, enforces idempotency keys, processes webhooks, and reconciles with gateway reports. Isolated so a gateway outage can't corrupt inventory.
Redis (seat locks + cache)
Atomic SET NX EX gives fast, auto-expiring seat holds. Also caches seat maps and hot show data for sub-millisecond reads.
PostgreSQL (source of truth)
Bookings, payments and final seat status need ACID. Write volume is modest (~35 bookings/sec average), so a relational DB with row-level locking is the right, simplest choice.
Kafka (message queue)
After a booking is confirmed, ticket generation, SMS/email, analytics and search updates all consume events independently. Keeps the critical booking path short.

End-to-end data flow — "user books 2 seats"

  1. User opens a show. Client calls GET /shows/{id}/seats; seat map is served from Redis/cache.
  2. User selects seats A5, A6 and hits continue. App sends POST /bookings with seat IDs and an idempotency key.
  3. Booking Service asks Inventory to hold both seats atomically in Redis with a 10-minute TTL. If any seat is taken, the whole hold fails and the user is told immediately.
  4. On success, Booking row is created with status PENDING in Postgres; user is redirected to payment.
  5. Payment Service creates a gateway order and the user pays.
  6. Gateway sends a webhook. Payment Service verifies the signature, dedupes by payment ID, and notifies Booking Service.
  7. Booking Service opens one DB transaction: marks seats BOOKED, booking CONFIRMED, and releases the Redis locks.
  8. A BookingConfirmed event goes to Kafka; consumers generate the QR ticket and send SMS/email/push.
  9. If payment fails or the TTL expires, seats auto-release and become available to others.

Different data, different access patterns, different databases — not one engine forced to do everything.

Core tables (PostgreSQL)

CREATE TABLE shows (
  show_id     BIGINT PRIMARY KEY,
  movie_id    BIGINT NOT NULL,
  screen_id   BIGINT NOT NULL,
  start_time  TIMESTAMPTZ NOT NULL,
  base_price  NUMERIC(10,2)
);
CREATE INDEX idx_shows_movie_time ON shows(movie_id, start_time);

CREATE TABLE show_seats (
  show_id     BIGINT,
  seat_id     INT,
  status      VARCHAR(10) DEFAULT 'AVAILABLE',  -- AVAILABLE | BOOKED
  booking_id  BIGINT NULL,
  version     INT DEFAULT 0,                    -- optimistic lock
  PRIMARY KEY (show_id, seat_id)
);

CREATE TABLE bookings (
  booking_id      BIGINT PRIMARY KEY,
  user_id         UUID NOT NULL,
  show_id         BIGINT NOT NULL,
  status          VARCHAR(12),   -- PENDING | CONFIRMED | EXPIRED | CANCELLED
  amount          NUMERIC(10,2),
  idempotency_key VARCHAR(64) UNIQUE,
  created_at      TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_bookings_user ON bookings(user_id, created_at DESC);

Redis seat-lock structure

Key:   lock:{show_id}:{seat_id}
Value: booking_id (or user_id)
TTL:   600 seconds   ← auto-release if user abandons checkout

SET lock:9001:A5 booking_42 NX EX 600     → 1 = acquired, nil = taken

Seat map = DB status (BOOKED) overlaid with live Redis locks (HELD).
Cached per show, invalidated on every lock change or expiry.

Sharding strategy

  • Show & seat data — shard by show_id (or city + show_id); all seats of one show live together so a multi-seat booking stays on a single shard and a single transaction.
  • Bookings — shard by user_id for "my bookings"; booking writes reference show_id, so keep seat confirmation on the show's shard.
  • Redis locks — partition by show_id with consistent hashing so one show's locks are always on the same node.
  • Geo partitioning — users browse one city at a time, so city is a natural boundary for catalog and show data. Also keeps latency low.
06 / Deep dives

Deep dive on 3 critical components

For each: the problem, the naive solution, why it fails, and the real solution used at scale. Volunteer these problems before the interviewer asks — it signals senior-level thinking.

01 Seat locking — preventing double booking

The problem: Thousands of users try to grab seat A5 at the same instant. Exactly one must win, the rest must be told immediately, and abandoned holds must expire on their own.

Naive solution — check then update
seat = SELECT status FROM show_seats WHERE seat_id = 'A5';
if (seat.status == 'AVAILABLE') {
    UPDATE show_seats SET status = 'BOOKED' WHERE seat_id = 'A5';
}

Why it fails: Classic race condition. Two requests both read AVAILABLE before either writes, and both succeed. Holding DB row locks across the whole payment flow isn't an option either — it would pin connections for up to 10 minutes per user.

Real solution — two layers: Redis hold + DB conditional update
Layer 1 — Temporary hold (fast, auto-expiring):
  For each seat: SET lock:{show}:{seat} {booking} NX EX 600
  Use a Lua script so all seats in the request are acquired
  atomically — if any fails, roll back the ones already taken.

Layer 2 — Final confirmation (durable, correct):
  After payment success, in one transaction:
    UPDATE show_seats
       SET status='BOOKED', booking_id=:b, version=version+1
     WHERE show_id=:s AND seat_id IN (:seats)
       AND status='AVAILABLE';
    -- rows updated must equal seats requested, else ROLLBACK + refund

Seat state machine:
  AVAILABLE ──hold──► HELD ──payment ok──► BOOKED
                        │
                        └─ TTL expiry / payment fail ──► AVAILABLE

Redis is the fast gate that stops 99.9% of contention.
Postgres conditional UPDATE is the safety net if Redis loses a lock.
The key insight: never trust a single layer. Redis gives speed and natural expiry; the database's conditional update guarantees that even a lock bug or failover can never produce two CONFIRMED bookings for one seat.
02 Flash-sale traffic — the virtual waiting room

The problem: A mega-release opens bookings at 10:00 AM. By 10:00:05, a million users are hitting the seat map and hold APIs for the same few shows. The inventory layer would collapse.

Naive solution — just autoscale everything

Why it fails: Autoscaling takes minutes; the spike lasts seconds. Even with infinite servers, contention on the same hot seat rows and Redis keys doesn't shrink — more servers just means more losers hammering the same keys, plus thundering-herd retries from frustrated users.

Real solution — shed load at the edge, admit gradually
1. Pre-warm: cache show + seat maps in Redis before sale opens.

2. Waiting room (for flagged hot releases):
   - User gets a queue token (position in a Redis sorted set)
   - Admission rate = capacity the booking flow can handle
   - Admitted users get a signed, short-lived "entry pass"
   - Seat APIs reject requests without a valid pass

3. Protect the core:
   - Per-user and per-IP rate limits, bot detection/CAPTCHA
   - Seat map served from cache (1–2s TTL) not from DB
   - Circuit breakers + graceful "try again" on overload

4. Read/write separation:
   - Browsing and seat-map reads: replicas + cache
   - Holds and bookings: isolated service and connection pool

Fairness matters: queue by arrival time, cap seats per user,
so scalpers with 10,000 sessions can't grab the inventory.
This is a product decision as much as an engineering one: a short, honest queue ("you're #4,200, ~3 min") is far better than a site that crashes and leaves everyone with errors.
03 Payments — idempotency, timeouts and reconciliation

The problem: Payment is an external, unreliable system. User pays but the webhook is delayed. The app retries and double-charges. The hold expires while the payment is in flight. Money and seats must always end up consistent.

Naive solution — synchronous call, trust the response
charge = gateway.charge(amount);
if (charge.success) { confirmSeats(); }

Why it fails: A network timeout leaves you not knowing whether the charge happened. Retrying may double-charge; not retrying may lose a paid booking. Browser-side redirects can also fail to return, so the client's word can't be trusted.

Real solution — idempotent, event-driven state machine
Booking:  PENDING ─► PAYMENT_INITIATED ─► CONFIRMED
                   │                   │
                   └─► EXPIRED         └─► FAILED ─► REFUND

1. Idempotency key on every booking/payment request
   (UNIQUE constraint) → retries return the same result.

2. Source of truth = gateway webhook, not the browser redirect.
   Verify signature, dedupe by payment_id, process once.

3. Hold TTL extension: when payment starts, extend the lock
   (e.g. +5 min) so a slow-but-successful payment isn't orphaned.

4. Late success: payment succeeds but seats already released
   → try to re-acquire the same seats; if taken, auto-refund.

5. Reconciliation job: periodically compare our PENDING
   bookings with gateway status API and settle mismatches.

6. Outbox pattern: confirm booking + write event in the
   same DB transaction; a relay publishes to Kafka reliably.

Never call a third-party gateway inside a DB transaction.
Commit state first, then act, then reconcile.
07 / Tradeoffs & alternatives

What we did NOT choose and why

Rejected alternatives

AlternativeWhy rejected
Pessimistic DB locks for the whole checkoutHolds row locks and connections for minutes per user. Won't survive a spike. Redis TTL holds are far cheaper.
Redis as the only source of truthVolatile; a failover can lose locks or bookings. Money-related state needs durable ACID storage.
Cassandra/NoSQL for bookingsWrite volume is low (~35/sec avg). We need multi-row transactions and strong consistency, which relational DBs give for free.
Optimistic locking only (no holds)Users would fill payment details, then find the seat gone. Terrible UX at peak. Holds protect the experience.
Synchronous payment confirmationGateway timeouts leave state unknown. Webhooks + reconciliation are the reliable pattern.
No waiting room, only autoscalingScale-up is slower than the spike, and contention doesn't disappear with more servers.
Microservice per tiny functionKeep seat hold, booking state and confirmation tightly coordinated; too many hops add latency and failure modes on the critical path.

What breaks at 10× scale and how we fix it

Problem — Hot shows overwhelm a single shard

One blockbuster show gets most of the traffic, so the shard holding it becomes a hotspot even though average load is low.

Fix

Dedicated shards/Redis nodes for flagged hot shows, per-show request queues, and cached seat maps with very short TTLs to absorb reads.

Problem — Redis failover loses active locks

A primary crashes and a replica without the latest writes is promoted; some held seats appear free again.

Fix

The DB conditional update remains the final arbiter, so no double-booking can be confirmed. Users who lose a seat get an instant refund path and a clear message.

Problem — Expiry storms

Thousands of holds created in the same second all expire together, causing a burst of seat-map invalidations and refreshes.

Fix

Add small random jitter to TTLs, push seat-state deltas over SSE/WebSocket instead of clients polling, and batch cache invalidation per show.

Problem — Multi-region consistency

Expanding to several countries means the same show can't be sold from two regions at once.

Fix

Each show has a single home region that owns its inventory. Other regions serve cached reads and route writes to the home region. Catalog data replicates globally.

08 / Summary

Cheat sheet

The ten things worth remembering before walking into the room.

Key numbers

10M DAU · 3M bookings/day · 30K peak read QPS · ~6K peak hold QPS · ~4 GB/day data · 10 min hold TTL

Key databases

PostgreSQL (bookings, seats, payments) · Redis (seat locks, cache) · Elasticsearch (search) · S3 (media, tickets)

Seat strategy

Redis SET NX EX hold, then Postgres conditional UPDATE on confirm. Two layers: speed plus correctness.

Booking state

PENDING → PAYMENT_INITIATED → CONFIRMED, with EXPIRED / FAILED / REFUND branches. Driven by webhooks.

Flash sales

Pre-warm cache, waiting room with entry pass, rate limits, bot protection, read/write isolation.

Key tradeoffs

Strong consistency on seats vs. eventual on listings. Hold time vs. seat turnover. Fairness vs. raw speed.

Hardest part

Exactly-once seat sale under extreme contention, with expiring holds and an unreliable payment gateway.

Kafka's role

Post-confirmation fan-out only: tickets, SMS/email, analytics, search updates. Never on the seat-locking critical path.

Sharding keys

Seats/shows → show_id (or city) · Bookings → user_id · Redis locks → show_id via consistent hashing.
