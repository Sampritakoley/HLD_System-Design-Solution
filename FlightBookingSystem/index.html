01 / Understanding the problem

What is this system, really?

A travel platform lets people search flights and hotels across hundreds of airlines, hotel chains and agencies, compare prices in one place, and book. Most of the inventory is not ours: we are a live aggregator sitting in front of other people’s systems.

The core tension: users want fast results and accurate prices, but every price lives in a slow, rate-limited third-party system that changes constantly.

Core features in scope

Search

Origin, destination, dates, passengers (or city, dates, guests) with filters and sorting.

Price comparison

Merge results from many providers, dedupe, rank by price, duration and quality.

Booking

Re-check price and availability, collect passenger details, pay, get confirmation.

Trips & alerts

Itineraries, cancellations, price alerts and notifications.

What makes this hard at scale

  • Provider fan-out. One search triggers dozens of slow external calls with different formats and limits.
  • Stale prices. Fares change in minutes; cached prices are fast but sometimes wrong.
  • Double selling. The last seat or room must go to exactly one buyer.
  • Search explosion. Routes × dates × passengers × cabins is an enormous space.
  • Partial failure. Providers time out constantly; the page must still load.
02 / Requirements

Functional vs. non-functional requirements

Non-functional requirements drive the architecture, so they come first.

Functional

  • Search one-way, return and multi-city flights
  • Search hotels by city, map area or name
  • Filters: price, stops, airline, rating, amenities
  • View details and fare rules
  • Book with passenger and payment details
  • Cancel, modify, get e-ticket or voucher
  • Price alerts and notifications
  • Redirect to provider (meta) or book directly

Non-functional

  • 50M DAU, ~250M searches/day, 10K/s peak
  • First results in < 2 s; complete in < 10 s
  • 99.99% availability for search
  • Never double-book a seat or room
  • Search results can be eventually consistent
  • Payments and bookings exactly-once
  • Degrade gracefully when providers fail
  • Scales horizontally; respects provider rate limits

Clarifying questions

Pure metasearch (redirect out) or do we also sell and take payment?
Which providers: airline direct APIs, GDS like Amadeus or Sabre, hotel aggregators?
How fresh must prices be on the results page versus at checkout?
Do we hold inventory ourselves, or only create bookings in provider systems?
Flights only, hotels only, or bundles with one cart?

Assumptions

Bookings per day     = 1M (avg ~12/sec, peak ~100/sec)
Providers per search = ~50 (airlines, GDS, OTAs, hotel suppliers)
Cache hit rate       = ~80-90% for popular routes
Search response      = ~50-200 KB of offers
Booking record       = ~5 KB

QPS

Searches: 50M × 5 / 86,400 = ~2.9K/sec avg → ~10K/sec peak
Fan-out without cache: 10K × 50 = ~500K provider calls/sec (impossible)
With ~80-90% cache hits:        ~50-100K calls/sec
Bookings: 1M / 86,400          = ~12/sec avg → ~100/sec peak

The fan-out multiplies load by 50. Caching and rate-limit
management matter more than raw compute.

Storage

Fare cache: ~50K popular routes × 365 days × few cabins × ~2 KB
          ≈ ~100 GB in Redis, sharded
Hotels:    ~2M properties, rates cached by property × date window
Bookings:  1M/day × 5 KB = 5 GB/day ≈ ~2 TB/year
Search logs and clicks: large, go to Kafka → data lake

Bandwidth

Responses: 10K/s × ~100 KB = ~1 GB/s peak → compress, paginate, stream
The constraint is outbound provider capacity and latency, not storage.

Architecture

 │         │                     └─► [ Fare Cache (Redis) ]

 ├─► [ Booking Service ] ─► [ Bookings DB ]

 │
 └─► [ Kafka ] ─► Alerts · Notifications · Analytics · Cache warmers

Search is a fast read path; booking is a slow, careful write path

Component rationale

Search orchestrator
Scatter-gather across providers with per-provider timeouts and circuit breakers. Returns partial results as they arrive.
Provider adapters
One adapter per supplier translates their API and rate limits into our common offer model. Isolates failures and format differences.
Fare cache (Redis)
Stores recent prices keyed by route, date, cabin and passengers with short TTLs. Cuts provider calls by 80-90%.
Ranking and dedupe
Merges the same flight offered by many sellers, then ranks by price, duration, stops and trust.
Hotel index (Elasticsearch)
Hotel content is mostly static, so geo search, filters and facets run on an index; only rates are fetched live.
Booking and payment services
Source of truth for bookings: a state machine with transactions, idempotency and compensations.
Kafka
Feeds cache warmers, price alerts, notifications and analytics off the hot path.

End-to-end flow — "user searches and books a flight"

  1. User searches DEL → LHR; Search Service creates a search_id and opens a streaming channel.
  2. Orchestrator checks the fare cache; cache hits return instantly as first results.
  3. For misses and stale entries, adapters call providers in parallel with ~3-8 s timeouts; results stream in as they arrive.
  4. Offers are normalized, deduped and ranked; fresh prices are written back to the cache.
  5. User picks an offer; Booking Service re-checks the live price and availability with the provider (PRICE_VERIFIED).
  6. Passenger details are collected; the seat is held at the supplier where supported, then payment is authorized (PAYMENT_AUTHORIZED).
  7. Supplier ticketing is called with an idempotency key; on success the booking is CONFIRMED and the payment is captured.
  8. On failure, the authorization is voided and the user is told; Kafka triggers the e-ticket and notifications.

Core tables and keys

-- PostgreSQL (bookings)
CREATE TABLE bookings (
  booking_id    UUID PRIMARY KEY,
  user_id       BIGINT NOT NULL,
  type          TEXT,          -- FLIGHT | HOTEL
  status        TEXT NOT NULL, -- INITIATED | PRICE_VERIFIED | PAYMENT_AUTHORIZED | CONFIRMED | FAILED | CANCELLED
  supplier      TEXT,
  supplier_ref  TEXT,          -- PNR or hotel confirmation code
  total_amount  NUMERIC(12,2), currency CHAR(3),
  idem_key      TEXT UNIQUE,   -- prevents duplicate bookings on retry
  created_at    TIMESTAMP DEFAULT now()
);

-- Redis
Key: fare:{origin}:{dest}:{date}:{cabin}:{pax}  Value: compressed offers   TTL 5-30 min
Key: hold:{booking_id}                           Value: supplier hold ref   TTL 10-15 min
Key: ratelimit:{provider}                        Value: token bucket

Sharding strategy

  • Fare cache — consistent hashing on the route + date key; hot routes get replicas.
  • Bookings — shard by user_id so “my trips” stays on one shard.
  • Hotel index — shard by geography (region or geohash) for fast map queries.
  • Kafka — partition by search_id or booking_id to keep order per entity.
06 / Deep dives

Deep dive on 3 critical components

For each: the problem, the naive solution, why it fails, and the real solution. Volunteer these before the interviewer asks.

01 Search fan-out — aggregate 50 slow providers into one fast page

The problem: A single search needs prices from dozens of providers, each with different latency, formats and failure rates, yet the user expects results in seconds.

Naive solution — call providers one by one and wait
for provider in providers: results += provider.search(query)   # sequential
return results

Why it fails: Latency adds up (50 × 1 s = 50 s) and one hung provider blocks everything. Results only appear when the slowest has answered.

Real solution — parallel scatter-gather with timeouts, streaming results
1. Orchestrator fires all provider calls in parallel (async I/O).

2. Each call has its own timeout and circuit breaker. A provider that
   keeps failing is skipped for a cool-off window.

3. Stream results to the client as they arrive (SSE / WebSocket):
   cache hits first, then fast providers, then stragglers.
   The UI re-sorts as the list grows.

4. Normalize each response into one offer model, then dedupe:
   same flight (carriers, times) from many sellers → one card with
   several prices, keyed by a canonical itinerary hash.

5. Per-provider token buckets respect rate limits; coalesce identical
   in-flight searches so 1,000 users on DEL→LHR trigger one call.

6. Cut off at a deadline (~8-10 s) and mark the search complete.

Hotels: fetch static content from our index, call suppliers
only for live rates by property ids returned from geo search.
Never make the user wait for the slowest provider. Stream partial results, bound every call with a timeout, and deduplicate identical requests.
02 Price caching & freshness — fast but not wrong

The problem: Live provider calls are slow and costly, but cached prices go stale and users hate clicking a $400 fare that turns into $480.

Naive solution — always live, or cache everything for hours
Option A: call every provider on every search
Option B: cache results for 24 hours

Why it fails: A overloads providers and blows latency and cost budgets. B shows stale or sold-out fares and destroys trust.

Real solution — tiered TTL cache, background refresh, verify at checkout
1. Cache key: route + date + cabin + passengers. Value: offers + fetched_at.

2. TTL by volatility: popular routes and near dates short (5 min),
   far dates and quiet routes longer (30-60 min).

3. Stale-while-revalidate: serve the cached value immediately, label
   it "price may change", and refresh in the background.

4. Cache warmers: Kafka search-volume stream pre-fetches the top
   routes and dates before users ask.

5. Learn from bookings: when a re-check at booking shows a different
   price, evict that key and record the drift per provider.

6. Always re-verify price and availability with the provider before
   taking payment. Show "price changed" and let the user accept.

The cache is for discovery. Checkout is the source of truth.
Staleness is a product tradeoff, not a bug. Be fast and slightly stale on search, and strict at the moment money moves.
03 Booking — exactly one booking, never a double sale

The problem: Booking touches our DB, a payment gateway and an external supplier. Any step can fail or time out, and two users may chase the last seat or room.

Naive solution — charge, then book, in one request
charge(card); supplier.book(); save(booking)   # no holds, no retry safety

Why it fails: If the supplier fails after the charge, the user paid with no ticket. A retry after a timeout can book twice. Two buyers can both see availability and both pay.

Real solution — hold, authorize, confirm, with a saga and idempotency
1. Re-check price, then place a supplier hold (a soft reserve) with a
   short TTL. If the supplier has no holds, rely on step 3.

2. Authorize payment first (reserve funds, do not capture).

3. Ticketing call with an idempotency key (booking_id).
   Success → capture payment → CONFIRMED.
   Failure → void authorization → FAILED, release hold.

4. Booking state machine in the DB with conditional updates:
     UPDATE bookings SET status='CONFIRMED'
     WHERE booking_id=? AND status='PAYMENT_AUTHORIZED'

5. Timeouts mean unknown state: mark PENDING_VERIFICATION and let a
   reconciliation job query the supplier by reference, then complete or
   compensate.

6. Own inventory (hotel contracts): atomic conditional decrement per
   room-type per night, in one transaction across all nights:
     UPDATE room_inventory SET available = available - 1
     WHERE room_type=? AND night BETWEEN ? AND ? AND available > 0

Authorize before ticketing: it is far easier to void an
authorization than to refund a captured payment or cancel a ticket.
Never leave money and inventory out of sync. Use holds, idempotency keys and a state machine, and treat timeouts as “unknown” that reconciliation resolves.
07 / Tradeoffs & alternatives

What we did NOT choose and why

Rejected alternatives

AlternativeWhy rejected
Sequential provider callsLatency adds up; one slow supplier blocks the page.
Live calls on every searchProvider rate limits and cost; unacceptable latency.
Long-lived price cacheStale fares erode trust and cause failed bookings.
Charge before confirming supplierRisk of paid-but-unticketed customers and costly refunds.
2PC across us, payment and supplierExternal systems cannot participate; use a saga.
Strong consistency for searchNeedless cost; results are advisory until checkout.

What breaks at 10× scale and how we fix it

Problem — Provider outage or slowdown

A major GDS goes down or starts timing out, dragging every search with it.

Fix

Per-provider timeouts and circuit breakers, bulkheads so one provider cannot exhaust threads, and cached or alternate-source results as fallback.

Problem — Traffic spikes on a route

A sale or a news event sends thousands of identical searches to one route in a minute.

Fix

Request coalescing (single-flight), hot-key replication in Redis, and pre-warming from search-volume streams.

Problem — Unknown booking state

The supplier call times out after payment authorization; did the booking happen?

Fix

Idempotent supplier calls, a PENDING_VERIFICATION state, reconciliation jobs that look up the supplier reference, and user messaging that does not promise before confirmation.

Problem — Regional outage

One region of the cache, index or DB goes down.

Fix

Multi-region deployment with stateless services, replicated bookings, regional caches that rebuild from providers, and read-only degradation for search.

08 / Summary

Cheat sheet

What to remember before walking into the room.

Key numbers

50M DAU · ~10K searches/sec · ~50 providers per search · ~100K provider calls/sec · ~100 bookings/sec

Key datastores

Redis (fare cache) · Elasticsearch (hotels, geo) · PostgreSQL (bookings) · Kafka · data lake

Search strategy

Parallel fan-out, timeouts, circuit breakers, streamed partial results, dedupe and rank.

Cache strategy

Tiered TTL, stale-while-revalidate, cache warmers, evict on price drift.

Booking state machine

INITIATED → PRICE_VERIFIED → PAYMENT_AUTHORIZED → CONFIRMED, or FAILED / CANCELLED.

Key tradeoffs

Speed vs. price freshness. Coverage vs. latency. Authorize-first safety vs. extra steps.

Hardest part

Giving fast, believable prices from slow third parties, then booking exactly once.

Patterns

Scatter-gather · circuit breaker · single-flight · saga · idempotency · stale-while-revalidate

Sharding keys

Fare cache → route+date · Bookings → user_id · Hotels → geo region · Kafka → search_id / booking_id
