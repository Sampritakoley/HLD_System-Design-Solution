01 / Understanding the problem

What is this system, really?

Autocomplete shows a short list of likely searches as the user types. Type “how to” and you instantly see “how to tie a tie”, “how to lose weight”, and so on. It saves keystrokes, fixes spelling and guides people to better queries.

The core tension: the answer must arrive faster than the user types the next letter, for hundreds of thousands of requests per second, while the underlying popularity of queries keeps shifting.

Core features in scope

Prefix suggestions

Return the top 5-10 completions for whatever the user has typed so far.

Ranking

Order by popularity, with freshness, location, language and optional personalization.

Freshness

Trending and breaking queries appear within minutes, not days.

Safety & quality

Filter offensive, private or illegal suggestions; handle typos gracefully.

What makes this hard at scale

  • Extreme QPS. Every keystroke can trigger a request; traffic is several times the search rate.
  • Tight latency. Users perceive anything over ~100-200 ms as laggy.
  • Huge key space. Billions of distinct queries and prefixes, though the top ones dominate.
  • Moving popularity. News, memes and events change what should rank first, within minutes.
  • Hot prefixes. Short prefixes like “a” or “how” receive a disproportionate share of traffic.
02 / Requirements

Functional vs. non-functional requirements

Non-functional requirements drive the architecture, so they come first.

Functional

  • Given a prefix, return top 5-10 suggestions
  • Rank by popularity and relevance
  • Support multiple languages and regions
  • Reflect trending queries quickly
  • Filter inappropriate content
  • Optional personalization from history
  • Handle misspellings (fuzzy matching)
  • Log user queries to improve ranking

Non-functional

  • 500M DAU, ~300K QPS peak at the edge
  • Response p99 < 100 ms end to end
  • 99.99% availability
  • Suggestions can be eventually consistent
  • Trending data fresh within ~minutes
  • Read-heavy, almost no user-visible writes
  • Degrade gracefully (serve slightly stale data)
  • Scales horizontally by prefix and region

Clarifying questions

Is the corpus past search queries, a product catalog, or both?
How many suggestions are returned, and does ranking use only frequency?
How fresh must trending suggestions be: minutes, hours or daily?
Do we personalize per user, and what are the privacy constraints?
Which languages and scripts must be supported?

Assumptions

DAU                    = 500M, ~5 searches per user per day
Searches per day       = 2.5B
Requests per search    = ~4 (debounced; not every keystroke fires)
Suggestion requests    = ~10B/day
Cache hit rate         = ~90% (browser, CDN, edge, Redis) for popular prefixes
Distinct queries kept  = ~1B (min frequency threshold applied)
Average query length   = ~20 characters; response ≈ 0.5-1 KB

QPS

Requests:  10B / 86,400 = ~115K/sec avg → ~300K/sec peak
Origin after ~90% cache hits: ~30K/sec peak hitting the suggestion servers
Query logging: 2.5B/day = ~29K/sec avg → streamed to Kafka

Reads dominate completely. Caching at every layer is the first
lever; the second is serving from memory.

Storage

Query logs: 2.5B/day × ~100 B = ~250 GB/day → aggregated, raw kept short-term
Suggestion index: ~1B queries × ~50 B (text + score) = ~50 GB
Trie / prefix map with top-K per node: ~100-200 GB total, split across shards
Each shard replica fits in RAM. Keep only queries above a minimum
frequency to cut the long tail.

Bandwidth

Responses: 300K/sec × ~1 KB = ~300 MB/s at the edge, mostly served by CDN and caches
The constraint is latency and QPS, not storage or bandwidth.
04 / High-level design

Architecture

Every box exists because of a number from Step 3. Two paths: a fast read path and a slow offline build path.

 CLIENT (debounce ~100 ms · local cache · cancel stale requests)
     │
 [ CDN / Edge cache ]  popular prefixes
     │
 [ API Gateway / LB ]  rate limit · routing by prefix / region
     │
 [ Suggestion Service ] ─► [ In-memory Trie / prefix index shards ]
     │         ▲                       ▲ atomic snapshot load
     │         │                       │
     │   [ Redis cache ]        [ Trie Builder ] ◄── [ Aggregated query counts ]
     │                                                   ▲
     └─► log query ─► [ Kafka ] ─► [ Stream aggregation (Flink) ] ─► trending boosts
                                  └► [ Batch aggregation (Spark) ] ─► [ Data lake ]

Read path never touches a database; it serves from memory. Writes happen offline.

Component rationale

Client
Debounces keystrokes, cancels outdated requests, and caches earlier results so deleting a character is instant.
CDN / edge cache
Short, popular prefixes are identical for millions of users, so edge caches absorb most traffic for a few minutes at a time.
Suggestion service
Stateless servers that look up the prefix in the in-memory index, apply filters and personalization, and return the top K.
In-memory trie / prefix index
Each node stores the top-K completions, so a lookup is just walking the prefix, no sorting at query time.
Trie builder
Offline job that turns aggregated counts into a fresh index snapshot, then ships it to servers for an atomic swap.
Kafka + aggregation
Collects query logs; batch jobs compute long-term popularity, a streaming job detects trending queries in minutes.
Filter / safety service
Blocklists and classifiers remove offensive, private or legally restricted suggestions before they reach an index.

End-to-end flow — "user types 'new yo'"

  1. After a ~100 ms pause the client sends GET /suggest?q=new+yo&lang=en&region=US, unless the local cache has it.
  2. The request hits the CDN or edge; a popular prefix returns immediately from cache.
  3. On a miss, the gateway routes by prefix to the right suggestion shard (and nearest region).
  4. The service checks Redis; on a miss it walks the trie to node “new yo” and reads its precomputed top-K list.
  5. It merges in trending boosts, applies filters and optional personalization, then returns about 5-10 items.
  6. The response is cached with a short TTL (minutes) and shown to the user in well under 100 ms.
  7. When the user finally searches, the query is logged to Kafka, feeding both the streaming and batch aggregations.
  8. Periodically the Trie Builder produces a new snapshot that servers load and swap in atomically.
05 / Database design

Storage layer

Different data, different access patterns, different stores. The serving path uses memory, not a database.

DataStoreWhy
Serving index (prefix → top-K)In-memory trie / hash mapMicrosecond lookups, read-only snapshots
Hot prefix cacheRedis + CDNAbsorbs the heaviest traffic
Raw query logsKafka → data lake (S3 / HDFS)High-volume append, batch processing
Aggregated query countsBigtable / Cassandra / ParquetLarge key-value, rebuilt periodically
Blocklists, configPostgreSQL / config serviceSmall, needs audit
Personalization signalsRedis / feature storePer-user recent searches, low latency

Core structures

-- Trie node (conceptual)
Node {
  children: map<char, Node>
  top_k:    [ (query, score) × K ]   -- precomputed, sorted
  is_end:   bool
}

-- Alternative: flat map built offline (simpler, easier to shard)
"ne"       → [ "new york", "netflix", "news", "nepal", "new balance" ]
"new"      → [ "new york", "news", "new balance", "newegg", "new year" ]
"new yo"   → [ "new york", "new york times", "new york weather" ]

-- Aggregated counts (offline)
query_counts(query, locale, window, count, last_seen)

-- Score
score = w1 × log(frequency) + w2 × recency/trend boost + w3 × locale match

Sharding strategy

  • By prefix range — e.g. first 1-2 characters map to a shard; simple routing, but skewed (“s” is far busier than “x”).
  • Balanced by traffic — use a shard map built from observed load and rebalance periodically.
  • Replication — each shard has many read replicas; the index is read-only so replication is trivial.
  • By region and language — separate indexes per locale to keep each one small and relevant.
06 / Deep dives

Deep dive on 3 critical components

For each: the problem, the naive solution, why it fails, and the real solution. Volunteer these before the interviewer asks.

01 Prefix data structure — top-K in microseconds

The problem: Given any prefix, return the 5-10 most popular completions out of a billion queries in a few milliseconds.

Naive solution — SQL LIKE with sort
SELECT query FROM queries WHERE query LIKE 'new yo%'
ORDER BY count DESC LIMIT 10

Why it fails: Even with an index, short prefixes match millions of rows that must be sorted per request. A relational DB cannot serve 30K+ such queries per second within a few milliseconds.

Real solution — trie with precomputed top-K at every node
1. Build a trie keyed by characters. Each node stores the top-K
   completions (with scores) for its prefix, computed offline.

2. Lookup = walk len(prefix) nodes, then return node.top_k.
   O(L) time with no sorting and no scanning. Microseconds.

3. Memory: storing K full strings per node is heavy. Store pointers
   or ids to a shared string table instead, and use a compressed
   trie (radix tree) to merge single-child chains.

4. Prune the long tail: only index queries above a frequency
   threshold, and limit max prefix depth (e.g. 50 chars).

5. Alternative: a flat hash map prefix → top-K list built offline.
   Simpler and easy to shard; costs more memory for repeated prefixes.

6. Fuzzy matching: fall back to edit-distance or n-gram candidates
   only when exact prefix results are empty or low quality.

7. Immutable snapshots: the trie is never mutated while serving.
   A new version is built offline and swapped in atomically.

Precompute at build time what you would otherwise compute at
query time. That moves all cost off the latency path.
The key insight: trade memory and offline compute for query speed. Precomputing top-K at each prefix turns a search problem into a pointer walk.
02 Data pipeline & freshness — keep suggestions current

The problem: Popularity changes continuously. Rebuilding on every query is impossible, but a weekly rebuild misses breaking news and new products.

Naive solution — update the trie on every search
on each search: for each prefix of query: node.count++ ; re-sort top_k

Why it fails: Tens of thousands of searches per second would write to the same hot nodes (“a”, “th”), forcing locks and re-sorting on the serving path. It slows reads and risks inconsistent results across replicas.

Real solution — separate read and write paths: batch + streaming layers
1. Log every search to Kafka (async, sampled if needed). The serving
   path never writes.

2. Batch layer (hourly/daily, Spark): aggregate counts per query and
   locale over a window with time decay; rebuild the full trie
   snapshot; run safety filters.

3. Streaming layer (Flink, minutes): sliding-window counts detect
   queries whose rate is spiking vs their baseline. Output a small
   "trending boosts" table per locale.

4. At serve time, merge: batch top-K + trending boosts → final ranking.
   The boost table is small, so it fits in memory and refreshes quickly.

5. Deployment: build snapshot → validate (size, sanity checks, sample
   queries) → push to servers → each loads in the background and swaps
   atomically. Keep the previous version for instant rollback.

6. Filtering: blocklists, abuse classifiers and legal takedowns apply
   at build time and also as a fast serve-time deny list for urgent
   removals.

7. Sampling: count 1 in N searches for very hot queries to cut volume.
   Accuracy loss is negligible for ranking.

Freshness is a spectrum: daily for the stable long tail,
minutes for trending, seconds for emergency removals.
The tradeoff is freshness versus stability and cost. Use a slow, accurate batch layer for the bulk and a small fast layer for what is changing right now.
03 Serving at scale — caching, sharding and hot prefixes

The problem: 300K requests per second at peak, from users all over the world, with a p99 under 100 ms, and heavily skewed toward a few short prefixes.

Naive solution — every request hits the central service
client → one suggestion cluster in one region → trie lookup → response

Why it fails: Cross-continent latency alone can exceed the budget. Identical requests for “fa” or “how” hit the same servers millions of times. One region outage takes down the feature for everyone.

Real solution — layered caches, geo-distributed replicas, smart sharding
1. Client: debounce (~100 ms), cancel in-flight requests, keep a local
   cache so backspacing is free. Typically cuts requests 30-50%.

2. Browser/CDN cache: Cache-Control with a short TTL (e.g. 1-5 min)
   for non-personalized responses. Popular prefixes become cache hits
   before reaching our servers.

3. Regional deployment: full replicas of the index in every major
   region, behind geo-DNS or anycast. Round trip stays in tens of ms.

4. Server cache: Redis or in-process LRU for hot prefixes; most short
   prefixes are served without even touching the trie.

5. Hot prefix handling: very short prefixes (1-2 chars) are precomputed
   and pushed to the edge; their answers barely change.

6. Sharding when the index is too big for one machine: split by prefix
   with load-aware shard maps; each shard replicated many times and
   health-checked, with routing in the gateway.

7. Personalization without breaking caching: serve the cached global
   list, then merge a small per-user list (recent searches) on the
   client or in a light server step.

8. Resilience: timeouts of a few tens of ms, return partial or cached
   results, and fail quietly (search still works without suggestions).

Every layer that answers early removes load from the next one.
Suggestions are a nice-to-have, so they must never block the search box.
Most requests should never reach the trie. Cache at the client, edge and server, and keep replicas close to users so the remaining lookups are both fast and cheap.
07 / Tradeoffs & alternatives

What we did NOT choose and why

Rejected alternatives

AlternativeWhy rejected
SQL LIKE queriesScans and sorts millions of rows per request; too slow and costly.
Sort completions at query timeWasted work; precomputing top-K per prefix is far cheaper.
Update the trie in real timeWrite contention and inconsistency; use immutable snapshots plus a trending layer.
Elasticsearch prefix queries onlyHigher latency and cost at this QPS; fine for catalogs, not for web scale.
Single global clusterHigh latency for distant users and a single failure domain.
Fully personalized, uncached resultsKills cache hit rate; blend a small personal layer instead.

What breaks at 10× scale and how we fix it

Problem — Hot prefixes and traffic spikes

A breaking event sends millions of identical queries for the same new prefix within seconds.

Fix

Edge caching with request coalescing, push trending boosts quickly, and replicate hot shards. Short TTL caches absorb the spike without overloading origin.

Problem — Memory too large for one machine

The index grows as languages, locales and long-tail queries are added.

Fix

Prune the tail, use a compressed trie with a shared string table, split by locale, and shard by prefix with replicas. Keep each shard comfortably within RAM.

Problem — Offensive or harmful suggestions slip through

Coordinated abuse or unfortunate query patterns push bad completions to the top.

Fix

Blocklists and classifiers at build time, a fast serve-time deny list for urgent takedowns, minimum unique-user thresholds to resist manipulation, and human review for sensitive categories.

Problem — Bad snapshot deployed

A pipeline bug produces an empty or corrupted index, and every server loads it.

Fix

Validation gates (size, sample-query checks), canary rollout to a few servers first, keep the previous snapshot for instant rollback, and monitor suggestion click-through and empty-result rates.

08 / Summary

Cheat sheet

What to remember before walking into the room.

Key numbers

500M DAU · ~10B requests/day · ~115K QPS avg, ~300K peak · ~90% cache hits · p99 < 100 ms · ~50 GB index

Key datastores

In-memory trie (serving) · Redis + CDN (cache) · Kafka + data lake (logs) · Bigtable / Cassandra (counts)

Index strategy

Trie or flat map with precomputed top-K per prefix; compressed, pruned to frequent queries; immutable snapshots.

Freshness strategy

Batch rebuild for the bulk, streaming trending boosts for minutes-fresh signals, instant deny list for removals.

Serving strategy

Client debounce, CDN and Redis caching, regional replicas, shard by prefix, graceful degradation.

Key tradeoffs

Memory vs. speed. Freshness vs. stability. Personalization vs. cache hit rate. Coverage vs. index size.

Hardest part

Staying under 100 ms at hundreds of thousands of QPS while rankings keep shifting.

Patterns

Trie · precomputation · lambda architecture (batch + stream) · atomic snapshot swap · layered caching · geo replication

Sharding keys

Index → prefix range (load-aware) + locale · Kafka → query hash · Cache → prefix + locale
