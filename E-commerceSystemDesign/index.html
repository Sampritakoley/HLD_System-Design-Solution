01 / Understanding the problem

What is this system, really?

An e-commerce platform lets millions of shoppers find products from many sellers, pay safely and get orders delivered. It is a read-heavy catalog on one side and a strictly consistent order and inventory engine on the other.

The core tension: 99% of traffic is browsing and search, which can be stale and cached; but the 1% that touches stock and money must never be wrong.

Core features in scope

Catalog & search

Browse categories, search by keyword, filter and sort across 100M+ listings.

Cart & checkout

Add items, apply offers, pick address and payment method, place the order.

Inventory

Track stock per SKU per warehouse; reserve on checkout, never oversell.

Orders & delivery

Payment, order lifecycle, shipping updates, returns and refunds.

What makes this hard at scale

  • Read firehose. Product pages and search dominate traffic and must be fast everywhere.
  • Overselling. Thousands of buyers racing for the last 100 units of a deal.
  • Distributed transaction. Order, inventory and payment are separate services that must agree.
  • Flash sales. Big Billion Days style events spike traffic 10× in seconds on a few hot SKUs.
  • Search relevance. Typos, synonyms, filters and ranking in tens of milliseconds.
02 / Requirements

Functional vs. non-functional requirements

Non-functional requirements drive the architecture, so they come first.

Functional

  • Browse and view product details
  • Search with filters, sort and autocomplete
  • Cart and wishlist
  • Place order, pay, cancel, return
  • Seller catalog and stock management
  • Order tracking and notifications
  • Coupons and dynamic pricing
  • Reviews and ratings

Non-functional

  • 100M DAU, 10M orders/day, 10× sale peaks
  • Product page and search p99 < 200 ms
  • 99.99% availability for browse and checkout
  • Never oversell (strong consistency on stock)
  • Catalog and search can be eventually consistent
  • Payments exactly-once, orders durable
  • Graceful degradation under overload
  • Scales horizontally

Clarifying questions

Single seller (Amazon retail) or multi-seller marketplace? This changes catalog and inventory ownership.
Do we manage warehouses and delivery, or only the shopping side?
Are flash sales and limited-stock deals in scope?
Which payment methods: cards, UPI, wallet, COD? COD needs post-delivery reconciliation.
How fresh must prices and stock be on the product page versus at checkout?
03 / Estimation

Back-of-envelope math

Order-of-magnitude accuracy, with every assumption stated.

~100K/sPeak page reads
~30K/sPeak search QPS
~10K/sPeak orders (sale)

Assumptions

DAU                  = 100M, ~30 page views each
Orders per day       = 10M (average ~115/sec, sale peak ~10K/sec)
Catalog              = 100M SKUs, ~5 KB metadata each
Order record         = ~3 KB
Read : write ratio   = ~100 : 1

QPS

Page views: 100M × 30 / 86,400 = ~35K/sec avg → ~100K/sec peak
Search:     ~30% of views         → ~30K/sec peak
Orders:     10M / 86,400          = ~115/sec avg → ~10K/sec in a flash sale

Reads dominate, so cache aggressively (CDN, Redis).
Writes are few but must be correct, so keep them in transactional stores.

Storage

Catalog:  100M × 5 KB      = ~500 GB (plus images on object store + CDN)
Orders:   10M/day × 3 KB   = 30 GB/day ≈ ~11 TB/year
Inventory: 100M × ~50 B    = ~5 GB, fits in memory
Search index: ~1-2× catalog = ~1 TB across shards

Bandwidth

Mostly images: 100K pages/s × ~500 KB = ~50 GB/s → served by CDN, not origin.

The constraint is read QPS and hot-key contention on stock,
not raw storage.
04 / High-level design

Architecture

Every box exists because of a number from Step 3.

 WEB / MOBILE APP
        │
   [ CDN ]  (images, static, cached pages)
        │
 [ API Gateway / LB ]  auth · rate limit
        │
 ├─► [ Catalog Service ] ──► [ Product DB ] ──► [ Redis cache ]
 ├─► [ Search Service ]  ──► [ Elasticsearch ]
 ├─► [ Cart Service ]    ──► [ Redis ]
 ├─► [ Order Service ]   ──► [ Orders DB ]
 │         │

 │         ├─► [ Payment Service ]   ──► [ Payment gateway ]
 │         └─► [ Pricing / Offers ]

 └─► [ Kafka ] ──► Search indexer · Notifications · Shipping · Analytics

Catalog changes flow through Kafka to the search index asynchronously

Component rationale

CDN + cache
Serves images and hot product pages from the edge. Without it, 100K reads/sec would hit origin.
Catalog service
Source of truth for product data, read-heavy. Cache in Redis with a short TTL and invalidate on seller updates.
Search service + Elasticsearch
Inverted index with filters, facets and ranking. Rebuilt incrementally from catalog change events.
Cart service
Carts are temporary and per-user, so Redis with a TTL (backed by a DB for logged-in users) is enough.
Inventory service
Owns stock counts and reservations. The only place that needs strong consistency under heavy contention.
Order + Payment services
Order service runs the state machine and coordinates a saga; Payment service talks to gateways idempotently.
Kafka
Decouples writes from search indexing, notifications, shipping and analytics, and absorbs spikes.

End-to-end flow — "user places an order"

  1. User opens a product: CDN or Redis serves the page; the price and stock shown are cached and may be slightly stale.
  2. User adds to cart; the cart lives in Redis. Prices are re-validated at checkout.
  3. On checkout, Order Service creates an order in PENDING with an idempotency key.
  4. Inventory Service reserves stock atomically with a 10-minute hold (RESERVED). If it fails, the order is rejected.
  5. Payment Service charges the user. On success the order moves to CONFIRMED and the reservation becomes a permanent deduction.
  6. On payment failure or timeout, the reservation is released and the order moves to CANCELLED.
  7. Kafka events trigger notifications, shipping and search/stock refresh; the order proceeds through SHIPPED to DELIVERED.

Core tables and keys

-- SQL (orders)
CREATE TABLE orders (
  order_id    UUID PRIMARY KEY,
  user_id     BIGINT NOT NULL,
  status      TEXT NOT NULL,  -- PENDING | CONFIRMED | SHIPPED | DELIVERED | CANCELLED
  total       NUMERIC(12,2),
  idem_key    TEXT UNIQUE,    -- prevents duplicate orders on retry
  created_at  TIMESTAMP DEFAULT now()
);
CREATE TABLE inventory (
  sku_id BIGINT, warehouse_id INT, available INT CHECK (available >= 0),
  reserved INT, PRIMARY KEY (sku_id, warehouse_id)
);

-- Redis
Key: stock:{sku}        Value: integer available
Key: cart:{user}        Value: HASH { sku: qty }   TTL 30d
Key: reserve:{order}    Value: { sku: qty }        TTL 10m

Sharding strategy

  • Catalog — shard by product_id; replicate and cache for reads.
  • Orders — shard by user_id so "my orders" is a single-shard query.
  • Inventory — shard by sku_id; hot SKUs get split into sub-counters (see deep dive 2).
  • Search — Elasticsearch shards with replicas; scale replicas for read QPS.
06 / Deep dives

Deep dive on 3 critical components

For each: the problem, the naive solution, why it fails, and the real solution. Volunteer these before the interviewer asks.

01 Search — relevant results over 100M products in tens of ms

The problem: Keyword search with typos, filters and sorting, 30K queries/sec at peak.

Naive solution — SQL LIKE query
SELECT * FROM products WHERE title LIKE '%running shoes%' AND price < 3000

Why it fails: A leading wildcard cannot use an index, so it scans every row. There is no relevance ranking, typo tolerance or facet counts.

Real solution — inverted index in Elasticsearch, fed by events
1. Each product change → Kafka → indexer → Elasticsearch.
   Search is eventually consistent (seconds of lag is fine).

2. Inverted index: term → list of product ids. Queries intersect
   postings lists, filters use cached bitsets.

3. Rank by text relevance (BM25) + popularity, rating, conversion,
   in-stock and seller quality. Fuzzy matching handles typos.

4. Autocomplete from a prefix index (edge n-grams or a trie)
   of popular queries, cached in Redis.

5. Cache top queries; scatter-gather across shards, merge top-K.

Never show stale stock as authoritative: search can say "in stock",
but the checkout reservation is the real decision.
Search is a derived read model. Keep the DB as truth, rebuild the index from events, and accept seconds of staleness for speed.
02 Inventory — never oversell, even in a flash sale

The problem: 50,000 users try to buy 1,000 units of a deal phone at the same instant.

Naive solution — read stock, then write
stock = SELECT available FROM inventory WHERE sku=?;
if stock > 0: UPDATE inventory SET available = stock - 1 WHERE sku=?

Why it fails: Check-then-act is a race: many requests see stock = 1 and all succeed. Row locks on one hot SKU also serialize everything and collapse throughput.

Real solution — atomic reserve, hold with TTL, shard the hot counter
1. Atomic conditional decrement (no read-then-write):
     UPDATE inventory SET available = available - :q, reserved = reserved + :q
     WHERE sku_id = ? AND available >= :q      -- 0 rows → out of stock

2. Hot SKUs: do it in Redis with a Lua script / DECRBY (single-threaded,
   atomic, 100K+ ops/sec), then persist to the DB asynchronously.

3. Split one counter into N sub-counters (stock:{sku}:0..N-1) so
   load spreads across keys and nodes; retry the next on empty.

4. Reservation has a TTL (about 10 min). Payment success → commit.
   Failure or expiry → release stock back.

5. Flash sale shield: queue or token-gate users, rate limit per user,
   return "sold out" fast once the counter hits 0.

The DB constraint available >= 0 is the final safety net
even if Redis and the DB drift.
Strong consistency applies to stock only. Browse, search and cart can be stale; the atomic reservation at checkout is the single point of truth.
03 Checkout — order, stock and payment must agree

The problem: Order, Inventory and Payment are separate services. Any step can fail or time out, and retries must not double-charge or double-reserve.

Naive solution — one distributed transaction (2PC)
BEGIN; reserve stock; charge card; create order; COMMIT;  -- across 3 services

Why it fails: Two-phase commit holds locks across services and an external payment gateway cannot take part. One slow dependency blocks everyone, and a coordinator crash leaves state stuck.

Real solution — saga with compensations and idempotency
1. Order Service is the orchestrator, persisting each step:
     PENDING → STOCK_RESERVED → PAYMENT_DONE → CONFIRMED

2. Failure at any step runs compensations:
     payment failed → release reservation → CANCELLED
     refund / release are themselves retried until they succeed.

3. Idempotency key per order on every call (order, reserve, charge):
   a retry returns the original result, never a second effect.

4. Payments: unique constraint on (order_id), async webhook from the
   gateway confirms status; a reconciliation job fixes stuck orders.

5. Use the outbox pattern: write the DB change and the Kafka event in
   one local transaction so events are never lost.

Timeouts everywhere + a sweeper for expired PENDING orders
guarantees nothing stays locked forever.
Replace one big transaction with a chain of small local ones plus compensations. Eventual consistency, but always a clear final state.
07 / Tradeoffs & alternatives

What we did NOT choose and why

Rejected alternatives

AlternativeWhy rejected
SQL LIKE for searchFull scans, no ranking, no typo tolerance.
2PC across servicesBlocks on the slowest participant; gateways cannot join it.
Check-then-update stockRace condition causes overselling.
One DB for everythingCatalog reads would starve order writes; scaling needs differ.
Strong consistency for catalog and searchCostly with no user benefit; seconds of lag is fine.
Deducting stock only after paymentAllows paying for items that are already gone; reserve first.

What breaks at 10× scale and how we fix it

Problem — Hot product during a flash sale

One SKU gets thousands of requests per second, overloading a single cache key and DB row.

Fix

Pre-warm caches, serve the page from the CDN, shard the stock counter, use a virtual waiting room, and shed excess load early.

Problem — Payment gateway slowdown

Timeouts leave orders pending with stock held, and users retry and risk double charges.

Fix

Idempotency keys, circuit breakers, multiple gateways with fallback, short reservation TTLs, and reconciliation jobs.

Problem — Search index lag or cluster failure

Updates take minutes to appear, or search goes down while browse still works.

Fix

Monitor consumer lag, replicate shards, fall back to category browse and cached results, and re-index from Kafka if needed.

Problem — Regional outage

A data center failure blocks browsing and checkout for a region.

Fix

Multi-region deployment, replicated orders and inventory, stateless services behind global load balancing, and degrade to read-only browse if checkout is impaired.

08 / Summary

Cheat sheet

What to remember before walking into the room.

Key numbers

100M DAU · ~100K reads/sec · ~30K search/sec · 10M orders/day · ~10K orders/sec in sales

Key datastores

Product DB + Redis · Elasticsearch · SQL for orders and inventory · Kafka · CDN

Search strategy

Inverted index fed by Kafka events; BM25 + popularity ranking; cached autocomplete.

Inventory strategy

Atomic conditional decrement, TTL reservation, sharded hot counters, DB constraint as backstop.

Order state machine

PENDING → CONFIRMED → SHIPPED → DELIVERED, or CANCELLED with compensations.

Key tradeoffs

Consistency for stock vs. availability for browse. Reserve early vs. fairness. Speed vs. search freshness.

Hardest part

Selling the last unit exactly once under massive concurrency, across services that can each fail.

Patterns

CQRS read models · saga · outbox · idempotency keys · cache-aside · load shedding

Sharding keys

Catalog → product_id · Orders → user_id · Inventory → sku_id · Kafka → order_id / sku_id
