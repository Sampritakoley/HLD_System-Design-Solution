01 / Understanding the problem

What is this system, really?

A rate limiter caps how many requests a client can make in a time window. It protects services from abuse, bugs and traffic spikes, enforces fair usage and plan quotas, and keeps costs predictable. Think of it as a tiny, extremely fast counter sitting in front of every API.

The core challenge: the limiter sits on the hot path of every request, so it must add almost no latency, never become a single point of failure, and stay accurate while counters are shared across dozens of gateway nodes. A slow or broken limiter is worse than none.

Core features in scope

Limit checks

For each request, decide allow or reject based on client identity and the matching rule. Decision in a couple of milliseconds.

Flexible rules

Limits per user, API key, IP or endpoint, with different tiers (free, pro, internal) and windows (per second, per minute, per day).

Clear feedback

Rejected calls get HTTP 429 with headers showing the limit, remaining quota and when to retry.

Live configuration

Rules change without redeploying. Updates reach every node within seconds.

What makes this hard at scale

  • Hot path latency. The check runs before every request; even 10ms extra is felt everywhere.
  • Distributed counters. Many gateways must agree on one client's count without racing each other.
  • Burst behaviour. Fixed windows allow double-rate bursts at the boundary; the algorithm choice matters.
  • Hot keys. One abusive IP or one huge customer can overload a single counter shard.
  • Failure mode. If the counter store dies, do we block everyone or let everyone through?
02 / Requirements

Functional vs. non-functional requirements

Non-functional requirements are what actually drive architecture decisions — they're listed first for a reason.

Functional

  • Limit by user, API key, IP, endpoint
  • Multiple rules per request (AND logic)
  • Different limits per plan tier
  • Return 429 with retry headers
  • Update rules dynamically
  • Allow burst within a steady rate
  • Expose metrics on blocked traffic
  • Allowlist for trusted clients

Non-functional

  • 1M checks/sec at peak
  • Added latency < 5ms (p99)
  • 99.99% availability
  • Fail open if limiter is down
  • Accurate within ~1-5% across nodes
  • Memory per client is tiny
  • Rule changes live in < 10s
  • Horizontally scalable

Clarifying questions

Client-side, server-side, or at the API gateway? Gateway is the usual answer.
What identifies a client: user ID, API key, IP, or a combination?
Hard limit or soft limit? Do we queue excess requests or reject them outright?
Single region or multi-region? Global limits are far harder than per-region limits.
Must counts be exact (billing quotas) or approximate (abuse protection)?
If the limiter fails, should traffic fail open or fail closed?
03 / Estimation

Back-of-envelope math

Order-of-magnitude accuracy is the goal here, not precision. Every assumption is stated explicitly.

~1M/sPeak limit checks
~10GBCounter memory
~20Redis shards

Assumptions

Total requests          = 300K/sec average
Peak (3x average)       = ~1M/sec
Active clients          = 50M in the last window (users + IPs)
Rules per request       = 2 (e.g. per-user and per-endpoint)
Counter state per key   = ~100 bytes (key + count + timestamp)

QPS

Checks/sec:
  1M requests × 2 rules        = ~2M counter ops/sec
  Redis handles ~100K ops/sec per node
  2M / 100K                    = ~20 shards (plus replicas)

Use a Lua script or pipelining so each check is one round trip,
not two. Local in-memory pre-checks cut remote calls further.

Storage

Counters:
  50M keys × 100 B             = ~5 GB  (~10 GB with overhead)
  Keys expire with their window (TTL), so memory self-cleans.

Rules config:
  ~10K rules × 1 KB            = ~10 MB, cached on every node

Blocked-request logs:
  ~1% blocked × 300K/s × 100 B = ~300 KB/s (~25 GB/day)

Bandwidth

2M ops/sec × ~100 B                        = ~200 MB/s to Redis
Per-shard load                             = ~10 MB/s, trivial

The constraint is latency and CPU per op, not bandwidth.
Keep Redis in the same zone as gateways: ~0.5ms round trip.
04 / High-level design

Architecture

Built top-down from the client. Every box exists because of a number from Step 3.

CLIENT (Mobile / Web / Partner API)

[ Backend services ]           │                                      │
                               ▼                                      ▼

                      counters, TTL, Lua
                               │
                               ▼
                   [ Metrics / Kafka ] ──► Dashboards · Alerts · Abuse detection

Blocked path: middleware returns 429 + Retry-After without touching backends

Component rationale

Rate limiter middleware
Runs inside the gateway as a library, not a separate hop. This avoids an extra network call and keeps added latency to one Redis round trip at most.
API Gateway
The natural choke point: every request passes through it, it already knows the client identity, and it can reject early before any backend work happens.
Redis Cluster
In-memory, sub-millisecond, atomic operations (INCR, Lua scripts) and native key expiry. Sharded by client key so each client's counter lives on exactly one node.
Rules Service + DB
Stores limits per client, tier and endpoint. Edited by admins or billing events, read rarely, so a simple relational store is enough.
Local rules cache
Each gateway keeps rules in memory and refreshes by polling or pub/sub push. Rule lookup never leaves the process.
Metrics pipeline
Allowed and blocked counts flow asynchronously to Kafka and dashboards. It powers alerts and abuse detection and is never on the request path.

End-to-end data flow — "request arrives at the gateway"

  1. Request reaches the gateway; auth identifies the user ID, API key or IP.
  2. Middleware looks up matching rules in the local cache (by tier and endpoint).
  3. It builds a counter key, e.g. rl:{user}:{endpoint}, and runs an atomic Lua script on Redis.
  4. The script refills or slides the window, checks the limit, and returns allow/deny plus remaining quota.
  5. If allowed, the request is forwarded to the backend with rate-limit headers attached.
  6. If denied, the gateway returns 429 with Retry-After immediately.
  7. An allow/block event is emitted asynchronously to the metrics pipeline.
  8. If Redis times out (e.g. 20ms), the middleware fails open and logs the failure.

Core tables and keys

-- PostgreSQL (rules)
CREATE TABLE rate_rules (
  rule_id     BIGINT PRIMARY KEY,
  scope       TEXT NOT NULL,        -- user | api_key | ip | endpoint
  tier        TEXT,                 -- free | pro | internal
  endpoint    TEXT,                 -- e.g. POST /orders
  limit_count INT NOT NULL,         -- tokens per window
  window_sec  INT NOT NULL,
  burst       INT,                  -- bucket capacity
  updated_at  TIMESTAMP DEFAULT now()
);

-- Redis (token bucket per client + rule)
Key:   rl:{rule_id}:{client_id}
Value: HASH { tokens: 87, last_refill_ms: 1735000000123 }
TTL:   2 x window (idle clients disappear automatically)

Atomic check script (token bucket)

-- KEYS[1]=bucket, ARGV: capacity, refill_per_sec, now_ms, cost
tokens, last = HMGET(key, 'tokens', 'last_refill_ms')
tokens = min(capacity, tokens + (now - last) * refill_per_sec)
if tokens >= cost then tokens -= cost; allowed = 1 else allowed = 0 end
HMSET(key, tokens, now); EXPIRE(key, ttl)
return { allowed, tokens }

Sharding strategy

  • Counters — hash of client_id picks the Redis shard, so one client's checks hit one node and stay consistent.
  • Hot clients — split one key into N sub-keys with a share of the limit each (see deep dive 2).
  • Rules — no sharding needed; replicate to every gateway cache.
  • Replicas — each shard has a replica for failover; counters may lose a few seconds of data, which is acceptable.
06 / Deep dives

Deep dive on 3 critical components

For each: the problem, the naive solution, why it fails, and the real solution used at scale. Volunteer these problems before the interviewer asks — it signals senior-level thinking.

01 Algorithm choice — accurate limits without bursts or memory bloat

The problem: Enforce "100 requests per minute" fairly, allow harmless short bursts, and keep memory tiny for 50M clients.

Naive solution — fixed window counter
key = clientId + floor(now / 60s);   INCR key;   if count > 100 → reject

Why it fails: A client can send 100 requests at 12:00:59 and 100 more at 12:01:00. That is 200 requests in two seconds, double the intended rate, all technically allowed.

Real solution — token bucket (or sliding window counter)
Token bucket:
  - Bucket holds up to `capacity` tokens; refills at a steady rate.
  - Each request spends one token. Empty bucket → 429.
  - Allows bursts up to capacity, then enforces the average rate.
  - State = 2 numbers per client (tokens, last_refill) ~ 100 bytes.

Sliding window counter (when smooth limits matter):
  - Keep counts for current and previous window.
  - estimate = prev × (1 − elapsed%) + current
  - Near-exact, 2 counters per client, no per-request log.

Sliding window log (exact, costly):
  - Stores every timestamp in a sorted set. Memory = limit × clients.
  - Use only for small limits where exactness is critical.

Default to token bucket for APIs; sliding window counter
for strict "N per minute" promises.
The key insight: no algorithm is best everywhere. Token bucket gives burst tolerance at minimal memory, and the sliding window counter fixes the boundary problem with only two numbers per client.
02 Distributed counting — consistency across many gateways

The problem: Dozens of gateway nodes check the same client at once. The count must be correct, and one popular key must not melt a single Redis node.

Naive solution — read, compare, then write
count = GET key;   if count < limit { SET key count+1; allow }

Why it fails: Two gateways read 99 at the same instant, both see "under the limit", both write 100, and both allow. Under load this is a race that lets many extra requests through. Local per-node counters are also wrong because the same client hits different nodes.

Real solution — atomic server-side script, plus hot-key splitting
1. Do the whole check in one Lua script on Redis.
   Redis runs scripts single-threaded, so there is no race.
   One round trip: refill + check + decrement.

2. Shard by client key with consistent hashing so a client's
   state lives on one node; add replicas for failover.

3. Hot keys (a huge customer or attacker):
   - Split limit into N sub-keys (rl:key:0..N-1), each with limit/N,
     pick one at random per request → load spreads across shards.
   - Or use a local token lease: each gateway borrows a batch of
     tokens (e.g. 50) from Redis and spends them locally.

4. Multi-region: enforce per-region limits locally and sync
   totals asynchronously; accept small overshoot for global caps.

Batching tokens cuts Redis calls by 10-50x at the cost
of slight over-allowance near the limit.
Exact global limits need a single source of truth and cost latency. For abuse protection, approximate counts within a few percent are fine and far cheaper. Only billing-grade quotas deserve strict accuracy.
03 Failure handling — when the limiter itself breaks

The problem: Redis slows down or a shard dies. The limiter sits in front of every request, so its failure must not take the whole API down.

Naive solution — block requests if the limiter errors
try { allowed = redis.check(key) } catch { return 429 }

Why it fails: A Redis hiccup turns into a full outage for every user. The protection mechanism becomes the biggest risk to availability, and retries from blocked clients make the situation worse.

Real solution — timeouts, fail open, local fallback
1. Hard timeout on Redis calls (~10-20ms). Never wait longer.

2. Fail open by default: on error or timeout, allow the request
   and emit an alert. Brief over-allowance beats a global outage.

3. Local fallback limiter: each gateway keeps an in-memory
   token bucket with a generous per-node limit (limit / node count)
   so abuse is still bounded while Redis is down.

4. Circuit breaker: after repeated failures, skip Redis for a few
   seconds and probe again, instead of timing out on every request.

5. Fail closed only for sensitive endpoints (login, OTP, payments)
   where unlimited attempts are dangerous.

6. Redis replicas with automatic failover; counters lost in a
   failover only reset windows, which is harmless.

Clients also get clear 429 + Retry-After headers and should
use exponential backoff with jitter to avoid retry storms.
Decide fail-open vs fail-closed per endpoint, not globally. Availability matters for most APIs; security matters for a few.
07 / Tradeoffs & alternatives

What we did NOT choose and why

Rejected alternatives

AlternativeWhy rejected
Separate limiter microserviceAdds a network hop to every request. Embedding in the gateway with Redis is faster.
Per-node local counters onlyLoad balancing spreads one client across nodes, so real usage can be N times the limit.
Relational DB for countersToo slow for millions of atomic updates per second; Redis fits natively.
Fixed window counterAllows 2x bursts at window edges; token bucket or sliding window is fairer.
Sliding window log everywhereMemory grows with the limit and client count; too costly at 50M keys.
Strictly consistent global countersCross-region coordination adds latency to every call for marginal accuracy.
Fail closed by defaultMakes the limiter a single point of failure for the entire API.

What breaks at 10× scale and how we fix it

Problem — Redis becomes the bottleneck

At 10M checks/sec, hundreds of shards and cross-node network load make Redis costly and latency-sensitive.

Fix

Use local token leases so gateways spend batches locally, add a fast in-process pre-check for obviously blocked clients, and add more shards with consistent hashing.

Problem — DDoS from millions of IPs

Distributed attacks create huge numbers of unique keys, flooding Redis memory with counters.

Fix

Shed traffic earlier at the CDN/WAF, use short TTLs for anonymous keys, and apply coarse per-subnet limits before per-IP limits.

Problem — Rule update lag

Changing a customer's plan takes minutes to reach all gateways, so they are throttled at the old limit.

Fix

Push changes through pub/sub with version numbers, keep a short polling fallback, and let gateways reload rules without restarting.

Problem — Multi-region accuracy

A client using several regions can exceed a global limit because each region counts separately.

Fix

Split the global limit into per-region budgets, sync usage asynchronously, and rebalance budgets based on observed traffic.

08 / Summary

Cheat sheet

The ten things worth remembering before walking into the room.

Key numbers

1M peak checks/sec · ~2M counter ops/sec · ~20 Redis shards · ~5-10 GB counters · < 5ms added latency

Key datastores

Redis Cluster (counters) · PostgreSQL (rules) · Local cache (rules on gateway) · Kafka (events)

Algorithm strategy

Token bucket by default; sliding window counter for strict windows; avoid fixed window and the full log at scale.

Consistency strategy

Atomic Lua script on the owning shard; no read-then-write; hot keys split into sub-keys or token leases.

Response contract

HTTP 429 · Retry-After · X-RateLimit-Limit · X-RateLimit-Remaining · X-RateLimit-Reset

Key tradeoffs

Accuracy vs. latency. Burst tolerance vs. strictness. Fail open vs. fail closed. Memory vs. exactness.

Hardest part

Keeping counters correct across many nodes while adding almost no latency and never becoming a single point of failure.

Placement

Inside the API gateway as middleware, before any backend work. Not a separate hop for each request.

Sharding keys

Counters → hash(client_id) · Rules → replicated everywhere · Events → Kafka partition by client_id
