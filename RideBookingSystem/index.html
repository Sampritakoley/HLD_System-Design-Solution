01 / Understanding the problem

What is this system, really?

A ride booking platform connects riders who need a trip with nearby drivers who are free, in seconds. It estimates fares, matches the best driver, tracks the trip live and settles payment. Think of it as a real-time marketplace running on a constantly moving map.

The core challenge: driver locations change every few seconds, matching must be fast and never assign one driver to two riders, and riders expect to watch the car approach in real time. Most of the data is hot, short-lived and geographic.

Core features in scope

Request a ride

Rider picks pickup and drop, sees fare and ETA per vehicle type, then confirms the booking.

Driver matching

Find nearby available drivers, offer the trip, and confirm exactly one driver within seconds.

Live tracking

Both sides see each other's position on the map from accept to drop-off.

Fare & payment

Dynamic pricing, trip lifecycle, payment at the end, receipts and ratings.

What makes this hard at scale

  • Location firehose. Every online driver sends a GPS ping every few seconds, a constant write-heavy stream.
  • Geospatial search. "Drivers within 2 km" must answer in milliseconds over a million moving points.
  • Double assignment. Two riders must never get the same driver, even under concurrent matching.
  • Real-time push. Millions of open connections streaming positions and trip updates.
  • Demand spikes. Rain, concerts and airports create hot zones with surge pricing and sudden load.
02 / Requirements

Functional vs. non-functional requirements

Non-functional requirements are what actually drive architecture decisions — they're listed first for a reason.

Functional

  • Rider requests a ride with pickup and drop
  • Fare and ETA estimate before booking
  • Find and match nearby available drivers
  • Driver accepts or rejects an offer
  • Live location for both rider and driver
  • Trip lifecycle: start, end, cancel
  • Payments, receipts and ratings
  • Surge pricing in high-demand zones

Non-functional

  • 20M rides/day, 1M drivers online at peak
  • Match found in < 5 seconds (p95)
  • 99.99% availability for booking
  • No driver assigned to two trips (strong consistency)
  • Location can be eventually consistent
  • Tracking delay < 2 seconds
  • Payments must be exactly-once
  • Scales horizontally by city or region

Clarifying questions

Single city, country or global? Sharding by city changes the design a lot.
Do we only support instant rides, or also scheduled rides and pooling?
How is a driver chosen: nearest, best ETA, or rating and acceptance rate?
Is surge pricing in scope, and how fresh must the multiplier be?
Which payment methods: card, wallet, cash? Cash needs post-trip reconciliation.
How accurate must ETA be? This decides whether we need a road-graph routing engine.
03 / Estimation

Back-of-envelope math

Order-of-magnitude accuracy is the goal here, not precision. Every assumption is stated explicitly.

~250K/sDriver location updates
~1K/sPeak ride requests
~2MLive connections

Assumptions

Rides per day           = 20M
Peak ride requests      = ~1K/sec (average ~230/sec, peak ~4x)
Drivers online at peak  = 1M, GPS ping every 4 seconds
Active trips at peak    = ~1M (rider + driver both connected)
Location payload        = ~100 bytes (id, lat, lng, heading, ts)
Trip record             = ~2 KB

QPS

Location writes:
  1M drivers / 4s              = ~250K updates/sec

Nearby-driver searches:
  ~1K requests/sec × ~3 retries = ~3K geo queries/sec (light)

Tracking pushes:
  1M trips × 1 update / 4s     = ~250K pushes/sec

Writes dominate. Keep location in memory and out of the
main trip database, which only sees ~1K writes/sec.

Storage

Live driver state (latest only):
  1M × 100 B                   = ~100 MB in Redis, trivial

Location history (optional, for analytics and disputes):
  250K/s × 100 B              = 25 MB/s ≈ 2 TB/day → sample, compress, TTL 30 days

Trips:
  20M/day × 2 KB               = ~40 GB/day ≈ 15 TB/year

Bandwidth & connections

Inbound GPS              = 250K × 100 B = ~25 MB/s
WebSocket connections    = ~2M; one node holds ~100K → ~20-40 gateway nodes

The constraint is connection count and write rate, not bandwidth.
Shard by city so each region handles only its own drivers.
04 / High-level design

Architecture

Built top-down from the client. Every box exists because of a number from Step 3.

RIDER APP                                  DRIVER APP
    │  REST (book)      ▲ WebSocket          │ WebSocket (GPS, offers)
    ▼                   │ (tracking)         ▼
[ API Gateway / LB ]  ◄──────────────►  [ Realtime Gateway ]
    │                                          │
    ├──► [ Trip Service ] ◄──► [ Trips DB ]    ▼
    │          │                         [ Location Service ]
    │          ▼                          │            │
    ├──► [ Matching Service ] ◄───────────┘            ▼
    │          │                      [ Redis Geo index ]   [ Kafka ]
    │          ▼                                              │
    ├──► [ Pricing / Surge ]                   Trip events, location stream
    ├──► [ ETA / Maps Service ]                               │
    └──► [ Payment Service ]                                  ▼
                                      [ Notifications · Analytics · Location history ]

Offers and trip updates are pushed over WebSocket; push notification is the fallback

Component rationale

Realtime gateway (WebSocket)
Holds persistent connections to drivers and riders. Polling would cost millions of extra requests; a socket lets us push offers and positions instantly.
Location service + Redis geo index
Ingests GPS pings and keeps only each driver's latest position in memory, bucketed by map cell. Answers "who is nearby" in milliseconds.
Matching service
Finds candidates, ranks them by ETA and acceptance, offers the trip one by one and locks the winner so nobody is double-booked.
Trip service + Trips DB
Source of truth for the trip state machine. Low write volume but needs transactions and durability.
Pricing & ETA services
Pricing computes fare and surge per zone from recent demand and supply. ETA uses a road-graph routing engine with live traffic.
Kafka
Decouples the hot path from consumers: location history, analytics, surge calculation and notifications all read events asynchronously.

End-to-end data flow — "rider books a ride"

  1. Rider enters pickup and drop; Pricing and ETA return the fare and time per vehicle type.
  2. Rider confirms; Trip Service creates a trip in REQUESTED state with an idempotency key.
  3. Matching Service queries the geo index for available drivers near the pickup cell and neighbouring cells.
  4. Candidates are ranked by road ETA, rating and acceptance rate.
  5. The top driver is locked (SET driver:lock NX EX 15) and an offer is pushed over WebSocket.
  6. Driver accepts within the timeout: trip moves to ACCEPTED and the driver is marked busy. Otherwise release the lock and offer the next driver.
  7. Rider and driver exchange live positions through the realtime gateway until pickup, then through STARTED to COMPLETED.
  8. Payment Service charges the rider idempotently and emits receipt and rating events.

Core tables and keys

-- PostgreSQL (trips)
CREATE TABLE trips (
  trip_id      UUID PRIMARY KEY,
  rider_id     BIGINT NOT NULL,
  driver_id    BIGINT,
  status       TEXT NOT NULL,   -- REQUESTED | ACCEPTED | STARTED | COMPLETED | CANCELLED
  pickup_lat   DOUBLE PRECISION, pickup_lng DOUBLE PRECISION,
  drop_lat     DOUBLE PRECISION, drop_lng   DOUBLE PRECISION,
  fare_amount  NUMERIC(10,2),
  surge_mult   NUMERIC(3,2),
  idem_key     TEXT UNIQUE,     -- prevents duplicate bookings
  created_at   TIMESTAMP DEFAULT now()
);

-- Redis
Key:   cell:{h3_cell_id}          Value: SET of available driver_ids
Key:   driver:{id}                Value: HASH { lat, lng, status, cell, ts }   TTL 30s
Key:   driver_lock:{id}           Value: trip_id   TTL 15s (offer lock)

Sharding strategy

  • Locations — shard Redis by city or region; a driver only matters to riders in the same area.
  • Trips — shard by trip_id (or rider_id) for even spread; recent trips are hot, old ones archive out.
  • Payments — keyed by trip_id with a unique idempotency key so retries never double-charge.
  • Replicas — Redis replicas for failover; losing a few seconds of location data is harmless since drivers re-ping.
06 / Deep dives

Deep dive on 3 critical components

For each: the problem, the naive solution, why it fails, and the real solution used at scale. Volunteer these problems before the interviewer asks — it signals senior-level thinking.

01 Geospatial lookup — find nearby drivers in milliseconds

The problem: Given a pickup point, return the closest available drivers out of 1M moving points, thousands of times per second, while those points update every 4 seconds.

Naive solution — range query on latitude and longitude
SELECT * FROM drivers
WHERE lat BETWEEN ? AND ? AND lng BETWEEN ? AND ? AND status = 'AVAILABLE'

Why it fails: Two independent range filters on a B-tree scan huge slices of rows, and 250K writes/sec to an indexed table crush the database. Disk-based SQL cannot keep up with constantly moving points.

Real solution — grid cells in memory (geohash / H3 / quadtree)
1. Divide the map into cells (geohash or Uber's H3 hexagons).
   Cell id is computed from lat/lng in O(1).

2. Redis keeps: cell_id → SET of available driver_ids.
   On each GPS ping: if the cell changed, SREM old cell, SADD new cell;
   always overwrite driver:{id} with the latest position.

3. Search: compute the rider's cell, then read that cell plus
   its neighbour ring (k-ring). Expand the ring until enough
   candidates are found.

4. Rank candidates by real road ETA, not straight-line distance.

5. Alternative: Redis GEOADD / GEOSEARCH does the same out of the box
   for moderate scale; H3 gives uniform neighbours and is easier to shard.

Cell size trades accuracy for speed: ~1 km cells work well for cities.
Only the latest position is stored, so memory stays around 100 MB.
The key insight: turn a 2D distance search into a few O(1) set lookups by bucketing the map, and keep it all in memory because the data is ephemeral.
02 Matching — one driver, one rider, no double booking

The problem: Thousands of riders compete for the same nearby drivers at the same moment. A driver must receive one offer at a time and never end up on two trips.

Naive solution — broadcast to all and first accept wins
offer trip to 10 nearest drivers;  first accept → assign

Why it fails: Drivers get offers that vanish, fairness suffers, and two riders' broadcasts can overlap so one driver accepts both. Checking "is driver free" then writing "busy" is also a read-then-write race.

Real solution — ranked sequential offers with an atomic lock
1. Rank candidates by ETA, rating, acceptance rate.

2. For the top driver, atomically claim them:
     SET driver_lock:{id} {trip_id} NX EX 15
   NX fails if another trip already holds the driver → skip to the next one.

3. Push the offer over WebSocket; wait up to ~10-15s.
   Accept  → trip ACCEPTED, driver status BUSY, remove from cell set.
   Reject or timeout → DEL lock (only if the value matches), try next.

4. Trip state machine enforced in the database with a conditional update:
     UPDATE trips SET status='ACCEPTED', driver_id=? 
     WHERE trip_id=? AND status='REQUESTED'
   A second accept affects 0 rows, so it is safely rejected.

5. If nobody accepts after N attempts, widen the search radius,
   then tell the rider "no drivers available".

Sending offers to a small batch (2-3) at once speeds up matching
in dense areas; the lock still guarantees a single winner.
Strong consistency is needed only for assignment, not for location. Use a lock plus a conditional database update so that even a lock expiry or retry cannot produce two drivers on one trip.
03 Real-time location — streaming at 250K updates per second

The problem: Ingest a GPS ping from every driver every few seconds, keep the geo index fresh, and show the driver's car moving smoothly on the rider's map.

Naive solution — HTTP polling and database writes
driver: POST /location every 4s  →  UPDATE drivers SET lat, lng
rider:  GET /driver-location every 2s

Why it fails: Every call pays connection and auth overhead, rider polling multiplies the load, and a relational UPDATE per ping is thousands of times too slow. Most polls return unchanged data.

Real solution — WebSocket, memory-first writes, Kafka fan-out
1. Persistent WebSocket per driver and per active rider.
   Tiny binary payloads, no repeated handshakes.

2. Location Service writes latest position to Redis only
   (overwrite, TTL 30s so dead drivers vanish automatically).

3. Publish each ping to Kafka, partitioned by driver_id:
   history, analytics and surge consumers read it off the hot path.

4. Tracking: for a trip in progress, route driver pings to the rider's
   socket through a pub/sub topic trip:{id}. No polling.

5. Adaptive frequency: ping every 1-2s near pickup or turns,
   every 5-10s on straight roads or when idle. Client smooths
   positions between updates for fluid animation.

6. Reconnect handling: apps reconnect with backoff and jitter;
   push notifications are the fallback for offers and trip updates.

Losing a ping is harmless, the next one overwrites it. Skip durability
on the hot path and keep it only for history and trips.
Location data is high-volume but disposable. Treat it as a stream, not as records: memory for the present, Kafka for the past.
07 / Tradeoffs & alternatives

What we did NOT choose and why

Rejected alternatives

AlternativeWhy rejected
SQL lat/lng range queriesCannot sustain 250K moving-point writes/sec or millisecond proximity search.
HTTP polling for trackingWasteful and laggy; WebSockets push only when something changes.
Broadcast offer to all nearby driversRaces, wasted offers and unfair; sequential or small-batch offers with locks are cleaner.
Nearest by straight-line distanceIgnores rivers, one-way roads and traffic; road ETA picks better drivers.
Single global location storeDrivers only matter locally; per-city sharding cuts load and latency.
Storing every GPS ping in the trips DBOverloads the transactional store; history belongs in Kafka and a time-series or column store.
Strong consistency for locationsAdds cost for no benefit; a 4-second-old position is acceptable.

What breaks at 10× scale and how we fix it

Problem — Hot cells during surges

A stadium or airport exit creates thousands of requests on a handful of cells, overloading those Redis keys and the matching workers.

Fix

Use smaller cells in dense areas, batch requests per cell, and run matching in rounds (collect riders for a second, then assign globally) instead of first-come matching.

Problem — Payment failures and duplicate charges

Network retries or a payment gateway timeout could charge a rider twice or leave a completed trip unpaid.

Fix

Idempotency keys per trip, a ledger with a unique constraint, async retries through a queue, and reconciliation jobs against the gateway.

Problem — Realtime gateway node crashes

Thousands of drivers and riders lose their sockets at once and reconnect together.

Fix

Keep connection state stateless (trip and driver state lives in Redis and the DB), reconnect with jittered backoff, and let any gateway node resume a session.

Problem — Regional outage

A whole city's Redis or database region goes down, blocking new bookings.

Fix

Isolate cities as independent cells with their own stacks, replicate trips to a standby region, and let drivers repopulate the geo index within seconds of reconnecting.

08 / Summary

Cheat sheet

The ten things worth remembering before walking into the room.

Key numbers

20M rides/day · ~1K peak requests/sec · 1M drivers · ~250K GPS updates/sec · ~2M sockets · match < 5s

Key datastores

Redis (live geo index) · PostgreSQL (trips, payments) · Kafka (events) · Cassandra / S3 (location history)

Geo strategy

H3 or geohash cells; cell → driver set in Redis; search the cell plus neighbour ring; rank by road ETA.

Matching strategy

Ranked offers, Redis SET NX EX driver lock, conditional DB update for ACCEPTED.

Trip state machine

REQUESTED → ACCEPTED → STARTED → COMPLETED, or CANCELLED. Transitions are conditional updates.

Key tradeoffs

Consistency for assignment vs. eventual for location. Nearest vs. best ETA. Speed of match vs. fairness of batching.

Hardest part

Matching riders to drivers fast, without double booking, over a map that changes every few seconds.

Placement

WebSocket gateway for live traffic; stateless services behind it; everything sharded by city.

Sharding keys

Locations → city / H3 region · Trips → trip_id · Kafka → driver_id · Payments → trip_id
