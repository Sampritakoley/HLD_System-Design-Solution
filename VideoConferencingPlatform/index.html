01 / Understanding the problem

What is this system, really?

A video conferencing platform lets people in different places see, hear and share screens with each other in real time. Think of it as a giant switchboard: every participant sends their media up, and the system forwards it to everyone else within a fraction of a second.

The core challenge: unlike video streaming, nothing can be pre-computed or cached. Media is live, latency must stay under ~200 ms, and every stream fans out to many viewers. Real-time packet routing, not storage, is the bottleneck.

Core features in scope

Meetings

Create, schedule and join a meeting by link or ID, with a waiting room and host controls.

Audio & video

Two-way real-time audio and video with gallery and active-speaker layouts.

Screen share & chat

Share a screen at readable quality, send in-meeting chat and reactions.

Recording

Cloud recording with transcript, available shortly after the meeting ends.

What makes this hard at scale

  • Hard real-time. Audio delayed beyond ~200 ms ruins conversation; late packets are useless.
  • No caching. Live media cannot sit on a CDN; every packet is routed on the fly.
  • Fan-out. With N participants, each stream must reach N-1 others, so traffic grows quadratically if designed naively.
  • Unreliable networks. Participants on WiFi, 4G and office LANs suffer loss, jitter and changing bandwidth.
  • Firewalls and NAT. Most clients cannot accept direct inbound connections.
02 / Requirements

Functional vs. non-functional requirements

Non-functional requirements are what actually drive architecture decisions — they're listed first for a reason.

Functional

  • Schedule, start and join meetings via link
  • Real-time audio and video for up to 100–1000 participants
  • Screen sharing
  • In-meeting chat, mute, raise hand, reactions
  • Host controls: waiting room, remove, mute all
  • Cloud recording and transcripts
  • Works on web, mobile and desktop

Non-functional

  • 300M daily participants, ~30M concurrent at peak
  • End-to-end media latency < 200 ms (p95)
  • Join a meeting in < 3 seconds
  • 99.99% availability for live meetings
  • Audio prioritised over video under bad networks
  • Graceful degradation, not call drops
  • Encryption in transit; optional end-to-end
  • Recordings never lost once a meeting ends

Clarifying questions

Typical and maximum meeting size? 1:1 and 1000-person meetings need different designs.
Webinar mode (few speakers, many viewers) in scope, or only interactive meetings?
Is end-to-end encryption required? It blocks server-side recording and transcoding.
Which devices and what maximum resolution (720p, 1080p)?
Global audience? This decides how many media regions we need.
Cloud recording and live transcription required, or client-side only?
03 / Estimation

Back-of-envelope math

Order-of-magnitude accuracy is the goal here, not precision. Every assumption is stated explicitly.

~30MPeak concurrent participants
~50 TbpsPeak media egress
~0.7 PB/dayRecordings

Assumptions

Daily participants      = 300M, average meeting 40 min, average size 6
Meetings per day        = 300M / 6 = ~50M
Peak concurrent         = ~30M participants ≈ ~5M live meetings
Upload per client       = ~1.5 Mbps (audio 50 kbps + simulcast video layers)
Download per client     = ~1.5 Mbps (a few forwarded streams)
Recorded meetings       = 3% → 1.5M/day, ~0.45 GB each
Metadata per meeting    = ~2 KB

QPS

Meeting joins:
  300M / 86,400                = ~3.5K/sec avg → ~20K/sec peak (top of the hour)

Media packets:
  30M clients × ~100 pkts/sec  = ~3B packets/sec in, similar out

Signaling messages (mute, chat, hand raise, etc.):
  ~10x joins                   = ~200K/sec peak

Metadata QPS is small. The real load is packets per second: media
servers must be stateless-ish, UDP-based, and horizontally scaled.

Storage

Recordings:
  1.5M × 0.45 GB               = ~0.7 PB/day → ~250 PB/year

Transcripts + chat:
  1.5M × ~1 MB                 = ~1.5 TB/day (small)

Metadata:
  50M × 2 KB                   = ~100 GB/day

Live media is never stored. Only recordings persist, and they can
move to cold storage after 30-90 days.

Bandwidth & connections

Ingress                  = 30M × 1.5 Mbps ≈ ~45 Tbps
Egress                   = 30M × 1.5 Mbps ≈ ~45-50 Tbps
Media servers (SFU)      = ~5 Gbps usable per node → ~10K nodes at peak
Signaling connections    = 30M persistent WebSockets

Unlike video-on-demand there is no 95% cache hit rate to save us.
Ingress ≈ egress, so cost control means many regions and efficient forwarding.
04 / High-level design

Architecture

Built top-down from the client. Every box exists because of a number from Step 3. Control plane (signaling) and media plane (audio/video packets) are kept separate.

CLIENT A (web / mobile / desktop)                CLIENT B ... CLIENT N
   │ HTTPS + WebSocket (signaling)                    │
   │ UDP / SRTP (media)                               │
   ▼                                                  ▼
[ API Gateway / LB ] ──► [ Meeting Service ] ◄──► [ Meeting DB + Redis ]
   │                          │ picks region + SFU
   ├──► [ Signaling Servers (WebSocket) ] ◄──► [ Redis pub/sub: room state ]
   │
   │      ┌────────── MEDIA REGION ──────────┐
   └─────►│ [ TURN / STUN ]  [ SFU cluster ] │◄──── UDP media from clients
          │       │               │          │
          │       │      SFU ↔ SFU cascade   │──► other regions
          └───────┼───────────────┼──────────┘
                  │               ▼
                  │         [ Kafka ] ──► [ Recording Workers ] ──► [ Object store ]
                  │               │                                     │
                  │               └──► [ Transcription / Moderation ]   ▼
                  ▼                                          [ Metadata / Playback ]
            [ Chat Service ] ──► [ Cassandra ]

Media goes client → SFU → clients over UDP. App servers never touch media packets

Component rationale

Meeting service
Creates meetings, validates passwords and waiting-room rules, and assigns each meeting to the nearest healthy media region and SFU. Owns the meeting lifecycle.
Signaling servers (WebSocket)
Carry join/leave, SDP offer/answer, ICE candidates, mute and chat events. Low bandwidth but long-lived connections; room state is shared through Redis pub/sub.
SFU (Selective Forwarding Unit)
Receives each participant's stream once and forwards selected streams to others without decoding. Far cheaper than an MCU and avoids the N² mesh.
STUN / TURN
STUN helps clients discover their public address; TURN relays media for clients behind strict NATs or firewalls (TCP/443 fallback).
Recording & transcription workers
Join the meeting as a silent participant, mix or compose streams asynchronously, and write the file to object storage. Off the live path.
Chat service + metadata stores
Chat is append-heavy and lives in Cassandra. Meeting metadata sits in sharded SQL with a Redis cache.

End-to-end data flow — "host starts, participant joins"

  1. Host creates a meeting; Meeting Service stores it and returns a link with a meeting ID.
  2. A participant opens the link, authenticates, and the Meeting Service picks a region (by latency) and an SFU.
  3. Client opens a WebSocket to signaling and exchanges SDP offer/answer and ICE candidates.
  4. Client establishes a UDP path to the SFU (direct, via STUN, or relayed by TURN) with DTLS-SRTP encryption.
  5. Client uploads its audio and simulcast video layers once to the SFU.
  6. The SFU forwards the right layer of each speaker to every other participant based on their bandwidth and layout.
  7. Mute, hand raise and chat events flow through signaling and Redis pub/sub to everyone in the room.
  8. On end, recording workers finalise the file, store it, and metadata marks the recording READY.
05 / Database design

Storage layer

Live media lives only in memory on SFUs. Persistent stores hold meeting metadata, chat and recordings — each matched to its access pattern.

DataStoreWhy
Meetings, users, schedulesMySQL / PostgreSQL (sharded) + RedisRelations, transactions, read-heavy
Live room state (participants, SFU)Redis (+ pub/sub)Fast, ephemeral, TTL-based
Chat messagesCassandraAppend-heavy, keyed by meeting
Recordings and transcriptsObject storage (S3 / GCS)Cheap, durable, tiered
Quality and usage eventsKafka → columnar analytics storeHigh-volume, analysed offline

Core tables and keys

-- PostgreSQL / MySQL (meetings)
CREATE TABLE meetings (
  meeting_id   BIGINT PRIMARY KEY,       -- snowflake id (shown as 10-11 digit code)
  host_id      BIGINT NOT NULL,
  title        TEXT,
  status       TEXT NOT NULL,            -- SCHEDULED | LIVE | ENDED
  region       TEXT,                     -- media region currently hosting
  sfu_id       TEXT,                     -- assigned SFU node
  passcode     TEXT,
  start_time   TIMESTAMP,
  created_at   TIMESTAMP DEFAULT now()
);

-- Cassandra
chat:   PK ((meeting_id), sent_at, message_id)

-- Redis
Key: room:{meeting_id}     Value: HASH { sfu_id, region, host, locked }       TTL while LIVE
Key: participants:{id}     Value: SET of user_id / connection ids

Sharding strategy

  • Meetings — shard by meeting_id; all lookups are by ID.
  • Chat — partition by meeting_id so a meeting's chat reads from one partition.
  • Room state — Redis cluster keyed by meeting_id; the same key routes signaling to the right room.
  • Recordings — keyed by meeting_id and segment, stored in the recording's home region.
06 / Deep dives

Deep dive on 3 critical components

For each: the problem, the naive solution, why it fails, and the real solution used at scale. Volunteer these problems before the interviewer asks — it signals senior-level thinking.

01 Media routing — P2P vs MCU vs SFU

The problem: Deliver every participant's audio and video to everyone else in under 200 ms without melting client uplinks or server CPUs.

Naive solution — full-mesh peer-to-peer
Each client sends its stream directly to every other client: N × (N-1) streams

Why it fails: With 10 people each client uploads 9 copies of its video. Phones and home uplinks collapse, batteries drain, and NAT traversal fails for many pairs. It only works for 1:1 calls.

Real solution — SFU with simulcast
1. Each client uploads ONE set of streams to the SFU: audio plus 3 video
   layers (simulcast): 180p, 360p, 720p.

2. The SFU does not decode or re-encode. It just forwards RTP packets,
   choosing per receiver which layer to send:
     active speaker      → 720p
     gallery thumbnails  → 180p
     off-screen tiles    → paused

3. Client uplink stays constant, regardless of meeting size.
   Server cost is forwarding, which is cheap (packets/sec, not CPU-heavy).

4. Audio: forward only the top ~3 loudest speakers to cap bandwidth.

5. Screen share is an extra stream forwarded at high resolution, low fps.

6. MCU alternative: mixes all streams into one composite. Low client
   bandwidth, but very high server CPU and added latency. Used only for
   legacy rooms and recording.

Rule of thumb: P2P for 1:1, SFU for groups, MCU only for
recording or legacy SIP/H.323 endpoints.
The key insight: upload once, let the server forward selectively. The SFU trades a little server bandwidth for constant client cost and low latency.
02 Real-time transport — staying smooth on bad networks

The problem: Keep latency under 200 ms while participants suffer packet loss, jitter and sudden bandwidth drops.

Naive solution — stream over TCP with big buffers
Video over TCP/HTTP with a few seconds of buffering, like on-demand streaming

Why it fails: TCP retransmits lost packets and blocks everything behind them (head-of-line blocking), adding seconds of delay. Big buffers make conversation impossible because people talk over each other.

Real solution — WebRTC over UDP with adaptive control
1. Media uses SRTP over UDP. A late packet is dropped, never waited for.

2. Bandwidth estimation (Google Congestion Control / transport-wide feedback)
   measures delay and loss continuously and tells the sender how much it
   can push.

3. Loss recovery, in order of cost:
     NACK       → retransmit only if there is time before playout
     FEC        → redundant packets, especially for audio (e.g. Opus in-band)
     PLI / FIR  → request a keyframe when a video frame is unrecoverable

4. Adaptive jitter buffer on receiver: ~40-100 ms, grows under jitter.

5. Degrade in this order as the network worsens:
     drop video layer → lower frame rate → turn video off → keep audio.
   Audio is always protected.

6. Connectivity: ICE tries direct UDP, then STUN-derived, then TURN/UDP,
   then TURN over TCP/TLS on port 443 to get through strict firewalls.

7. Place SFUs at the edge (many regions) and route by lowest RTT so the
   first hop is short.

Each region's SFU also reports loss, jitter and RTT per call,
so bad routes and overloaded nodes are detected in seconds.
The key insight: in real-time media, late equals lost. Use UDP, adapt the bitrate continuously, and sacrifice video quality before audio continuity.
03 Meeting state & scale-out — placement, cascading, failover

The problem: Route each meeting to an SFU, scale to 1000-person meetings that exceed one node, and survive node failures without ending calls.

Naive solution — random SFU per participant, one server per meeting forever
Participant joins → load balancer picks any SFU
Whole meeting pinned to one SFU until it ends

Why it fails: Participants of the same meeting land on different SFUs that cannot exchange media. A pinned SFU caps meeting size, adds latency for distant attendees, and its crash kills the meeting.

Real solution — meeting-aware placement + cascaded SFUs
1. Meeting Service assigns a meeting to an SFU in the region closest to the
   first joiner, stored in Redis as room:{id} → sfu_id.

2. Later joiners are routed to the SFU for their own nearest region. SFUs
   connect to each other and forward streams once per link (cascading):
     India SFU ⇄ US SFU: one copy of each speaker's stream, not one per viewer.

3. Large meetings: SFUs form a tree. Each leaf serves a few hundred viewers.
   Webinar mode: only speakers publish, viewers receive-only and can also
   use HLS with a few seconds of delay at 10K+ scale.

4. Capacity-aware placement: pick the SFU by CPU, NIC bandwidth and number
   of streams, not just round-robin.

5. Failover: heartbeats detect a dead SFU within seconds. Clients get a
   "reconnect" signal, re-run ICE to a replacement SFU, and the stream
   resumes. Room state in Redis survives because it is not on the SFU.

6. Signaling is sharded by meeting_id; Redis pub/sub fans room events out
   to all signaling nodes holding that meeting's WebSockets.

Media servers are soft-state: the only truth is the meeting
record and Redis. Replacing one mid-call costs a brief glitch, not the call.
Meeting records need strong consistency (who is host, is it locked). Presence and reactions can be eventually consistent. Keep media and control planes separate so a signaling blip never drops audio.
07 / Tradeoffs & alternatives

What we did NOT choose and why

Rejected alternatives

AlternativeWhy rejected
Full-mesh P2P for groupsUplink grows with N; fails NATs and mobile devices beyond a handful of users.
MCU (server mixes all streams)Decoding and re-encoding per meeting is very expensive and adds latency; kept for recording only.
Media over TCP / HTTP streamingHead-of-line blocking and buffering break real-time conversation.
CDN for live interactive mediaAdds seconds of delay; fine for webinar viewers, wrong for participants.
Media through app serversNot built for millions of UDP packets/sec; dedicated SFUs scale far better.
Recording via client uploadUnreliable and depends on the host's device; server-side recorder is consistent.
Always-on end-to-end encryptionBlocks cloud recording, transcription and server-side layer selection; offered as opt-in.

What breaks at 10× scale and how we fix it

Problem — Top-of-the-hour join storm

Millions join at 9:00 AM sharp; the Meeting Service and SFUs see a sudden spike in joins.

Fix

Pre-warm SFU capacity before common start times, autoscale on join rate, rate-limit with queued retries, and cache meeting lookups in Redis.

Problem — Huge single meeting or webinar

One event with tens of thousands of viewers exceeds any single SFU.

Fix

Cascaded SFU tree for interactive attendees, receive-only viewer tiers, and an HLS/CDN path for very large audiences who do not need sub-second latency.

Problem — Bandwidth cost explosion

Ingress and egress are both ~50 Tbps with no cache to absorb it.

Fix

Forward only needed layers, pause off-screen video, cap audio to top speakers, use efficient codecs (Opus, VP9/AV1 where CPU allows), and peer directly with ISPs and cloud backbones.

Problem — Regional outage

A media region or its network goes down mid-call.

Fix

Keep room state outside SFUs, detect failure by heartbeat, reassign the meeting to the next-nearest region, and let clients auto-reconnect via signaling within seconds.

08 / Summary

Cheat sheet

The ten things worth remembering before walking into the room.

Key numbers

300M daily participants · ~30M concurrent · ~20K peak joins/sec · ~50 Tbps in and out · <200 ms latency · ~0.7 PB/day recordings

Key datastores

PostgreSQL/MySQL + Redis (meetings, room state) · Cassandra (chat) · Object storage (recordings) · Kafka (events, recording jobs)

Media strategy

WebRTC over UDP; SFU forwards simulcast layers; clients upload once regardless of meeting size.

Connectivity strategy

ICE: direct → STUN → TURN/UDP → TURN/TCP 443. DTLS-SRTP encryption on every hop.

Scale-out strategy

Region-aware placement, cascaded SFUs, capacity-aware assignment, HLS for huge webinars.

Meeting state machine

SCHEDULED → LIVE → ENDED. Status and host changes are conditional updates on the meeting record.

Key tradeoffs

Latency vs quality. SFU vs MCU cost. E2EE vs recording and transcription. Regions count vs ops cost.

Hardest part

Keeping sub-200 ms media flowing over unpredictable networks while fanning out at 50 Tbps with no caching.

Sharding keys

Meetings → meeting_id · Chat → meeting_id · Room state → meeting_id · Recordings → meeting_id + segment
