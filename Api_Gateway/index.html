01 / Understanding the problem

What is an API gateway, really?

An API gateway is the single front door to a fleet of backend services. It terminates TLS, authenticates callers, enforces limits, routes each request to the right service and reports what happened. Every request pays its latency tax, so it must be fast and almost never down.

The core challenge: it sits on the critical path of everything. A slow gateway slows the whole product, and a crashed gateway is a full outage. Yet it must also be configurable by hundreds of teams without redeploys.

Core features in scope

Routing

Map host, path and method to an upstream service, with versioning, rewrites and weighted canary splits.

Authentication

Validate API keys, JWTs and OAuth tokens once at the edge, then pass trusted identity downstream.

Rate limiting

Per-client, per-API and global quotas that protect backends and enforce fair use.

Resilience & observability

Timeouts, retries, circuit breakers, plus logs, metrics and trace IDs for every call.

What makes this hard at scale

  • Latency budget. The gateway may add only a few milliseconds at p99, with auth and limits included.
  • Distributed counters. A limit of 100 req/s must hold across 30 gateway nodes, without a network hop per request.
  • Config propagation. A route change must reach every node in seconds, safely, with no restarts.
  • Cascading failure. One slow upstream can eat every worker thread and take down unrelated APIs.
  • Single point of failure. Everything flows through it, so it must be stateless, replicated and fail-safe.
02 / Requirements

Functional vs. non-functional requirements

Non-functional requirements drive the architecture, so they get the most attention.

Functional

  • Route by host, path, method and headers
  • Authenticate API keys, JWT and OAuth
  • Rate limit and quota per client and API
  • Request and response transformation
  • Load balancing and health checks
  • Retries, timeouts, circuit breaking
  • Logging, metrics and distributed tracing
  • Admin API to manage routes and policies

Non-functional

  • 1M requests/sec at peak, ~500 services
  • Added latency under 10 ms at p99
  • 99.99% availability, no single point of failure
  • Stateless nodes that scale horizontally
  • Config changes live in under 5 seconds
  • Rate limits accurate within a few percent
  • Failure isolation between tenants and APIs
  • Secure by default: TLS, no secret leakage

Clarifying questions

Is this for external public traffic, internal service-to-service, or both?
Which protocols: REST only, or also gRPC, WebSocket and GraphQL?
Are limits per user, per API key, per IP, or per tenant? Is exact accuracy required?
Single region or multi-region active-active?
Should the gateway cache responses, or only route?
Build custom, or run on Envoy, Kong or NGINX? This sets how much we design from scratch.
03 / Estimation

Back-of-envelope math

Order-of-magnitude accuracy is enough. Every assumption is explicit.

~1M/sPeak requests
~1M/sRate limit checks
~25-75Gateway nodes

Assumptions

Peak traffic            = 1M req/sec (average ~300K/sec)
Avg request + response  = ~2 KB request, ~10 KB response
One node (8 vCPU)       = ~40K req/sec with TLS + auth + limits
Config size             = 500 services × 20 routes ≈ 10K routes, a few MB
Access log line         = ~500 bytes

QPS and capacity

Nodes needed:
  1M / 40K                     = 25 nodes, ×2-3 headroom = ~50-75 nodes

Rate limit checks:
  Every request checks a counter = 1M/sec
  Central Redis at 100K ops/sec per shard = ~10 shards
  Better: local token buckets + periodic sync cuts remote calls ~100×

Auth:
  JWT verified locally (signature + expiry) = no network call
  API keys cached in-process, 99%+ hit rate

Bandwidth and logs

Ingress   = 1M × 2 KB   = ~2 GB/s
Egress    = 1M × 10 KB  = ~10 GB/s  (CDN and compression absorb a lot)
Logs      = 1M × 500 B  = 500 MB/s ≈ 43 TB/day → sample 1-10%, always keep errors

The constraints are per-request CPU, TLS handshakes and connection counts,
not storage. Keep the hot path free of remote calls.

Component rationale

L4 load balancerSpreads TCP connections over gateway nodes with no request parsing. Cheap, fast, and removes the single entry point.
Gateway node (data plane)Stateless proxy running a filter chain. All hot-path data (routes, keys, public keys, limits) lives in local memory.
Control plane + Config DBTeams change routes and policies through an Admin API. Validated config is versioned and pushed to nodes, never read per request.
Redis clusterShared counters for rate limits and quotas, sharded by client key, used asynchronously where possible.
Service discoveryTracks healthy upstream instances so routing follows autoscaling and deploys without manual changes.
KafkaAccess logs, metrics and traces are emitted asynchronously so observability never blocks the request.

End-to-end flow: "client calls GET /v2/orders/42"

  1. DNS routes the client to the nearest region; the L4 load balancer picks a gateway node.
  2. The node terminates TLS and assigns a request-id and trace context.
  3. Auth filter verifies the JWT locally, or looks up the API key in its cache, and attaches identity headers.
  4. Rate limit filter takes a token from the local bucket for this client and API; over limit returns 429 with Retry-After.
  5. Router matches host, path and method in an in-memory trie and finds the orders upstream.
  6. Load balancer picks a healthy instance (least requests or power of two choices); the circuit breaker is checked.
  7. Request is proxied with a timeout; idempotent failures retry once on another instance.
  8. Response returns to the client; an access log and metrics are emitted asynchronously.

Storage layer

The gateway owns very little data. What it does own is config, counters and logs, each with a different home.

Config model and keys

-- PostgreSQL (control plane)
CREATE TABLE routes (
  route_id     UUID PRIMARY KEY,
  host         TEXT NOT NULL,
  path_prefix  TEXT NOT NULL,
  methods      TEXT[],
  upstream     TEXT NOT NULL,       -- service name
  auth_policy  TEXT,                -- NONE | API_KEY | JWT | OAUTH
  rate_policy  TEXT,
  timeout_ms   INT DEFAULT 3000,
  version      BIGINT NOT NULL,     -- monotonic config version
  UNIQUE (host, path_prefix)
);

-- Redis
Key:  rl:{client_id}:{api}:{window}   Value: counter        TTL = window
Key:  rl:tb:{client_id}:{api}         Value: HASH { tokens, ts }

Scaling strategy

  • Gateway nodes: stateless, autoscaled on CPU and connection count, spread over zones.
  • Redis: shard by client_id, replicas for failover; on failure, fall back to local limits.
  • Config: versioned snapshots pushed to nodes; each node acknowledges the version it runs.
  • Regions: one gateway fleet per region, global DNS routing, config replicated across regions.
06 / Deep dives

Deep dive on 3 critical components

For each: the problem, the naive solution, why it fails, and what is used at scale. Raise these before the interviewer asks.

01 Distributed rate limiting — accurate limits without a network hop per request

The problem: A client may make 100 requests/sec. Requests hit any of 50 nodes, so the limit must be shared, yet checking a central store 1M times per second adds latency and risk.

Naive solution: per-node counters, or one central Redis call per request
limit per node = 100 / 50 nodes      (uneven traffic breaks it)
INCR rl:{client}  on every request   (1M Redis ops/sec, +1-2 ms each)

Why it fails: Local-only counters are wrong when load balancing is uneven, and a fixed window allows a 2× burst at the boundary. A remote call per request puts Redis on the critical path, so a Redis blip becomes a gateway outage.

Real solution — token bucket with local batching and async sync
1. Algorithm: token bucket. Refill rate = limit, capacity = burst.
   Allows bursts, smooth over time, O(1) state per client.

2. Each node holds a local bucket and requests a "lease" of tokens
   from Redis (e.g. 10% of the limit) with an atomic Lua script:
     tokens = min(cap, tokens + elapsed*rate); grant = min(want, tokens)

3. Requests consume local tokens with no network call. When the
   lease runs low, refill asynchronously before it hits zero.

4. Accuracy trades against cost: bigger leases = fewer calls but
   more over-admission. Typically within a few percent.

5. Redis down? Fail open with conservative local limits for
   most APIs; fail closed for abuse-sensitive ones (login, OTP).

6. Return headers: X-RateLimit-Limit, -Remaining, Retry-After.

Sliding window counter (current + weighted previous window)
is a good alternative when you need smoother fairness than fixed windows.
The key insight: rate limiting is approximate by design. Spend accuracy only where it matters, and keep the remote store off the per-request path.
02 Auth and routing — decide fast, change safely

The problem: Every request needs identity verified and a destination chosen in well under a millisecond, while hundreds of teams change routes and keys at any time.

Naive solution — call the auth service and config DB per request
request → POST /auth/verify → SELECT * FROM routes WHERE path LIKE ... → proxy

Why it fails: Two network hops and a database query on the hot path add tens of milliseconds, and the auth service and DB become single points of failure at 1M req/sec. Linear or regex scans over 10K routes are slow too.

Real solution — local verification, in-memory route table, versioned config push
1. JWT: verify signature with cached public keys (JWKS), check exp,
   aud and scopes locally. No network call. Rotate keys by kid.

2. API keys: store only a hash. Cache key → client in an LRU with a
   short TTL (30-60s). A miss goes to the auth service once, then
   is cached, including negative results to stop key guessing.

3. Revocation: short token lifetimes plus a small pushed deny-list
   for emergency revokes. Cached keys expire within seconds.

4. Routing: compile routes into a radix trie keyed by host, then
   path segments. Lookup is O(path length), independent of route count.

5. Config propagation: control plane validates, versions and
   publishes a snapshot. Nodes watch (etcd / xDS), build the new
   table off to the side, then atomically swap the pointer.
   Bad config? Reject it, keep the last good version.

6. Roll out routing changes gradually: canary by weight
   (1% → 10% → 100%) with automatic rollback on error rate.

Validate with a dry run before publish: no duplicate paths,
upstream exists, timeouts sane, regexes safe from backtracking.
Treat gateway config like code: versioned, validated, canaried and instantly reversible. A bad route push can cause a bigger outage than a bad deploy.
03 Resilience — stop one slow service from taking everything down

The problem: One upstream starts responding in 30 seconds. Requests pile up, workers and connections are exhausted, and unrelated APIs through the same gateway start failing too.

Naive solution — shared worker pool, no timeouts, retry everything
proxy_pass upstream;      # default timeouts, unlimited retries, one shared pool

Why it fails: Slow calls hold resources, so capacity drains. Aggressive retries multiply load on an already struggling service (a retry storm) and turn a brownout into an outage.

Real solution — timeouts, budgets, breakers and bulkheads
1. Timeouts everywhere: connect (~100 ms), per-try and overall
   deadline per route. Propagate the remaining deadline downstream.

2. Retries only for idempotent calls, max 1-2, with jittered backoff
   and a retry budget (e.g. retries ≤ 10% of base traffic).

3. Circuit breaker per upstream: closed → open when error rate or
   latency passes a threshold → half-open probes → closed again.
   Open circuit fails fast (503) instead of waiting.

4. Bulkheads: cap concurrent connections per upstream, so one bad
   service cannot use the whole pool.

5. Outlier detection: eject instances with repeated failures from the
   load-balancing pool for a cool-off period. Active health checks too.

6. Load shedding: when the gateway itself is saturated, drop low
   priority traffic early with 503 and keep critical paths alive.

7. Graceful degradation: serve stale cached responses for safe GETs
   when the upstream is down.

Use power-of-two-choices or least-request load balancing, not
plain round robin, so slow instances naturally receive less traffic.
Fail fast and fail small. A rejected request costs microseconds; a hanging request costs a worker, a connection and everyone else’s latency.
07 / Tradeoffs & alternatives

What we did NOT choose and why

Rejected alternatives

AlternativeWhy rejected
Auth service call per requestAdds a network hop and a dependency to every call; local JWT verification is far cheaper.
Central counter for every rate limit checkPuts Redis on the critical path; local buckets with leases keep it off.
Fixed-window countersAllow 2× bursts at window edges; token bucket or sliding window is smoother.
Reading config from the DB per requestToo slow and fragile; in-memory snapshots with push updates are standard.
One shared gateway for all traffic typesNoisy neighbours; separate public, partner and internal gateways isolate failures.
Business logic inside the gatewayBecomes a deployment bottleneck; keep it to cross-cutting concerns only.
Sticky sessions at the gatewayHurts balancing and failover; keep services stateless instead.

What breaks at 10× scale and how we fix it

Problem: DDoS or a single abusive client

A flood of requests saturates nodes before limits can help, and attackers rotate API keys and IPs.

Fix

Absorb at the edge with CDN and WAF, apply cheap IP and connection limits before auth, add per-tenant quotas, and use autoscaling plus load shedding as the last line.

Problem: TLS handshake storms

After a node restart or deploy, thousands of clients reconnect at once and CPU spikes on handshakes.

Fix

Session resumption and TLS 1.3, long-lived HTTP/2 connections, connection draining on deploys, and terminating TLS at the L4 or edge tier with hardware offload when needed.

Problem: Control plane outage or bad config push

Admins cannot change routes, or a faulty config reaches every node at once.

Fix

Nodes run on the last good snapshot, so the control plane is off the request path. Staged rollout by node group, schema and dry-run validation, one-click rollback to a previous version.

Problem: Regional outage

An entire region’s gateway fleet or Redis becomes unavailable.

Fix

Active-active regions behind global DNS with health-based failover, independent Redis per region (limits become per-region approximations), and config replicated across regions.

08 / Summary

Cheat sheet

The things worth remembering before walking into the room.

Key numbers

1M req/sec · ~40K/sec per node · 50-75 nodes · <10 ms p99 overhead · config live in <5s · 99.99%

Key components

L4 LB · stateless gateway nodes · control plane + config DB · Redis · service discovery · Kafka

Request pipeline

TLS → auth → rate limit → route → transform → load balance → proxy → async logging

Rate limiting

Token bucket, local leases from Redis via Lua, async refill, fail open or closed per API.

Auth

Local JWT verify with cached JWKS, hashed API keys in an LRU, short TTLs plus a deny-list.

Routing

Radix trie in memory, atomic snapshot swap, canary weights, last-known-good fallback.

Resilience

Timeouts, retry budgets, circuit breakers, bulkheads, outlier ejection, load shedding.

Key tradeoffs

Accuracy vs latency in limits · fail open vs closed · central vs per-team gateways · features vs added latency.

Hardest part

Staying on the critical path of all traffic with near-zero latency and near-perfect availability.
