01 / Understanding the problem

What is this system, really?

A centralized logging system collects log lines from thousands of services and machines, stores them durably and cheaply, and lets engineers search them and get alerted within seconds. It is what you open at 3 a.m. when production breaks.

The core tension: writes are enormous and constant, while reads are rare but urgent and must be fast. The system must never lose logs during an incident, which is exactly when log volume spikes.

Core features in scope

Collection

Agents on every host and sidecars collect logs from files, stdout and SDKs.

Search & filter

Full-text and field queries over a time range, by service, level, trace id.

Alerting

Rules such as “error rate > 5% for 5 minutes” notify on-call near real time.

Retention & access

Tiered retention, multi-tenant access control, export and audit.

What makes this hard at scale

  • Write firehose. Millions of events per second, with spikes during outages.
  • Storage cost. Tens of terabytes per day; indexing everything is far too expensive.
  • Query latency. Search over terabytes in seconds, for needle-in-haystack queries.
  • Reliability under stress. The logging pipeline must survive the incidents it reports.
  • Noisy neighbours. One chatty service can drown out everyone else.
02 / Requirements

Functional vs. non-functional requirements

Non-functional requirements drive the architecture, so they come first.

Functional

  • Ingest logs from many sources and formats
  • Search by text, fields, time range and service
  • Live tail of a service’s logs
  • Dashboards and aggregations (counts, rates)
  • Alert rules with notifications
  • Retention policies and archiving
  • Multi-tenant access control
  • Mask sensitive data (PII, secrets)

Non-functional

  • 1M events/sec average, 3M/sec peak, ~43 TB/day
  • Searchable within ~5-10 seconds of emit
  • Query p95 < 5 s for recent data
  • High durability; at-least-once delivery
  • 99.9%+ availability for ingestion
  • Never block the application on logging
  • Cost-efficient: tiered hot, warm, cold
  • Scales horizontally

Clarifying questions

Is this for application logs only, or also metrics and traces?
How long must logs be searchable, and how long archived (compliance)?
Is losing a small fraction of logs acceptable, or are some (audit) logs lossless?
Do we need full-text search, or mostly filtering by labels plus grep?
Multi-tenant with per-team quotas, or one shared company?
03 / Estimation

Back-of-envelope math

Order-of-magnitude accuracy, with every assumption stated.

~1M/sLog events (3M/s peak)
~500 MB/sIngest bandwidth
~43 TB/dayRaw volume

Assumptions

Instances emitting logs = ~100K (across ~10K services)
Events per instance     = ~10/sec average → 1M/sec total
Average log line        = ~500 bytes
Peak factor             = ~3x during incidents
Compression             = ~8-10x for text logs
Search load             = ~500 queries/sec peak (engineers, dashboards, alerts)

Throughput

Events:    1M/sec avg → ~3M/sec peak
Bandwidth: 1M × 500 B = ~500 MB/s avg → ~1.5 GB/s peak
Kafka:     at ~50 MB/s per partition → ~30-60 partitions minimum,
           use hundreds for headroom and parallel consumers

Writes dominate by orders of magnitude. Design for append-only,
sequential writes and batching.

Storage

Raw per day:          500 MB/s × 86,400 = ~43 TB/day
Compressed (~10x):    ~4.3 TB/day
Hot (7 days, indexed): ~4.3 TB × 7 ≈ 30 TB + index overhead (~2x) = ~60 TB
Warm (30 days):        ~130 TB compressed on cheaper disks
Cold (1 year, S3):     ~1.6 PB compressed, object storage

Cost is the real constraint: tiering and not indexing every
field cut it by an order of magnitude.
04 / High-level design

Architecture

Every box exists because of a number from Step 3.

 APPS / HOSTS / CONTAINERS
   │  stdout, files, SDK
 [ Log Agent / Sidecar ]  buffer · batch · compress · retry
   │
 [ Ingest Gateway ]  auth · tenant quota · rate limit
   │
 [ Kafka ]  topics partitioned by tenant/service  ← durable buffer
   │
 ├─► [ Stream Processor ]  parse · enrich · mask PII · route
 │         │
 │         ├─► [ Indexer ] ─► [ Hot store: search index ]  (7 days)
 │         ├─► [ Archiver ] ─► [ Object store S3 ]          (warm/cold, Parquet)
 │         └─► [ Alert Engine ] ─► Notifications (PagerDuty / Slack)
 │
 └─► [ Query Service ] ─► hot index + S3 · cache · UI / API / dashboards

Kafka decouples bursty producers from slower storage, so spikes never reach the databases

Component rationale

Log agent / sidecar
Reads logs locally, buffers on disk, batches and compresses, then ships. Keeps the app independent of logging availability.
Ingest gateway
Authenticates sources, enforces per-tenant quotas and applies backpressure. Prevents one noisy service from hurting others.
Kafka
Durable, ordered, replayable buffer that absorbs 3× spikes and lets multiple consumers read the same stream independently.
Stream processor
Parses raw lines into structured fields, adds metadata (host, service, trace id), masks secrets, and routes to the right sinks.
Hot store (search index)
Elasticsearch/OpenSearch or ClickHouse for the last days: fast queries and aggregations on recent data.
Object store archive
Compressed columnar files in S3 for cheap long retention, queried on demand by a query engine.
Alert engine
Evaluates rules on the live stream (not by polling the database) for near-real-time notifications.

End-to-end flow — "a service logs an error and someone searches it"

  1. The app writes a log line to stdout; the local agent tails it, adds host and service labels, and batches lines.
  2. The agent compresses the batch and sends it to the Ingest Gateway; if the network fails it retries from its disk buffer.
  3. The gateway checks the tenant quota and appends the batch to Kafka (partition by service or tenant).
  4. The stream processor parses the line into fields, masks sensitive values and tags severity.
  5. The indexer bulk-writes to the hot store; in parallel the archiver writes batched Parquet files to S3.
  6. The alert engine counts errors per service in sliding windows and fires a notification when a rule is met.
  7. An engineer queries “service=checkout level=ERROR last 15m”; the Query Service prunes by time and service, scatters to shards, merges and returns results.

Log schema and layout

-- Structured log event
{ "ts": 1767225600123,           -- event time (ms)
  "tenant": "payments",
  "service": "checkout",
  "level": "ERROR",
  "host": "ip-10-0-3-17",
  "trace_id": "9f3c...",
  "message": "card authorization timeout",
  "fields": { "order_id": "...", "latency_ms": 5021 } }

-- Hot index: one index per day (or hour) per tenant group
logs-2026.01.01-shard-0..N     -- time-based partitioning, drop whole index on expiry

-- S3 layout (archive), partitioned for pruning
s3://logs/tenant=payments/service=checkout/date=2026-01-01/hour=14/part-0001.parquet

Sharding and retention strategy

  • Time-based partitions — most queries have a time range; expiring data means dropping a whole partition.
  • Kafka — partition by tenant + service to keep ordering per source and spread load.
  • Hot index — shards by time and a hash of service, balanced to avoid hot shards.
  • Lifecycle — hot 7 days, warm 30 days (fewer replicas), cold up to 1 year in S3, then delete or glacier.
06 / Deep dives

Deep dive on 3 critical components

For each: the problem, the naive solution, why it fails, and the real solution. Volunteer these before the interviewer asks.

01 Ingestion — absorb millions of events/sec without losing logs

The problem: Every instance emits logs continuously, volume triples during incidents, and the pipeline must neither lose data nor slow the applications.

Naive solution — apps write straight to the database
app → INSERT INTO logs (...)    # or synchronous HTTP call per line

Why it fails: A synchronous call per log line adds latency to the app and couples its health to the logging system. The database cannot take 3M writes/sec; a spike causes failures and data loss exactly when it matters.

Real solution — local agent, batching, Kafka as shock absorber
1. Agent on each host tails files/stdout asynchronously. The app never
   waits on the network.

2. Agent batches (e.g. 1 MB or 1 s), compresses (gzip/zstd) and keeps a
   bounded on-disk buffer to survive outages. On overflow: drop oldest
   DEBUG first, never block the app.

3. Ingest gateway authenticates, applies per-tenant rate limits and
   returns 429 for backpressure; agents back off with jitter.

4. Kafka with replication factor 3 and acks=all for durable writes.
   Partition by tenant+service; many partitions for parallel consumers.

5. Delivery is at-least-once. Duplicates are handled with a log id
   (agent id + sequence number) and idempotent writes in the indexer.

6. Priority lanes: audit and error logs on a protected topic so they
   survive overload; debug logs are sampled or dropped first.

Kafka retention of a few hours to days lets us replay if a
downstream store or parser has a bug.
Make logging asynchronous and buffered at every hop. A log queue absorbs spikes so the slow, expensive stores only see a smoothed, batched stream.
02 Storage & indexing — petabytes without bankrupting the company

The problem: 43 TB per day must stay searchable, but a full inverted index on all text multiplies storage and CPU cost.

Naive solution — index every field in one big cluster, forever
Elasticsearch: dynamic mapping, all fields indexed, 1 year on SSD

Why it fails: Index size can exceed the raw data, and field explosions (every unique key becomes a mapping) crash clusters. Keeping a year on SSD costs vastly more than the value of old logs.

Real solution — selective indexing, columnar storage, tiering
1. Index only what is queried by structure: timestamp, tenant, service,
   level, trace_id, host. Keep the message as a compressed blob, and
   scan it with grep-style search inside the narrowed set.
   (Loki style: index labels, not content. Cheap and fast enough.)

2. Time-partitioned indices. Writes go to the current partition only;
   old partitions are read-only and can be force-merged and compressed.

3. Tiering with lifecycle rules:
     hot  (0-7d)   SSD, replicas=1-2, full indexing
     warm (7-30d)  HDD, fewer replicas, fewer fields
     cold (30d-1y) Parquet on S3, queried by Trino/Athena/ClickHouse
     expire        delete or move to glacier for compliance

4. Columnar format (Parquet) compresses repetitive logs 10x or more
   and lets queries read only needed columns.

5. Limit field cardinality and mapping: reject or flatten explosive
   keys; keep high-cardinality values in the message body.

6. Bloom filters and min/max stats per file skip data that cannot match.

Keep hot small. Most queries hit the last hour; almost none
touch last quarter, so cold must be cheap, not fast.
Index less, compress more, tier by age. The tradeoff is slower queries on old data in exchange for a 10× lower bill.
03 Query & alerting — find the needle fast, page the right person

The problem: Engineers need results in seconds across terabytes, and alerts must fire within a minute of a problem starting.

Naive solution — scan everything, poll for alerts
SELECT * FROM logs WHERE message LIKE '%timeout%';   -- full scan
every minute: run each alert query against the database

Why it fails: Full scans over terabytes take minutes and starve other users. Thousands of alert rules polling the database add heavy constant load and react slowly.

Real solution — pruned scatter-gather, caching, stream-based alerts
1. Always require a time range (default last 15 min). Prune partitions
   by time, tenant and service before touching any data.

2. Scatter the query to relevant shards in parallel, each returns
   top-K or partial aggregates, the coordinator merges. Stream
   partial results to the UI.

3. Cache dashboard queries in Redis with short TTLs; align time buckets
   so refreshes hit the cache. Pre-aggregate common metrics
   (errors per service per minute) as rollups.

4. Guardrails: query timeouts, max scanned bytes, per-user concurrency
   limits and separate query pools so heavy queries cannot starve alerts.

5. Alerting on the stream: Kafka consumers keep sliding-window counters
   per rule (e.g. errors per 5 min per service). Fire when thresholds
   are crossed, with deduplication and grouping.

6. Live tail: subscribe to the Kafka topic filtered by labels and push
   over WebSocket rather than polling the index.

Alert on rollup counters and the stream, never on ad-hoc
full-text scans of the store.
Prune before you scan, and move continuous questions (alerts, tail) onto the stream instead of repeatedly asking the database.
07 / Tradeoffs & alternatives

What we did NOT choose and why

Rejected alternatives

AlternativeWhy rejected
Apps write directly to storageCouples app health to logging; cannot absorb spikes.
Relational DB for logsWrong shape for append-heavy, huge, time-series text.
Index all fields and full textIndex larger than data; mapping explosions; very costly.
Keep all logs on SSDOld logs are rarely read; tiering saves most of the cost.
Exactly-once delivery everywhereExpensive; at-least-once plus idempotent writes is enough.
Polling the DB for alertsHeavy constant load and slow detection; stream processing is better.

What breaks at 10× scale and how we fix it

Problem — Log storm from one service

A bug in a loop emits millions of lines per second and floods the pipeline for everyone.

Fix

Per-tenant and per-service quotas at the gateway, dynamic sampling and dedupe of repeated lines (“repeated 10,000 times”), and isolated Kafka topics for noisy tenants.

Problem — Indexer or search cluster falls behind

Hot store cannot keep up; consumer lag grows and searches miss recent logs.

Fix

Kafka buffers the backlog, autoscale consumers per partition, prioritize error logs, monitor lag as a first-class alert, and shed DEBUG logs first if necessary.

Problem — Hot shards and mapping explosion

Skewed services overload single shards; unbounded field names bloat cluster state.

Fix

Shard by time plus hashed service, split large tenants, enforce field limits and flatten dynamic keys into a single attributes field.

Problem — Sensitive data in logs

Passwords, tokens or card numbers leak into logs and into long-term storage.

Fix

Redact and mask in the agent and again in the stream processor, schema-level denylist, per-tenant access control, encryption at rest, and audit logs for who searched what.

08 / Summary

Cheat sheet

What to remember before walking into the room.

Key numbers

1M events/sec (3M peak) · ~500 MB/s · ~43 TB/day · ~10x compression · 7d hot / 30d warm / 1y cold

Key datastores

Kafka (buffer) · Elasticsearch / ClickHouse (hot) · S3 + Parquet (cold) · PostgreSQL (metadata) · Redis (cache)

Ingestion strategy

Local agent, batch and compress, gateway quotas, Kafka acks=all, at-least-once with idempotent writes.

Storage strategy

Index only key fields, time-partitioned, tier hot to cold, columnar compression, drop whole partitions.

Query strategy

Mandatory time range, prune then scatter-gather, rollups and cache, query guardrails.

Key tradeoffs

Cost vs. query speed. Index depth vs. storage size. Durability vs. dropping debug logs under overload.

Hardest part

Staying cheap and reliable at 40+ TB/day while still answering needle-in-haystack queries in seconds.

Patterns

Buffering queue · backpressure · tiered storage · time partitioning · stream alerting · sampling

Partition keys

Kafka → tenant+service · Index → time + service hash · S3 → tenant/service/date/hour
