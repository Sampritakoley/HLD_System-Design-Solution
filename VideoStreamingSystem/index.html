01 / Understanding the problem

What is this system, really?

A video platform lets creators upload videos once and lets millions of viewers watch them instantly on any device and network. Think of it as a giant media factory (upload, convert, store) bolted to a global delivery network.

The core challenge: videos are huge, viewers are everywhere on wildly different connections, and reads outnumber writes by roughly 1000:1. Bytes served, not database queries, is the bottleneck.

Core features in scope

Upload video

Creators upload large files reliably, add title, description and thumbnail, and publish.

Watch video

Playback starts in under 2 seconds with no buffering, adapting to the viewer's bandwidth.

Search & discover

Search by title or tags, home feed and "up next" recommendations.

Engagement

Views, likes, comments and subscriptions, with counts that feel live.

What makes this hard at scale

  • Huge files. Uploads are gigabytes; they must survive flaky networks and resume.
  • Transcoding cost. Every video becomes many resolutions and codecs; it is CPU-heavy and slow.
  • Egress bandwidth. Tens of Tbps of video leaves the system; origin servers alone can never serve it.
  • Device diversity. Phones on 3G and TVs on fibre need different bitrates of the same video.
  • Viral spikes. One video can go from zero to millions of concurrent viewers in minutes.
02 / Requirements

Functional vs. non-functional requirements

Non-functional requirements are what actually drive architecture decisions — they're listed first for a reason.

Functional

  • Upload videos with metadata and thumbnail
  • Stream videos on web, mobile and TV
  • Search by title, tag and channel
  • Like, comment, subscribe
  • View counts and watch history
  • Personalised home feed and recommendations
  • Resume playback from last position

Non-functional

  • 500M DAU, ~2.5B views/day
  • Playback start < 2 seconds (p95)
  • 99.99% availability for playback
  • Uploaded videos are never lost (11 nines durability)
  • Video live within minutes of upload
  • View counts eventually consistent
  • Smooth playback on poor networks
  • Cost-efficient storage and bandwidth

Clarifying questions

Only on-demand video, or live streaming too? Live changes latency and ingest entirely.
Maximum video length and size? This decides chunked and resumable upload.
Which devices and resolutions, up to 4K? This sets the transcoding ladder.
Global audience or one region? Decides CDN footprint and data residency.
Is monetisation (ads) in scope, or content moderation and copyright checks?
How exact must view counts be — live to the second, or approximate?

Back-of-envelope math

Order-of-magnitude accuracy is the goal here, not precision. Every assumption is stated explicitly.

Assumptions

DAU                     = 500M, ~5 videos watched per user per day
Views per day           = 2.5B  (average ~30K/sec, peak ~3-4x)
Watch time              = ~1 hour per user per day → 500M hours/day
Average bitrate         = 2.5 Mbps ≈ 1.1 GB per hour watched
Uploads                 = 5M videos/day, average 500 MB original
Read : write ratio      = ~500 views per upload (and more on hot videos)
Metadata per video      = ~2 KB

QPS

Video starts (manifest + first segments):
  2.5B / 86,400                = ~30K/sec avg → ~100K/sec peak

Uploads:
  5M / 86,400                  = ~60 videos/sec

View-count events:
  2.5B / 86,400                = ~30K writes/sec → batch and aggregate

Metadata QPS is modest. The real load is bytes: keep video off
application servers entirely and serve it from object storage and CDN.

Storage

Originals:
  5M × 500 MB                  = ~2.5 PB/day

Transcoded renditions (~6 resolutions, ~1.5x original in total):
  2.5 PB × 1.5                 = ~3.75 PB/day → ~1.4 EB/year

Metadata:
  5M × 2 KB                    = ~10 GB/day (tiny)

Tier storage by age: hot videos on SSD-backed CDN, long tail on cheap
cold object storage. Most videos are almost never watched.

Bandwidth & connections

Egress                   = 500M hrs × 1.1 GB / 86,400 s ≈ 6.4 TB/s = ~50 Tbps avg, ~100 Tbps peak
Concurrent streams       = 500M hrs / 24 ≈ 20M avg, ~50M peak
Ingress (uploads)        = 2.5 PB/day ≈ 30 GB/s ≈ ~250 Gbps

Egress is ~400x ingress. A CDN with a 95%+ hit rate is not optional;
origin then only serves ~5 Tbps of cache misses.
04 / High-level design

Architecture

Built top-down from the client. Every box exists because of a number from Step 3.

CREATOR                                        VIEWER (web / mobile / TV)
   │ resumable upload (chunks)                    │ GET manifest, then segments
   ▼                                              ▼
[ API Gateway / LB ] ◄────────────────────► [ CDN edge ] ──miss──► [ Origin / Object store ]
   │                                              ▲                        ▲
   ├──► [ Upload Service ] ──► [ Raw bucket ]     │                        │
   │            │                                 │               [ Processed bucket ]
   │            ▼                                 │                        ▲
   │        [ Kafka ] ──► [ Transcoding Workers (DAG) ] ─────────────────┘
   │            │                   └──► thumbnails · moderation · packaging (HLS/DASH)
   │            ▼
   ├──► [ Metadata Service ] ◄──► [ Metadata DB + Redis cache ]
   ├──► [ Search Service ] ◄──► [ Elasticsearch ]
   ├──► [ Recommendation / Feed ]
   └──► [ Engagement Service ] ──► [ Kafka ] ──► [ Stream aggregator ] ──► [ Counters DB ]

Video bytes never touch app servers: clients upload to and stream from object storage / CDN directly

Component rationale

Upload service + object storage
Issues pre-signed URLs so clients upload chunks straight to object storage. App servers only track upload state, which keeps them cheap and stateless.
Kafka + transcoding workers
An upload-complete event triggers a pipeline that splits the video into chunks, encodes each into every resolution in parallel, and packages HLS/DASH segments. Queueing absorbs bursts.
Processed bucket (origin)
Durable, replicated store of all renditions, segments and manifests. The CDN pulls from here on a cache miss.
CDN
Caches popular segments in edge locations close to viewers. This is what makes 100 Tbps possible and keeps start-up latency low.
Metadata service + DB + cache
Titles, channels, status, and manifest locations. Read-heavy, so a sharded SQL store fronted by Redis handles it easily.
Search, recommendations & engagement
Elasticsearch indexes metadata for search. Recommendations and view counters consume Kafka events asynchronously, off the playback path.

End-to-end data flow — "creator uploads, viewer watches"

  1. Creator starts an upload; Upload Service creates a record in UPLOADING state and returns pre-signed chunk URLs.
  2. Client uploads chunks in parallel to the raw bucket; any failed chunk is retried, and the upload can resume.
  3. On completion, an event goes to Kafka and status becomes PROCESSING.
  4. The transcoding DAG splits the video, encodes each chunk into 240p–4K, extracts thumbnails and runs moderation and copyright checks.
  5. Segments and manifests are written to the processed bucket; metadata flips to READY and the video is indexed for search.
  6. Viewer opens the video; the metadata service returns the manifest URL (from cache).
  7. The player fetches the manifest from the CDN, picks a starting quality, then requests segments and switches quality as bandwidth changes.
  8. Play, pause and completion events stream to Kafka for view counts, history and recommendations.

Storage layer

Different data, different access patterns, different stores — huge blobs in object storage, small relational metadata in SQL, counters in a fast aggregated store.

Core tables and keys

-- PostgreSQL / MySQL (videos)
CREATE TABLE videos (
  video_id     BIGINT PRIMARY KEY,       -- snowflake id
  channel_id   BIGINT NOT NULL,
  title        TEXT NOT NULL,
  description  TEXT,
  status       TEXT NOT NULL,            -- UPLOADING | PROCESSING | READY | FAILED | REMOVED
  duration_sec INT,
  manifest_url TEXT,                     -- HLS / DASH master playlist
  raw_key      TEXT,                     -- object-storage path of the original
  created_at   TIMESTAMP DEFAULT now()
);

-- Cassandra
comments:  PK ((video_id), created_at DESC, comment_id)
history:   PK ((user_id), watched_at DESC)

-- Redis
Key: video:{id}            Value: HASH { title, channel, manifest_url, status }   TTL 1h
Key: views:{id}            Value: counter, flushed to DB every few seconds

Sharding strategy

  • Metadata — shard by video_id for even spread; replicas absorb reads.
  • Comments — partition by video_id so one video's comments are read together.
  • History — partition by user_id; queries are always "this user's recent videos".
  • Video objects — keyed by video_id and rendition; replicated across regions, tiered to cold storage as they age.
06 / Deep dives

Deep dive on 3 critical components

For each: the problem, the naive solution, why it fails, and the real solution used at scale. Volunteer these problems before the interviewer asks — it signals senior-level thinking.

01 Upload & transcoding — turn one raw file into many playable formats

The problem: Accept multi-gigabyte files over unreliable networks, then convert each into many resolutions and codecs quickly, at 60 videos per second.

Naive solution — single POST upload, one server encodes the whole file
POST /upload (whole file)  →  app server  →  ffmpeg -i input.mp4 → 720p.mp4

Why it fails: A dropped connection restarts a 2 GB upload, file bytes choke the app servers, and encoding a long video on one machine takes hours. One crash loses everything.

Real solution — resumable chunked upload + parallel transcoding DAG
1. Client splits the file into ~5-10 MB chunks and uploads them in parallel
   to object storage via pre-signed URLs. Upload Service records which chunks
   arrived, so a dropped connection resumes from the last good chunk.

2. "Upload complete" event → Kafka → Transcoding Orchestrator.

3. Orchestrator builds a DAG of tasks:
     split into ~10s GOP-aligned segments
       → encode each segment per rendition (240p ... 4K, H.264 / VP9 / AV1)
       → merge and package as HLS / DASH segments + manifests
     in parallel: thumbnails, audio tracks, captions, moderation, copyright fingerprint

4. Stateless workers pull tasks from queues; a failed task is retried alone,
   not the whole video. Segments make encoding embarrassingly parallel.

5. Status moves PROCESSING → READY. Publish the lowest rungs first so the
   video becomes watchable in minutes, then add 4K later.

6. Cost control: priority queues (new creators and popular channels first),
   cheaper codecs for the long tail, spot instances for workers.

A 1-hour video split into 360 segments can be encoded by hundreds
of workers at once, cutting wall-clock time from hours to minutes.
The key insight: clients talk to object storage directly, and transcoding is a DAG of small, retryable, parallel tasks, not one long job.
02 Streaming delivery — adaptive bitrate over a CDN

The problem: Start playback in under 2 seconds for millions of viewers on different devices and networks, without buffering, while pushing ~100 Tbps.

Naive solution — serve one MP4 file from our servers
GET /videos/123.mp4   →  origin streams the whole file

Why it fails: A single high-quality file buffers on slow networks and wastes data on small screens. Origin servers cannot carry tens of Tbps, and far-away viewers suffer high latency.

Real solution — segmented ABR streaming (HLS / MPEG-DASH) + CDN
1. Each video exists as a ladder of renditions, each cut into 2-6 s segments.
   A master manifest (.m3u8 / .mpd) lists every rendition and segment URL.

2. Player downloads the manifest, starts at a safe low quality for a fast
   first frame, then measures throughput and buffer level and switches
   quality per segment (adaptive bitrate).

3. Segments are plain HTTP files, so a CDN caches them like static assets.
   Viewer → nearest edge → regional cache → origin (only on a miss).

4. Cache hierarchy: edge (hot) → regional mid-tier → origin shield, so a
   viral video causes one origin fetch per segment, not millions.

5. Proactively push (pre-warm) segments of trending or new big-channel
   videos to edges; leave the long tail to pull on demand.

6. Protect origin: request coalescing, long TTLs for immutable segments,
   signed URLs or tokens to prevent hotlinking.

Segments are immutable, so they can be cached for a very long time.
Only the manifest of a live or edited video needs short TTLs.
The key insight: turn video into small static files so the existing HTTP CDN machinery does the heavy lifting, and let the client choose quality.
03 View counts & metadata — hot keys at scale

The problem: Count 30K view events per second, show near-live totals, and serve metadata for a video that millions open at once, without melting the database.

Naive solution — increment a DB row per view and read metadata from the DB
UPDATE videos SET views = views + 1 WHERE video_id = ?
SELECT * FROM videos WHERE video_id = ?

Why it fails: Every view contends on the same row lock for a viral video, and each page load hits the database. Write contention and read load on a single shard cripple it.

Real solution — aggregate asynchronously, cache aggressively
1. Player sends a view event (after ~30 s of watching, to avoid spam).
   Events go to Kafka, partitioned by video_id.

2. A stream processor (Flink / Kafka Streams) aggregates counts per video
   in small windows and writes one batched update every few seconds.

3. Hot counters live in Redis (INCRBY); the DB stores the durable total.
   The UI shows a slightly stale number, which is fine.

4. Fraud and bot filtering runs in the same stream, before counts are final.

5. Metadata reads: cache-aside in Redis with a TTL, plus a local in-process
   cache on each app server for the hottest videos. Replicas absorb the rest.

6. Hot key protection: replicate a viral video's key across several cache
   nodes (key suffix or local cache) so one node is not the bottleneck.

Accuracy tradeoff: exact counts are not needed in real time.
Approximate now, reconciled from the event log later.
Counts and likes need only eventual consistency; the video's status and manifest need accuracy. Use the right guarantee for each and never put either on the playback critical path.
07 / Tradeoffs & alternatives

What we did NOT choose and why

Rejected alternatives

AlternativeWhy rejected
Serve video from app serversCannot carry Tbps of egress; object storage plus CDN is cheaper and scales by itself.
Single progressive MP4 per videoNo adaptation to bandwidth, poor seeking, constant buffering on weak networks.
Upload through the backendWastes server bandwidth; pre-signed direct uploads are simpler and resumable.
Transcode on upload in the requestSlow and fragile; an async DAG with retries is reliable and parallel.
Store video blobs in a databaseDatabases are the wrong tool for petabytes; keep only pointers there.
Exact real-time view countsHot-row contention for little value; batched eventual counts are enough.
WebRTC for on-demand playbackBuilt for ultra-low latency calls; HTTP segments are cheaper and cache well for VOD.

What breaks at 10× scale and how we fix it

Problem — Viral video and cold-cache stampede

A new video explodes; every edge misses at once and floods the origin with requests for the same segments.

Fix

Origin shield and request coalescing so each segment is fetched once, pre-warming for predicted hits, and multi-CDN failover for extra capacity.

Problem — Transcoding backlog

A burst of uploads (or a new codec rollout) grows the queue, and creators wait hours for their videos to go live.

Fix

Autoscale workers on queue depth, use priority lanes, publish low resolutions first, and encode rarely watched videos in cheaper, slower batches.

Problem — Storage cost explosion

Exabytes of renditions keep growing while most videos are almost never watched.

Fix

Tier by popularity and age, drop rarely used high-bitrate renditions and re-create on demand, use better codecs (AV1) for popular videos, and dedupe reuploads by content fingerprint.

Problem — Regional outage

A region hosting metadata or an origin bucket goes down, breaking playback and uploads for its users.

Fix

Replicate objects and metadata across regions, route viewers to the nearest healthy origin, and keep CDN-cached content playable even while origin is degraded.

08 / Summary

Cheat sheet

The ten things worth remembering before walking into the room.

Key numbers

500M DAU · 2.5B views/day · ~100K peak starts/sec · ~100 Tbps egress · 5M uploads/day · ~4 PB/day new storage

Key datastores

Object storage (videos) · MySQL/PostgreSQL + Redis (metadata) · Cassandra (comments, history) · Elasticsearch (search) · Kafka (events)

Upload strategy

Chunked, resumable uploads straight to object storage via pre-signed URLs; app servers track state only.

Transcoding strategy

Kafka-triggered DAG: split into segments, encode in parallel per rendition, package HLS/DASH, retry per task.

Delivery strategy

Adaptive bitrate over HTTP segments; multi-tier CDN with origin shield; pre-warm trending videos.

Video state machine

UPLOADING → PROCESSING → READY, or FAILED / REMOVED. Status changes are conditional updates.

Key tradeoffs

Storage cost vs. number of renditions. Start-up speed vs. quality. Exact vs. eventual counts. Pre-warm vs. pull-on-demand.

Hardest part

Delivering enormous bandwidth cheaply and smoothly, while converting every upload into many formats fast.

Sharding keys

Metadata → video_id · Comments → video_id · History → user_id · Kafka → video_id · Objects → video_id + rendition
