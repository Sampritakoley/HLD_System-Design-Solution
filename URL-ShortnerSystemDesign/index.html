01 / Understanding the problem

What is this system, really?

A URL shortener turns a long link into a short one (like sho.rt/aB3xK9q) and sends anyone who opens the short link to the original page. It is used in messages, QR codes, ads and social posts.

The core tension: the logic is trivial, but the scale is not. Short codes must be unique across billions of links, and redirects must be nearly instant for a read load that dwarfs the write load.

Core features in scope

Shorten

Create a short link for a long URL, optionally with a custom alias and expiry date.

Redirect

Resolve a short code and send the browser to the original URL in milliseconds.

Analytics

Count clicks and show breakdowns by time, country, device and referrer.

Management

Edit, disable or delete links; expire them automatically; block abusive URLs.

What makes this hard at scale

  • Unique codes. Billions of links need collision-free short codes, generated by many servers at once.
  • Read-heavy traffic. Redirects outnumber creations roughly 100 to 1.
  • Latency. A redirect is a visible delay before the real page; it must feel instant.
  • Hot links. A viral link can receive millions of hits in minutes.
  • Abuse. Shorteners are used to hide phishing and malware links.
02 / Requirements

Functional vs. non-functional requirements

Non-functional requirements drive the architecture, so they come first.

Functional

  • Create a short URL from a long URL
  • Redirect a short URL to the original
  • Optional custom alias
  • Optional expiration time
  • Click analytics per link
  • User accounts to manage links
  • Delete or disable a link
  • Block malicious destinations

Non-functional

  • 100M new URLs/day, 10B redirects/day
  • Redirect p99 < 50 ms (server side)
  • 99.99% availability for redirects
  • Short codes unique and hard to guess
  • Links never change meaning or get lost
  • Analytics can be eventually consistent
  • Reads scale independently from writes
  • Retain links for years

Clarifying questions

How long should links live by default, and can they expire?
Are short codes allowed to be sequential and guessable, or must they be random?
Do we need custom aliases, and who owns them?
Do we need detailed analytics, and how fresh must the counts be?
Can the same long URL map to one short code, or a new one each time?

Back-of-envelope math

Order-of-magnitude accuracy, with every assumption stated.

Assumptions

New URLs per day       = 100M
Read : write ratio     = 100 : 1 → 10B redirects per day
Retention              = 10 years
Record size            = ~500 bytes (code, long URL, user, timestamps, expiry)
Peak factor            = ~4x average
Cache                  = 80/20 rule: a small share of links gets most clicks

QPS

Writes:    100M / 86,400 = ~1.2K/sec avg → ~5K/sec peak
Redirects: 10B / 86,400 = ~115K/sec avg → ~500K/sec peak
Origin DB reads after ~90% cache hits: ~50K/sec peak

Reads dominate. Design the redirect path as a pure cache lookup
and keep the database off the hot path.

Storage

Per year:  100M × 365 = 36.5B URLs
10 years:  ~365B URLs × 500 B = ~180 TB
Code space: 62^7 = ~3.5 trillion codes → 7 characters is plenty for 365B links
          (62^6 = 56B is too small; 62^8 is unnecessary)

Cache: hot ~100M links × 500 B = ~50 GB across a Redis cluster
The data is small per record; the volume comes from sheer count.

Bandwidth

Redirect response is tiny (~500 B headers): 500K/sec × 500 B = ~250 MB/s peak
Constraint is request rate and latency, not bandwidth or capacity.
04 / High-level design

Architecture

Every box exists because of a number from Step 3. Two paths: a tiny write path and a huge read path.

 CLIENT / BROWSER
     │
 [ CDN / Edge ]  caches popular redirects
     │
 [ API Gateway / LB ]  rate limit · auth · abuse checks
     │
 ├─► [ Write Service ] ─► [ ID Generator ] (ranges / counter)
 │         │                         
 │         ├─► [ URL DB: sharded KV store ]  ◄── [ Cache: Redis cluster ]
 │         └─► [ Malware / URL Check ]
 │
 ├─► [ Redirect Service ] ─► Redis ─► URL DB (on miss)
 │         │
 │         └─► click event ─► [ Kafka ] ─► [ Analytics Pipeline ] ─► [ OLAP store ]
 │
 └─► [ Cleanup Job ]  expired links · [ Key Pool ] reclaimed codes

The redirect path only reads: CDN, Redis, then DB. Analytics are off the critical path

Component rationale

API gateway
Authenticates users, rate limits creation per user and IP, and routes writes and reads to the right services.
Write service + ID generator
Validates the URL, gets a unique ID, encodes it as a short code and stores the mapping. Never needs a global lock.
URL database (key-value)
Single access pattern: get by short code. A sharded KV or wide-column store scales to hundreds of terabytes easily.
Redis cache
Holds hot mappings in memory so most redirects never touch the database.
CDN / edge
Caches redirect responses close to users for very popular links, cutting latency and origin load.
Redirect service
Stateless and horizontally scalable: look up the code, return an HTTP redirect, emit a click event asynchronously.
Kafka + analytics
Click events stream through Kafka to aggregation jobs, so counting never slows a redirect.

End-to-end flow — "create and open a short link"

  1. User submits a long URL (and optional alias and expiry) to POST /shorten.
  2. The Write Service validates the URL, checks it against malware and blocklists, and applies rate limits.
  3. It takes a unique ID from the generator and encodes it into a 7-character base62 short code.
  4. The mapping (code → long URL, owner, expiry) is stored in the URL DB; the short URL is returned.
  5. Later, someone opens sho.rt/aB3xK9q; the CDN or edge serves it if cached.
  6. On a miss, the Redirect Service checks Redis; if still missing, it reads the DB and fills the cache.
  7. It checks expiry and status, then answers with an HTTP redirect (301 or 302) to the long URL.
  8. A click event (code, time, country, device, referrer) is published to Kafka for analytics.

Core tables and keys

-- URL mapping (KV / wide-column)
urls(
  short_code   VARCHAR(10) PRIMARY KEY,   -- "aB3xK9q"
  long_url     TEXT NOT NULL,
  user_id      BIGINT,
  created_at   TIMESTAMP,
  expires_at   TIMESTAMP NULL,
  status       TEXT                         -- ACTIVE | DISABLED | EXPIRED | BLOCKED
);

-- Click analytics (OLAP)
clicks(short_code, ts, country, device, referrer, ip_hash)

-- Redis
Key: url:{short_code}   Value: long_url + expiry   TTL ~24h (refreshed on hit)

-- Base62 alphabet: 0-9, a-z, A-Z (62 characters)
encode(125) = "21"   -- 2×62 + 1

Sharding strategy

  • URLs — shard by short_code (hash); every lookup goes to exactly one shard with even spread.
  • Replicas — several read replicas per shard; reads dominate and replication lag is harmless for immutable mappings.
  • Cache — consistent hashing across Redis nodes; replicate hot keys if needed.
  • Analytics — partition by day and short_code so link-level queries scan little data.
06 / Deep dives

Deep dive on 3 critical components

For each: the problem, the naive solution, why it fails, and the real solution. Volunteer these before the interviewer asks.

01 Short-code generation — unique, short and distributed

The problem: Many write servers must each generate unique 7-character codes with no collisions, at ~5K per second, without becoming a bottleneck or a single point of failure.

Naive solution — hash the URL and take the first 7 characters
code = base62( md5(long_url) )[:7]
if exists(code): code = base62( md5(long_url + salt) )[:7]   # retry

Why it fails: Truncation guarantees collisions as the table grows (birthday problem), so every write needs a DB check and possible retries. Retries under concurrency still race. It also gives the same code for the same URL for different users, which breaks per-user ownership and analytics.

Real solution — unique numeric IDs encoded in base62, with range allocation
1. Generate a globally unique integer ID, then base62-encode it.
   62^7 = 3.5T, so a 7-char code covers 365B links with room to spare.

2. Range allocation (counter ranges): a coordination service
   (ZooKeeper / etcd / a small DB) hands each write server a block,
   e.g. 1,000,000 IDs. The server increments locally with no
   per-request network call. Servers only coordinate when a block is
   used up.

3. Crash-safe: a dead server just wastes its unused range. That is
   fine, since the ID space is huge.

4. Alternative: Snowflake-style 64-bit ID (timestamp + machine id +
   sequence). Unique without coordination, but the encoded code is
   longer (about 11 chars).

5. Alternative: pre-generate random keys offline into a key pool
   (Key Generation Service). Servers take keys in batches, mark them
   used, and keep a local cache of keys.

6. Predictability: sequential IDs reveal volume and can be enumerated.
   Mitigate by shuffling bits (a reversible permutation) before
   encoding, or by using the random key pool.

7. Custom alias: check availability with an atomic conditional
   insert (INSERT ... IF NOT EXISTS); reject reserved words.

Uniqueness by construction beats uniqueness by checking.
Never rely on "generate, check, retry" at scale.
Separate uniqueness (a counter or ID range) from appearance (base62, bit shuffling). Handing out blocks of IDs means servers coordinate rarely and never share a lock.
02 The redirect read path — 500K requests per second, almost no DB

The problem: Redirects make up 99% of traffic. Each must resolve a code to a URL in a few milliseconds, even when one link suddenly goes viral.

Naive solution — query the database on every redirect
GET /aB3xK9q → SELECT long_url FROM urls WHERE code = 'aB3xK9q' → 302

Why it fails: 500K queries per second would need a huge database fleet. A single viral link hammers one shard, and every request pays disk and network latency that adds up on a path where users are waiting.

Real solution — layered caching and a stateless redirect tier
1. CDN / edge cache: popular redirects are served from the edge
   with a short TTL, never reaching our data centers.

2. Redis cache-aside: Redirect Service checks Redis first. On a miss,
   it reads the DB (replica) and populates Redis with a TTL. LRU eviction
   keeps the hot ~20% of links in memory.

3. In-process cache for the very hottest keys (a small LRU per server)
   handles viral links without even a Redis call.

4. Negative caching: cache "code not found" briefly, and use a Bloom
   filter of existing codes, so attackers guessing random codes
   cannot flood the DB with misses.

5. 301 vs 302:
     301 (permanent): browsers cache it, so repeat visits skip us.
     Less load, but we lose click counts and cannot change the target.
     302 (temporary): every click hits us, so analytics and edits work.
   Most shorteners use 302 (or 301 with short max-age) when analytics matter.

6. Statelessness: any redirect server can answer any request, so
   scaling is just adding nodes behind the load balancer.

7. Expiry and status are checked on the cached value; expired or
   disabled links return 404/410 and are evicted.

A good target is a 95-99% cache hit rate. The database then
only sees cold links and cache refills.
The product tradeoff is explicit: 301 minimizes load but sacrifices analytics and control; 302 keeps both at the cost of more traffic, which the cache layers absorb.
03 Analytics, expiry & abuse — everything off the critical path

The problem: Users want click statistics, links must expire, and attackers will use the service to hide phishing URLs, all without slowing redirects.

Naive solution — update a counter in the DB on every click
UPDATE urls SET click_count = click_count + 1 WHERE code = ?   -- per redirect

Why it fails: 500K writes per second on the same hot rows creates lock contention and turns a read-only path into a write path. Expiry via full table scans is just as costly. Nothing stops abuse before a bad link spreads.

Real solution — async event pipeline, lazy and batch expiry, layered abuse control
1. Analytics: the Redirect Service publishes a small click event to
   Kafka (fire and forget; drop on failure rather than slow the user).
   Stream/batch jobs aggregate into per-minute and per-day counts
   in an OLAP store (ClickHouse / Druid). Dashboards read aggregates.

2. Counts are eventually consistent (seconds to minutes). That is
   acceptable. For exact, instant totals on one link, use a Redis
   counter flushed periodically.

3. Expiry, lazy: on lookup, compare expires_at with now; if expired,
   return 410 and evict from cache. No work for links nobody visits.

4. Expiry, batch: a background job scans by expires_at (indexed or
   time-bucketed) and marks or deletes expired rows. Reclaimed codes
   can return to a pool, or stay retired to avoid confusing old links.

5. Abuse prevention at creation: validate URL format, check against
   malware/phishing lists (e.g. Safe Browsing), block known bad domains,
   rate limit per user/IP, require login for high volume.

6. Abuse after creation: re-scan links periodically, accept user
   reports, and allow instant disable. A disabled link must stop
   redirecting immediately, so invalidate the cache entry.

7. Privacy: hash IPs in analytics, respect retention rules, and avoid
   storing more than needed.

Anything that is not needed to answer the redirect belongs in a
queue, not on the request path.
Keep the hot path read-only and tiny. Counting, cleanup and scanning are important, but they can all happen a few seconds later.
07 / Tradeoffs & alternatives

What we did NOT choose and why

Rejected alternatives

AlternativeWhy rejected
Hash and truncate the URLCollisions grow with scale; needs check-and-retry on every write.
Single auto-increment counterSingle point of failure and write bottleneck; use ranges instead.
Query DB for every redirectCannot sustain 500K/sec; caches are essential.
Per-click DB counter updateHot row contention; use event streaming and aggregation.
Relational DB with joins for URLsThe access pattern is pure key lookup; KV scales more simply.
Always 301 redirectsBrowser caching hides clicks and blocks later edits or takedowns.

What breaks at 10× scale and how we fix it

Problem — A link goes viral

Millions of requests per minute hit the same code, overloading one cache key and one shard.

Fix

CDN caching, in-process caches on redirect servers, replicate hot keys across Redis nodes, and request coalescing so a miss triggers one DB read.

Problem — ID range service is down

Write servers run out of their allocated range while the coordinator is unavailable.

Fix

Allocate large ranges so servers have minutes to hours of headroom, run the coordinator as a replicated quorum (etcd/ZooKeeper), and pre-fetch the next block early.

Problem — Cache or Redis cluster failure

A cold cache sends a flood of traffic to the database all at once.

Fix

Replicated Redis with automatic failover, staggered TTLs to avoid mass expiry, rate limiting and request coalescing to the DB, and gradual warm-up from recent access logs.

Problem — Phishing and malware links

Attackers create thousands of short links that point to harmful sites.

Fix

Reputation checks at creation, rate limits, re-scanning of existing links, an interstitial warning page for suspicious domains, fast takedown with cache invalidation, and a public reporting channel.

08 / Summary

Cheat sheet

What to remember before walking into the room.

Key numbers

100M writes/day · 10B reads/day · ~1.2K writes/sec · ~115K reads/sec (~500K peak) · 7-char code · ~180 TB over 10 years

Key datastores

DynamoDB / Cassandra (mappings) · Redis (cache) · Kafka + ClickHouse (analytics) · ZooKeeper / etcd (ID ranges)

ID strategy

Unique integer ID from per-server ranges, base62 encoded, optional bit shuffling for unpredictability.

Read strategy

CDN, in-process LRU, Redis cache-aside, negative caching, Bloom filter, stateless redirect tier.

Redirect choice

302 (or short-lived 301) when analytics and edits matter; 301 only when load matters most.

Key tradeoffs

Random vs. sequential codes. 301 vs. 302. Exact vs. eventual analytics. Cache size vs. hit rate.

Hardest part

Generating unique codes without coordination bottlenecks, and serving redirects at massive read scale.

Patterns

Cache-aside · range allocation · consistent hashing · async event pipeline · lazy expiry · Bloom filter

Sharding keys

URLs → hash(short_code) · Cache → short_code · Clicks → day + short_code · Kafka → short_code
