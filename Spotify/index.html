01 / Understanding the problem

What is this system, really?

Spotify is a music streaming platform. Users search a catalog of ~100M tracks, press play and hear audio within a second, build playlists, download for offline, and get personalised recommendations. Think of it as a giant media CDN with a metadata brain and a data pipeline bolted on.

The core challenge: unlike BookMyShow, there is no scarce inventory to protect. A song can be played by millions at once. What matters is latency (music must start instantly and never stutter), bandwidth cost (audio bytes dominate everything) and data accuracy (every play feeds recommendations and pays artist royalties).

Core features in scope

Search & browse

Find tracks, artists, albums and playlists with typo tolerance and autocomplete. Read-heavy and cacheable.

Playback

Start a track in under a second, adapt quality to the network, seek, and resume across devices.

Library & playlists

Liked songs, followed artists, user and collaborative playlists that stay consistent across devices.

Recommendations

Home feed, Discover Weekly and radio, built from listening history collected by an event pipeline.

What makes this hard at scale

  • Bandwidth dominates. Audio bytes dwarf every API payload; egress cost and CDN hit rate decide the architecture.
  • Start latency is the UX. Users judge the app by the gap between tap and sound.
  • Skewed popularity. A few thousand tracks get most plays (power-law), while the long tail is huge and rarely touched.
  • Collaborative playlists. Several people edit one ordered list at once, from phones that may be offline.
  • Billions of events. Every play, skip and search is an event that must be captured reliably without slowing playback.
02 / Requirements

Functional vs. non-functional requirements

Non-functional requirements are what actually drive architecture decisions — they're listed first for a reason.

Functional

  • Search tracks, artists, albums
  • Stream audio with seek and pause
  • Create and edit playlists
  • Like songs, follow artists
  • Offline downloads
  • Personalised home and radio
  • Resume playback across devices
  • Track plays for royalties

Non-functional

  • 50M DAU, ~1.25B plays/day
  • Play start < 500ms (p95)
  • Search < 200ms (p99)
  • No rebuffering on stable networks
  • 99.99% availability for playback
  • Eventual consistency OK for recs and counts
  • Strong-ish consistency for library and playlists
  • Play events never lost (royalties)

Clarifying questions

Music only, or podcasts and video too? Different file sizes and licensing.
Do we build our own CDN or rent one? This changes the cost model completely.
Are offline downloads in scope, and do they need DRM and expiry?
Do collaborative playlists need real-time sync or is refresh-on-open enough?
Is there a free tier with ads? Ad insertion adds a whole service.
How fresh must recommendations be — daily batch or near real time?
03 / Estimation

Back-of-envelope math

Order-of-magnitude accuracy is the goal here, not precision. Every assumption is stated explicitly.

~45K/sPeak play-start QPS
~1.6TbpsPeak audio egress
~250GBPlay events / day

Assumptions

DAU                     = 50M users
Listening per user      = ~25 tracks/day (~100 min)
Track length / bitrate  = 4 min at 160 kbps (~4.8 MB)
Peak concurrent         = 10M listeners
Catalog                 = 100M tracks, 3 quality levels each

QPS

Play starts:
  50M × 25 = 1.25B/day
  1.25B / 86,400              = ~14,500/sec
  Peak (3× average)           = ~45,000/sec

Each play start is a cheap API call (auth + signed URL).
The heavy part is the audio bytes that follow, not the API.

Storage

Audio files (3 qualities: ~2.5 + 4.8 + 9.6 MB):
  100M × ~17 MB               = ~1.7 PB

Play events:
  1.25B × 200 B               = ~250 GB/day (~90 TB/year)

Metadata + user data           = tens of TB, small next to audio

Bandwidth

10M concurrent × 160 kbps                  = ~1.6 Tbps
Popular-track CDN hit rate                 = ~95%+
Origin egress after CDN                    → ~80 Gbps

Power-law popularity: top ~1% of tracks carry most traffic,
so edge caches stay warm and origin sees mostly long-tail misses.

Component rationale

CDN / edge cache
Serves nearly all audio bytes. Because of power-law popularity, a small hot set fits in edge caches and gives ~95%+ hit rate. Without it, origin egress would be impossible.
API Gateway / Load Balancer
Auth, rate limiting, routing and SSL termination for all metadata calls. Audio requests bypass it and go to the CDN directly using signed URLs.
Catalog Service
Tracks, albums, artists, credits. Written by ingestion, read by everyone, so it is heavily cached and replicated. Eventual consistency is fine.
Search Service
Elasticsearch with n-gram analysers for autocomplete and typo tolerance, plus popularity as a ranking signal. Index updated asynchronously from catalog events.
Playback Service
Checks subscription and licensing by region, picks a bitrate, and returns a short-lived signed manifest URL. Also stores the current playback position for cross-device resume.
Playlist & Library Service
Owns user playlists, liked songs and follows. Access pattern is key-based and partitioned by user or playlist, so a wide-column store fits well.
Recommendation Service
Serves precomputed recommendation lists from a feature store. Models train offline on listening history; serving is a fast key lookup, never heavy compute on request.
Kafka + Event Ingest
Every play, skip and search becomes an event. Kafka decouples capture from consumers: royalty ledger, analytics, recommendation features. Playback never waits on it.

End-to-end data flow — "user plays a song"

  1. User taps a track. Client calls POST /playback/start with track ID and device info.
  2. Playback Service validates the session, subscription and regional license, then chooses a bitrate from the client's network hint.
  3. It returns a signed CDN manifest URL (valid a few minutes) and the client begins fetching the first chunks.
  4. CDN edge serves chunks from cache; on a miss it pulls from S3 and caches for the next listener.
  5. The client buffers ahead and prefetches the next queued track's first chunk so the following song starts instantly.
  6. Client sends heartbeat events (start, 30s mark, skip, end) to Event Ingest in batches.
  7. Events land in Kafka; consumers update royalty counts, listening history and recommendation features.
  8. Playback position is saved to Redis so the user can resume on another device.

Storage layer

Different data, different access patterns, different databases — not one engine forced to do everything.

DataDatabaseWhy
Track, album, artist metadataPostgreSQL + cacheRelational, read-heavy, low write rate
Playlists, library, followsCassandraHuge key-based data, horizontal scale

Core tables

-- PostgreSQL (catalog)
CREATE TABLE tracks (
  track_id    BIGINT PRIMARY KEY,
  album_id    BIGINT NOT NULL,
  title       TEXT NOT NULL,
  duration_ms INT,
  regions     TEXT[]               -- licensed countries
);
CREATE INDEX idx_tracks_album ON tracks(album_id);

-- Cassandra (user data, partitioned by owner)
CREATE TABLE playlist_items (
  playlist_id  UUID,
  position     TEXT,               -- fractional index, keeps order
  track_id     BIGINT,
  added_by     UUID,
  PRIMARY KEY (playlist_id, position)
);
CREATE TABLE user_library (
  user_id   UUID,
  added_at  TIMESTAMP,
  track_id  BIGINT,
  PRIMARY KEY (user_id, added_at)
) WITH CLUSTERING ORDER BY (added_at DESC);

Audio storage layout

Key:   audio/{track_id}/{bitrate}/chunk_{n}.ogg   (~5-10 sec chunks)
Meta:  audio/{track_id}/manifest.json               (chunk list per bitrate)

Small chunks let the client start after the first one, seek anywhere,
and switch bitrate mid-song. They also cache well at the edge.

Sharding strategy

  • Playlists — partition by playlist_id; all items of one playlist live together for fast ordered reads.
  • Library and history — partition by user_id so "my liked songs" is one partition read.
  • Catalog — small enough to replicate fully with read replicas; shard by track_id only if it outgrows a cluster.
  • Search — shard index by document hash; replicate for read throughput.
  • Audio — object keys prefixed by hashed track ID to avoid hot prefixes in S3.
06 / Deep dives

Deep dive on 3 critical components

For each: the problem, the naive solution, why it fails, and the real solution used at scale. Volunteer these problems before the interviewer asks — it signals senior-level thinking.

01 Audio delivery — instant start, no buffering

The problem: Serve 1.6 Tbps of audio to 10M listeners, start playback in under 500ms, and keep it smooth on bad networks, at a sane cost.

Naive solution — stream whole files from origin
GET /audio/{track_id}.mp3   → app server reads S3, streams bytes

Why it fails: App servers become bandwidth pipes and cannot scale to Tbps. Users far from the origin get high latency, a full-file download wastes data when they skip, and a single quality level stalls on weak networks.

Real solution — chunked adaptive streaming via CDN
1. Transcode at upload: 3+ bitrates, split into 5-10s chunks.

2. Playback Service returns a signed manifest URL only.
   Audio bytes never pass through our app servers.

3. Client fetches chunk by chunk from the nearest edge:
   - First chunk small → fast start
   - Adaptive bitrate: measure throughput, switch quality
   - Buffer 20-30s ahead; seek = jump to that chunk

4. Prefetch: load first chunk of the next queued track
   so song changes feel instant.

5. Cache warming: push new releases from big artists to
   edge nodes before release day.

6. Offline: download encrypted chunks, license key expires
   unless the app re-validates periodically.

Signed URLs expire in minutes, so links cannot be shared
to bypass subscription or region licensing.
The key insight: the control plane (auth, licensing, URLs) is tiny and stays in our services; the data plane (audio bytes) lives entirely on the CDN. Scaling audio then becomes a caching problem, not a compute problem.
02 Collaborative playlists — ordering under concurrent edits

The problem: Several users add, remove and reorder tracks in the same playlist, sometimes from offline phones. The list must converge to the same order everywhere without losing edits.

Naive solution — store the list as one array
playlist.tracks = [t1, t2, t3, ...]     -- read, modify, write back

Why it fails: Two users read the same array, each inserts a track, and the last write silently wipes the other's change. Rewriting a 10,000-track array for one insertion is also expensive and conflicts constantly.

Real solution — one row per item, fractional positions, versioned ops
1. Each track in a playlist is its own row, keyed by
   (playlist_id, position). Inserts touch one row only.

2. Position is a sortable string / fractional index:
   insert between "a" and "b" → "am". No renumbering of
   the rest of the list.

3. Edits are operations (add, remove, move) with a playlist
   version number. Server applies them in order and
   returns the new version.

4. Clients send the base version they edited from.
   Non-conflicting ops merge; concurrent moves resolve
   by last-writer-wins on that single item.

5. Offline edits are queued and replayed on reconnect.
   Changes pushed to open clients via WebSocket.

Per-item rows mean two people adding different songs at the
same time never conflict at all.
Full CRDTs or operational transforms give stronger guarantees but are heavy. For playlists, per-item rows plus fractional indexing cover nearly every real conflict at a fraction of the complexity.
03 Play events — accurate counts for royalties and recommendations

The problem: 1.25B plays a day must be captured even when phones go offline, and counted exactly once, because artists are paid per stream and recommendations depend on the data.

Naive solution — write each play to the database
onPlay(): db.execute("UPDATE tracks SET plays = plays + 1 ...")

Why it fails: ~15K writes/sec hammer one hot counter row for popular tracks, and a slow DB would hurt playback. Retries after a network failure double-count, and offline plays would be lost.

Real solution — event log, dedupe, then aggregate
1. Client emits events with a unique event_id (UUID),
   batches them and retries until acknowledged.
   Offline: store locally, upload on reconnect.

2. Ingest service validates and writes to Kafka.
   Partition by user_id to keep one user's events ordered.

3. At-least-once delivery + idempotent consumers:
   dedupe by event_id in a short-window store.

4. Royalty rule: a stream counts only after 30s of playback.
   Computed from start/heartbeat events, not client claims.

5. Stream processing (Flink/Spark) aggregates counts into
   the royalty ledger and per-track stats, batched, not per row.

6. Raw events land in the data lake → feed the feature
   store that drives recommendations.

Kafka is the durable buffer. If a consumer is down,
events wait; nothing is lost and playback is unaffected.
Reads for display (play counts on a track page) can lag by minutes. The royalty ledger is reconciled in batch from the raw log, so it stays correct even if the real-time counters drift.
07 / Tradeoffs & alternatives

What we did NOT choose and why

Rejected alternatives

AlternativeWhy rejected
Stream audio through app serversTurns compute servers into bandwidth pipes. The CDN with signed URLs is cheaper and faster.
Store audio in a databaseBlobs belong in object storage. Databases are for metadata and queries.
Single bitrate per trackStalls on weak networks and wastes data on strong ones. Adaptive bitrate costs a little storage for big UX gains.
Relational DB for user libraryKey-based access at huge scale with simple queries fits Cassandra better; joins are not needed.
Real-time recommendations on each requestToo slow and costly. Precompute offline, serve by lookup, refresh incrementally.
Synchronous play countingCouples playback to the analytics path. Async events keep playback independent.
Full CRDT for playlistsCorrect but heavy. Per-item rows with fractional indexing are enough.

What breaks at 10× scale and how we fix it

Problem — Album-drop thundering herd

A superstar releases at midnight; millions request the same new tracks, and every edge misses at once and hits origin.

Fix

Pre-warm edge caches before release, use request coalescing so one miss fetches for everyone, and add a mid-tier shield cache between edge and S3.

Problem — Hot partitions

A viral public playlist with millions of followers makes one Cassandra partition a hotspot.

Fix

Cache the playlist snapshot aggressively (reads are far more common than edits), and bucket very large partitions so load spreads across nodes.

Problem — Event pipeline lag

Kafka consumers fall behind during peak hours, delaying recommendations and dashboards.

Fix

Add partitions and consumers, auto-scale stream jobs on lag, and separate the royalty path from the analytics path so one cannot starve the other.

Problem — Global latency and licensing

Users worldwide need fast starts, but licences differ by country and some tracks are blocked in some regions.

Fix

Serve metadata from regional replicas, enforce region rules in the Playback Service before issuing the signed URL, and route users to their nearest edge.

08 / Summary

Cheat sheet

The ten things worth remembering before walking into the room.

Key numbers

50M DAU · 1.25B plays/day · ~45K peak play QPS · ~1.6 Tbps peak egress · ~1.7 PB audio · 250 GB events/day

Key databases

PostgreSQL (catalog) · Cassandra (playlists, library) · Redis (sessions) · Elasticsearch (search) · S3 (audio)

Streaming strategy

Transcode to 3 bitrates, 5-10s chunks, signed URLs, CDN serves the bytes, adaptive bitrate on the client.

Playlist strategy

One row per item, fractional positions, versioned ops, WebSocket push, offline edits queued.

Event pipeline

Client batches with event_id → Kafka → idempotent consumers → royalty ledger, stats, feature store.

Key tradeoffs

Cost vs. latency (CDN vs. origin). Storage vs. quality (more bitrates). Freshness vs. cost (recs).

Hardest part

Delivering Tbps of audio cheaply with instant start, while capturing every play exactly once.

Kafka's role

Durable buffer for play events feeding royalties, analytics and recommendations. Never on the playback path.

Sharding keys

Playlists → playlist_id · Library/history → user_id · Search → doc hash · Audio → hashed track_id prefix.
